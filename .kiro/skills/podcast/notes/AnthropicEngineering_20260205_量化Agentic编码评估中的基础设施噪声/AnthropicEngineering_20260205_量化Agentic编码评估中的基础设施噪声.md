## 核心发现

基础设施配置可以使 agentic 编码基准测试波动数个百分点——有时**超过排行榜上顶级模型之间的差距**。

在内部实验中，Terminal-Bench 2.0 上资源最多和最少的配置之间差距为 **6 个百分点**（p < 0.01）。这意味着：如果模型 A 在配置 X 上得分 72%，模型 B 在配置 Y 上得分 68%，你无法确定 A 真的比 B 好——差距可能完全由基础设施差异解释。

---

## 为什么 Agentic 评估不同于静态评估

**静态基准测试**（如 MMLU、HumanEval）直接评分模型输出——给一个 prompt，检查 response。运行时环境不影响结果。模型要么知道答案，要么不知道。

**Agentic 编码评估**根本不同：模型被给予一个完整环境，在其中编写程序、运行测试、安装依赖、多轮迭代。运行时不再是被动容器，而是**问题解决过程的组成部分**。

这个区别至关重要：两个资源预算和时间限制不同的 agent **不是在做同一份考试**。一个有 16 核 CPU 和 30 分钟超时的 agent，与一个有 2 核 CPU 和 5 分钟超时的 agent，面对的是本质不同的任务——前者可以尝试更多策略、运行更多测试、编译更快。

## 实验设计

为了量化基础设施噪声，我们在 Terminal-Bench 2.0 上用同一个模型（控制变量）运行多组实验，每组只改变一个基础设施参数。每个配置运行足够多次以获得统计显著性。

我们测试的变量包括：
- CPU 核数和 RAM 大小
- 执行时间限制
- 网络访问权限
- 磁盘 I/O 速度
- 容器启动状态（冷启动 vs 热缓存）

---

## 关键变量及其影响

### CPU 和 RAM

更多资源 = 更快的编译和测试 = 在相同时间限制内更多迭代机会。对于需要编译大型项目的任务（如 C++ 代码库），CPU 差异的影响尤为显著。一个需要 3 分钟编译的项目，在 2 核机器上可能只允许 agent 尝试 2 次，而在 16 核机器上可以尝试 8 次。

### 时间限制

更长的超时让 agent 可以尝试更多策略。我们观察到一个有趣的模式：**agent 的成功率不是随时间线性增长的**。很多任务要么在前几分钟解决，要么需要大量额外时间来尝试不同方法。这意味着时间限制的选择会不成比例地影响某些类型的任务。

### 网络访问

能否安装额外依赖直接影响解题策略。一些任务如果 agent 可以 `pip install` 一个特定库就变得简单，但在离线环境中需要从头实现。这不是在测量模型能力的差异，而是在测量环境约束的差异。

### 磁盘 I/O

影响大型项目的构建速度和日志读取速度。在 I/O 密集型任务上，SSD vs HDD 的差异可以改变 agent 的有效迭代次数。

## 对排行榜的影响

这些发现对公开基准排行榜有严重影响：

1. **几个百分点的差距可能完全由基础设施差异解释**。当排行榜上前三名模型的差距在 2-3% 时，如果它们使用了不同的基础设施配置，排名可能毫无意义。

2. **不同提交者可能使用不同配置**。即使基准测试规定了"推荐配置"，实际执行中的差异（云提供商、实例类型、网络条件）仍然引入噪声。

3. **同一模型在不同日期的得分可能不同**。如果评估基础设施有波动（共享资源、网络拥塞），即使模型没变，分数也会变。

## 建议

### 对基准测试设计者

1. **标准化并强制执行基础设施配置**——不仅指定资源，还要强制执行。使用容器化确保一致性。
2. **报告基础设施配置细节**——CPU、RAM、超时、网络访问、磁盘类型都应该是评估报告的一部分。
3. **量化你自己的基础设施噪声**——在发布基准之前，用同一模型在不同配置上运行，报告方差。
4. **考虑归一化**——如果可能，将分数归一化到标准配置，或报告置信区间。

### 对基准测试消费者

1. **谨慎解读小差距**——如果两个模型差距在基础设施噪声范围内，它们可能实际上没有区别。
2. **关注趋势而非绝对值**——同一配置上的相对变化比跨配置的绝对分数更有意义。
3. **要求透明度**——如果排行榜不报告基础设施配置，其结果的可信度应该打折扣。

### 更深层的问题

**强制方法论本身会改变基准测试实际测量的内容。** 如果你限制 CPU 到 2 核来"公平"，你实际上在测量"在资源受限环境中的表现"——这可能不是你想测量的。如果你给无限资源，你在测量"给定无限重试的最终能力"——这也可能不是你想测量的。

没有"正确"的配置——只有明确你在测量什么，并确保所有参与者在相同条件下被测量。
