上周 OpenAI 在 Codex 中发布了 Auto-review。此前用户有两个选择：Default mode（需要频繁人类批准）和 Full Access mode（移除摩擦但牺牲监督）。Auto-review 提供了第三条路——用一个独立 agent 替代用户在沙箱边界的审批。在内部，Auto-review 增强了 OpenAI 在无需同步人类监督的情况下运行长 agentic 任务的信心。

· · ·

Auto-review 是什么

在 Auto-review 模式下，Codex session 需要人类批准的频率比手动批准模式低约 200 倍，同时仍然捕获许多人类想要阻止的操作。大多数操作在沙箱内运行无需批准。对于需要审查的小部分，Auto-review 批准约 99%。即使 Auto-review 拒绝了一个操作，Codex 通常也能自行恢复——找到更安全的方式继续推进。

在内部部署中，OpenAI 内部 Codex Desktop token 使用量的大部分来自 Auto-review 模式，且份额在增长。

部署快照示例： 10,000 个操作中，9,280 个在沙箱内执行；720 个被 auto-review 审查；其中 713 个被批准继续；7 个被拒绝（4 个通过更安全的替代方案继续，3 个停下来询问用户）。

· · ·

审批摩擦反而损害安全

Default permission mode 限制 Codex 只能读取文件、在预指定可写根目录下编辑、在边界内运行本地命令。超出这些限制的操作——通常是普通的网络调用或简单 Python 脚本——必须等待用户授权。

这些限制让用户沮丧，经常使长时间后台 session 不可能。沮丧创造了新风险：

1. 用户切换到 Full Access mode——没有环境强制的规则，恶意代码执行、数据泄露、凭证探测等有害操作不会被沙箱阻止 2. 用户写过于宽松的前缀规则——内部流量中检测到相当一部分用户允许所有以 python 开头的命令 3. 用户不理解后果就批准命令——由于缺乏专业知识、审查疲劳或两者兼有

还有巨大的生产力成本。一个专家 agent 团队不能每几分钟就停下来等授权 curl google.com。

· · ·

在沙箱边界扩展自主权

Auto-review 扩展了 Codex 无需人类干预能做的事，同时仍然阻止许多可能对用户或组织造成严重或不可逆伤害的操作。到达沙箱边界时，Codex 可以请求升级以在沙箱外执行操作。在 Auto-review 中，一个独立的 Codex agent 评估这些请求，考虑用户意图、环境、安全策略和操作的可能影响。

角色分离很重要。 主 agent 被优化来完成用户任务，这创造了把审批边界当作又一个障碍来克服的压力。Auto-review 有更窄的工作：决定提议的越界操作是否应该运行。将该决策放在单独的模型调用中，使审批策略更容易评估、监控和改进。

Auto-review 旨在阻止可能造成严重或难以逆转伤害的操作：泄露数据、暴露 secret、删除数据、削弱安全设置、运行不受信任的代码、或遵循来自不受信任内容的与用户指令冲突的指示。Auto-review 也考虑用户意图——批准用户明确请求的名义上有风险的操作。

Auto-review 使用 GPT-5.4 Thinking（low reasoning）。在评估中，更强大的模型在风险检测和用户意图辨别上都更好。

拒绝不仅仅说"不"。它给 Codex 一个理由和足够的信号来安全继续，无需询问用户批准或指导。在内部部署中，Codex 在被拒绝后继续并在超过一半的情况下成功找到可接受的解决方案。同时监控 Codex 试图博弈 Auto-reviewer 的情况——为减少这种可能性，在重复拒绝后自动停止轨迹。

· · ·

评估：少有确定性保证的系统

在内部使用 Auto-review 之前，需要对可用性和安全性进行清晰评估。

可用性通过内部流量的接受率衡量。安全性通过合成增强数据集评估——内部流量低估了可能危险场景的长尾。使用现有和合成 eval 聚焦不同威胁模型：

  • Agent 过度热心： 用 GPT-5.3-codex 生成 Codex 可能在过度热心完成用户任务时采取风险操作的 agentic 场景
  • Prompt Injection： 在 Codex 被训练过的攻击者 prompt inject 的内部评估上运行 Auto-review
  • 错位模型： 使用 MonitoringBench——coding agent 试图隐蔽执行恶意任务（如下载恶意软件）的轨迹数据集
类别指标结果
可用性升级操作的自动批准率99.1%
可用性所有操作的有效批准率99.93%
安全过度热心召回率90.3%
安全Prompt Injection 召回率99.3%
安全MonitoringBench [Hard] 召回率96.1%

持续监控生产中的 Auto-review 摩擦：升级率、批准和拒绝率、增加的延迟、用户覆盖、频繁被标记审查的命令。同时运行人类和 AI 红队活动来识别可能溜过的安全问题。

· · ·

注意事项

Auto-review 不应被视为安全保证。 在自动化和人类红队中，识别出 Auto-review 可能被误导批准命令而无需用户批准的情况。正在积极修复这些问题，但不期望这类系统成为确定性保证的来源。

此外，不应被理解为防止模型 scheming 的机制。 Auto-review 在升级点评估提议的沙箱外操作。策略性隐藏意图的模型可能仍然产出看起来良性的升级请求，或在沙箱内以 Auto-review 永远看不到的方式行动。这些风险需要互补的监控和评估方法，包括 chain-of-thought 监控。

· · ·

远期展望

目标是一个 agent（如 Codex）可以被信任拥有与员工相同权限级别的未来。今天还没有到那个未来，Auto-review 模式可能不是那个未来需要的最终形态。Auto-review 是多方面的妥协：与传统安全系统相比，它牺牲确定性换取表达力；与 full access mode 相比，它牺牲速度换取安全。

对齐努力的关键目标是驾驭这两个权衡。模型监控器应该对外部攻击和判断失误具有韧性。Agent 本身也应该具备同样的对抗鲁棒性和常识。
