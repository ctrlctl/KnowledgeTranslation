## 为什么需要 Multi-Agent [04:52]

Rashmi 的核心论点：当你面对一个**复杂的、多面向的目标**时，multi-agent 架构才有意义。

从经典 ML 到 LLM 生成响应，再到需要执行具体行动——这是一个自然演进。Multi-agent 的适用场景是：你有一个大的复杂目标，可以拆解为多个步骤，每个步骤交给一个专注于该任务的 agent 来执行。

判断标准：如果一个应用需要服务**多种用户意图**，且需要自主决策和复杂推理，就不能用单一确定性模型解决，需要引入随机推理系统——也就是 multi-agent。

## Chat Concierge：落地案例 [06:17]

Chat Concierge 是 Capital One 的**首个 multi-agent 生产部署**（beachhead initiative），面向汽车经销商场景。

核心流程：

1. **意图识别 agent**：理解客户意图，通过追问来消歧
2. **规划 agent（planner）**：根据意图分发到不同工具/动作
3. **治理 agent**：验证响应是否符合风险标准、准确性、延迟要求
4. **响应精炼 agent**：将结果转化为客户能理解的自然语言

选择这个场景的原因：**高表面积、低风险**——既能覆盖足够多的交互模式来观察失败模式，又不会在出错时造成严重后果。

## 监管环境下的 Agent 治理 [10:05]

Capital One 的优势在于它本质上是一家"做银行业务的科技公司"，有成熟的**模型风险办公室（Model Risk Office）**。

治理分两层：

- **平台层**：强制性的企业级网络安全策略、guardrails、安全执行——这些对所有 agent 统一生效
- **应用层**：各业务线在平台基础上叠加自己的领域策略

关键设计原则是**策略绑定的 agent 操作（policy-bound agentic operations）**。策略通过多种方式在多个边界执行：guardrails、工具权限、agent manifest（定义 agent 被允许执行的动作范围）。

这让 agent 架构师可以专注于设计，而平台负责治理和合规。

## 平台架构与开发者体验 [16:15]

从经典 ML 到 agentic 系统的关键范式转变：

- **数据血缘和上下文血缘**需要跨多个 agent 传递，同时不能撑爆 context window
- **延迟不再是非功能性需求，而是产品特性**——直接影响用户体验
- 需要集成 memory 服务、tool 服务、数据治理

平台为不同成熟度的开发者提供不同层次的支持：

- **新手**：预构建蓝图（blueprints），拿来即用
- **熟练开发者**：SDK、框架、CLI、UI 全套工具链
- 底层基础设施（Kubernetes 等）通过 API 完全抽象

核心理念：**不剥夺开发者的自主权（agency）**。平台提供工具和可观测性，开发者根据观察到的系统行为自行决定如何调整。

---

## 可观测性的范式转变 [20:31]

Agentic 系统的可观测性比传统系统更关键，因为你在处理**随机系统之间的交互**。

需要观测的维度：

- 调用了哪些工具？
- 什么推理过程导致了该工具调用？
- 跨系统传递的上下文是什么？
- 端到端延迟 profile（不能只看单个模型的延迟）

关键洞察：**必须能够回放 agent 的行为**来理解系统如何运作。延迟优化是跨职能的端到端工作，不能孤立地只评估模型延迟。

Capital One 的做法是在已有的可观测性基础设施上，通过插件式 SDK 扩展 agent 特有的观测能力。

---

## 评估框架 [26:15]

基本原则与经典 ML 相同（golden dataset + 目标指标），但有一个关键区别：

**必须做端到端评估，而非单个 agent 评估。** 单个 agent 的评估结果没有意义，除非它在上下游整个系统中都能正常工作。

平台提供：
- 评估工具和管道
- Golden dataset 管理
- 沙箱环境

模型快速迭代的应对：平台内置推理优化层和基准测试机制，新模型可以快速实验和部署。

---

## 模型策略：专业化与推理分离 [28:37]

Capital One 的核心哲学：**数据优势就是 AI 优势**。

两个支柱：
1. **推理能力**：通过 agentic 框架提供
2. **专业化**：通过微调和 teacher-student 蒸馏实现个性化体验

倾向于自托管模型，因为：
- 需要用自有数据做专业化
- 需要控制延迟指标
- 蒸馏后的小模型在特定任务上既快又准

## Human-in-the-Loop 设计 [34:14]

Human-in-the-loop 通常部署在**高风险场景**。

设计原则：
- 作为 multi-agent 编排中的一个决策节点
- 平台对通知机制保持不可知（agnostic）——有的业务用 24/7 支持团队，有的用离线通知
- 关键是定义清楚**在哪个节点中断循环让人介入**，之后循环继续

平台的角色是提供灵活的编排框架，让业务线按自己的方式嵌入人类决策。

---

## 关键架构决策 [30:27]

Chat Concierge 项目的核心决策：

1. **从第一天就用平台思维**——即使是第一个 agent 应用，也按平台标准构建
2. **全栈方法**：数据位置、模型优化策略、跨层监控、延迟优化、开源基础模型的专业化策略
3. **工具标准选择**：MCP vs 原生 tool calling 等决策封装在平台内，对开发者透明
4. **人类交接点**：明确定义策略驱动的 handoff 触发条件

Rashmi 称之为"管弦乐问题"——如何编排从试点到生产再回到实验的整个生命周期。

## 闭环学习系统 [42:13]

Agentic 系统的定义特征：计划、推理、行动、观察、学习——形成闭环。

平台的角色：
- 在闭环的各个环节提供 hooks 和工具
- 可观测性捕获失败模式信号
- 信号回流到实验环境
- 开发者可以调整 prompt、模型、上下文管理、检索/grounding 等任何环节

关键洞察：**最大的收益来自生产后的遥测数据（post-production telemetry）**。

---

## 规模化挑战与经验教训 [46:03]

Capital One 当前处于 agentic 开发生命周期的**规模化阶段**——如何将系统扩展到服务数百万客户。

给同行的建议：

1. **把 agentic AI 当作系统来对待**——不是单个模型，是完整系统
2. **从治理数据开始**——数据优势是 AI 优势
3. **风险控制嵌入多层**——不是事后补丁
4. **延迟是端到端问题**——包括 handoff 在内
5. **生产后遥测是最大收益来源**
6. **不要丢弃已有技术栈**——Capital One 的云原生基础让 agentic 转型变得顺畅

对平台团队的额外建议：
- 识别缺失的服务和策略
- 用全新视角看待可观测性
- 尽早埋点，定义升级阈值
- **构建 agent 的问题已经解决了，现在的关键是 agent 在执行环境中的治理**
