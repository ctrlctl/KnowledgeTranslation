引言

好的评估帮助团队更自信地发布 AI agent。没有评估，容易陷入被动循环——只在生产中发现问题，修一个故障又制造新的。评估让问题和行为变化在影响用户之前就可见，其价值在 agent 的整个生命周期中持续累积。

正如我们在构建有效的 Agent 中描述的，agent 在多轮中运行：调用工具、修改状态、基于中间结果适应。这些让 agent 有用的能力——自主性、智能、灵活性——也让它们更难评估。

通过内部工作和与前沿 agent 开发客户的合作，我们学到了如何为 agent 设计更严格、更有用的评估。以下是在各种 agent 架构和真实部署场景中行之有效的方法。

· · ·

评估的结构

评估（eval） 是对 AI 系统的测试：给 AI 一个输入，然后对其输出应用评分逻辑来衡量成功。本文聚焦于开发期间无需真实用户即可运行的自动化评估。

单轮评估很直接：一个 prompt、一个响应、一套评分逻辑。对于早期 LLM，单轮非 agentic 评估是主要方法。随着 AI 能力进步，多轮评估变得越来越普遍。

Agent 评估更加复杂。Agent 跨多轮使用工具，修改环境状态并随之适应——这意味着错误会传播和累积。前沿模型还能找到超越静态评估限制的创造性解决方案。例如，Opus 4.5 在 τ2-bench 的一个航班预订问题中发现了政策中的漏洞。它按评估标准"失败"了，但实际上为用户找到了更好的解决方案。

构建 agent 评估时，我们使用以下定义：

  • Task（任务）：也叫 problem 或 test case，是一个有明确输入和成功标准的单个测试
  • Trial（试验）：对一个 task 的一次尝试。因为模型输出在运行间有变化，我们运行多次 trial 来产生更一致的结果
  • Grader（评分器）：对 agent 表现某方面打分的逻辑。一个 task 可以有多个 grader，每个包含多个 assertion（也叫 check）
  • Transcript（记录）：也叫 trace 或 trajectory，是一次 trial 的完整记录，包括输出、工具调用、推理、中间结果和所有交互。对 Anthropic API 来说，就是评估运行结束时的完整 messages 数组
  • Outcome（结果）：trial 结束时环境中的最终状态。航班预订 agent 可能在 transcript 末尾说"您的航班已预订"，但 outcome 是环境 SQL 数据库中是否存在预订记录
  • Evaluation harness（评估框架）：端到端运行评估的基础设施。提供指令和工具、并发运行 task、记录所有步骤、评分输出、聚合结果
  • Agent harness（agent 框架）：也叫 scaffold，使模型能作为 agent 行动的系统：处理输入、编排工具调用、返回结果。评估"一个 agent"时，我们评估的是 harness 和模型的协同工作
  • Evaluation suite（评估套件）：为衡量特定能力或行为而设计的 task 集合。套件中的 task 通常共享一个宽泛目标

Agent 评估的组成部分。

为什么要构建评估

团队刚开始构建 agent 时，通过手动测试、dogfooding 和直觉的组合可以走得出奇地远。更严格的评估甚至看起来像是拖慢发布的开销。但过了早期原型阶段，一旦 agent 进入生产并开始扩展，没有评估就会崩溃。

断裂点通常出现在用户报告 agent 在修改后感觉变差了，而团队"盲飞"——除了猜测和检查没有其他验证方式。没有评估时，调试是被动的：等投诉、手动复现、修 bug、祈祷没有其他回归。团队无法区分真正的回归和噪声，无法在发布前自动测试数百个场景，也无法衡量改进。

我们多次见证这个过程。例如，Claude Code 最初基于 Anthropic 员工和外部用户的反馈快速迭代。后来我们加了评估——先是针对简洁性和文件编辑等窄领域，然后是过度工程化等更复杂行为。这些评估帮助识别问题、指导改进、聚焦研究-产品协作。配合生产监控、A/B 测试、用户研究等，评估提供了持续改进 Claude Code 的信号。

评估在 agent 生命周期的任何阶段都有用。早期，评估迫使产品团队明确定义 agent 的成功标准；后期，它们帮助维持一致的质量标准。

评估还决定了你能多快采用新模型。当更强的模型发布时，没有评估的团队面临数周测试，而有评估的竞争对手可以快速确定模型优势、调优 prompt、几天内完成升级。

一旦评估存在，你免费获得基线和回归测试：延迟、token 使用量、每任务成本、错误率都可以在静态 task 库上跟踪。评估还能成为产品和研究团队之间最高带宽的沟通渠道，定义研究人员可以优化的指标。

如何评估 AI Agent

我们看到几种常见的大规模部署 agent 类型：编码 agent、研究 agent、计算机使用 agent、对话 agent。每种可能部署在各种行业，但可以用类似技术评估。

评分器类型

Agent 评估通常组合三种评分器：基于代码的、基于模型的、人工的。每种评分器评估 transcript 或 outcome 的某个部分。

基于代码的评分器：

  • 方法：字符串匹配（精确、正则、模糊）、二元测试（fail-to-pass、pass-to-pass）、静态分析（lint、类型、安全）、outcome 验证、工具调用验证、transcript 分析
  • 优势：快速、便宜、客观、可复现、易调试
  • 劣势：对有效变体脆弱、缺乏细微差别

基于模型的评分器：

  • 方法：基于 rubric 的评分、自然语言断言、成对比较、基于参考的评估、多 judge 共识
  • 优势：灵活、可扩展、捕获细微差别、处理开放式任务
  • 劣势：非确定性、比代码贵、需要与人工评分器校准

人工评分器：

  • 方法：SME 审查、众包判断、抽样检查、A/B 测试、标注者间一致性
  • 优势：金标准质量、匹配专家用户判断、用于校准模型评分器
  • 劣势：昂贵、慢、通常需要大规模获取人类专家

能力评估 vs 回归评估

能力评估（Capability evals） 问："这个 agent 能做好什么？"应该从低通过率开始，针对 agent 挣扎的任务，给团队一个可以攀爬的山坡。

回归评估（Regression evals） 问："agent 还能处理它以前能处理的所有任务吗？"应该有接近 100% 的通过率。它们防止倒退——分数下降意味着有东西坏了。

Agent 发布和优化后，通过率高的能力评估可以"毕业"成为持续运行的回归套件。曾经衡量"我们能做到这个吗？"的 task 变成衡量"我们还能可靠地做到这个吗？"

评估编码 Agent

编码 agent 编写、测试和调试代码，像人类开发者一样浏览代码库和运行命令。确定性评分器对编码 agent 很自然，因为软件通常容易评估：代码能跑吗？测试通过吗？

两个广泛使用的编码 agent 基准：

  • SWE-bench Verified：给 agent 来自流行 Python 仓库的 GitHub issue，通过运行测试套件评分。LLM 在一年内从 40% 进步到 >80%
  • Terminal-Bench：测试端到端技术任务，如从源码构建 Linux 内核或训练 ML 模型

有了验证关键 outcome 的通过/失败测试后，通常还有用的是评估 transcript。例如，基于启发式的代码质量规则可以评估生成代码的质量（不仅仅是通过测试），基于模型的评分器配合清晰 rubric 可以评估 agent 如何调用工具或与用户交互。

评估对话 Agent

对话 agent 的成功可以是多维的：工单是否解决（状态检查）、是否在 <10 轮内完成（transcript 约束）、语气是否恰当（LLM rubric）？

评估研究 Agent

研究评估面临独特挑战：专家可能对综述是否全面有分歧，ground truth 随参考内容不断变化，更长更开放的输出留下更多出错空间。

一种策略是组合评分器类型：groundedness check 验证声明有检索来源支持，coverage check 定义好答案必须包含的关键事实，source quality check 确认咨询的来源权威。对有客观正确答案的任务用精确匹配。LLM 可以标记无支持的声明和覆盖缺口，也可以验证开放式综述的连贯性和完整性。

处理非确定性

无论 agent 类型如何，agent 行为在运行间有变化，这使评估结果比表面看起来更难解读。每个 task 有自己的成功率——可能一个 task 90%，另一个 50%——一次评估运行通过的 task 下次可能失败。

两个指标帮助捕获这种细微差别：

  • pass@k：k 次尝试中至少一次成功的概率。适用于一次成功就够的工具
  • pass^k：k 次尝试全部成功的概率。适用于一致性至关重要的 agent

从零到一：构建优秀评估的路线图

从小处开始

我们看到团队因为觉得需要数百个 task 而推迟构建评估。实际上，20-50 个从真实失败中提取的简单 task 就是很好的起点。早期 agent 开发中，每次系统修改通常有明显的影响，这种大效应量意味着小样本量就够了。评估等得越久越难构建——早期产品需求自然转化为测试用例，等太久就得从线上系统逆向工程成功标准。

从真实失败中提取 task

从开发期间运行的手动检查开始——每次发布前验证的行为和终端用户常试的任务。如果已经在生产中，看 bug tracker 和支持队列。将用户报告的失败转化为测试用例，确保套件反映实际使用；按用户影响优先级排序。

确保 task 质量

好的 task 是两个领域专家会独立得出相同通过/失败判定的 task。task 规范中的歧义变成指标中的噪声。每个 task 应该是正确遵循指令的 agent 可以通过的。

例如，审计 Terminal-Bench 发现：如果 task 要求 agent 写一个脚本但没指定文件路径，而测试假设了特定路径，agent 可能因为自身无过错而失败。评分器检查的一切都应该在 task 描述中明确；agent 不应因为模糊规范而失败。

对每个 task，创建一个参考解决方案很有用：一个已知可工作的输出，通过所有评分器。这证明 task 可解，并验证评分器配置正确。

测试正面和负面情况

测试行为应该发生的情况和不应该发生的情况。

确保环境隔离

每次 trial 应该从干净环境开始。运行间不必要的共享状态（残留文件、缓存数据、资源耗尽）可能导致因基础设施不稳定而非 agent 性能的相关失败。共享状态也可能人为抬高性能——例如，在一些内部评估中我们观察到 Claude 通过检查之前 trial 的 git 历史获得不公平优势。

选择正确的评分器

推荐：尽可能选择确定性评分器，必要时用 LLM 评分器获得额外灵活性，审慎使用人工评分器做额外验证。

有一种常见冲动是检查 agent 是否遵循了非常具体的步骤，如按正确顺序调用工具序列。我们发现这种方法太僵硬，导致过于脆弱的测试——agent 经常找到评估设计者没预料到的有效方法。评估 agent 产出了什么，而非它走的路径，通常更好。

LLM-as-judge 评分器应该与人类专家紧密校准。为避免幻觉，给 LLM 一个出路，如提供"当信息不足时返回 Unknown"的指令。

· · ·

评估如何与其他方法配合

评估是理解 agent 行为的一种方法，但不是唯一的。它们与生产监控、A/B 测试、用户研究等方法互补。评估在开发期间提供快速反馈循环，而生产监控捕获评估无法预见的真实世界边缘情况。

· · ·

结论

Agent 评估不需要完美才有用。从小处开始，聚焦真实失败，随着 agent 成熟逐步扩展。评估的价值随时间复合——前期成本可见，但收益持续累积。

关键要点：

  • 评估让问题在影响用户之前可见
  • 组合代码、模型和人工评分器来匹配 agent 的复杂性
  • 从 20-50 个基于真实失败的 task 开始
  • 评估 outcome 而非路径
  • 确保环境隔离以获得可靠结果
  • 能力评估攀爬山坡，回归评估防止倒退
