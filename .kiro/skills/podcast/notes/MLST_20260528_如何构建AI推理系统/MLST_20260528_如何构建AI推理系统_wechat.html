推理为什么难 [07:38]

Philip 用格斗做类比：推理工程就像综合格斗（MMA），你不能只精通一个方面就指望赢。你需要同时掌握：

  • GPU 层面：CUDA 编程、PyTorch、推理引擎
  • 应用研究：量化技术、投机解码（speculative decoding）、KV cache 复用、模型并行化、disaggregation
  • 分布式系统：过去 20 年云架构的所有经典问题
  • 大规模流量处理：全球范围的高并发请求

这些全部要在几百毫秒的延迟 SLA 内协调完成。推理的难度在于把大量复杂系统编排在一起。

· · ·

研究到生产的速度 [10:06]

推理领域的研究到生产时间线可能是全世界最快的。医学需要几十年，物理工程需要几年，即使是 AI 训练也需要几周到几个月来调参。但推理的时间线往往是几小时。

一个新模型架构发布，你必须在第零天就搞清楚怎么支持它。Base10 的一位工程师在 PoloQuant 论文发布后 31 小时就实现了对应的 CUDA kernel。

唯一可能比推理更快的领域是量化交易（trading，不是 training）。

谁应该关心推理工程 [13:46]

两个理由：

1. 职业方向：三年前全世界可能只有几百个推理工程师，现在有数万人。即使 AI 辅助编码让个人生产力大幅提升，Philip 认为未来几年推理工程师的需求还会增长 10 到 100 倍。

2. 产品差异化：每个垂直 AI 应用公司最终都要搞清楚自己的推理策略。好的推理是"产品感觉像魔法"和"慢到让用户流失"之间的区别。

理解推理解锁更好的产品 [16:22]

大多数 AI 工程师在 GPT/Claude 的世界观里长大：有 N 个模型，每个有固定的智能水平、固定的速度、固定的成本、固定的可靠性。

推理工程的第一课是：这些不是离散的点，而是一个频谱。你可以通过调整 batch size、添加或移除投机解码算法来在延迟和吞吐之间做权衡。

理解这个频谱后，你可以：

  • 在产品中实现优先级队列（付费用户优先于免费用户）
  • 用自己的 eval 来量化模型，确信不会降低质量，而不是被第三方提供商随机降智
  • 理解 KV cache 复用的工作方式——前缀中哪怕一个 token 的差异都会让后续整个缓存失效——从而优化 chat template 的结构

推理成熟度路径 [23:12]

这是一个产品成熟度周期，不是公司成熟度周期。小公司可能比大公司走得更远。

1. 按 token 付费的闭源模型：几乎所有人都应该从这里开始。API key 就能获得前沿智能。 2. 超大规模云服务商：遇到成本或容量问题时，转向 AWS/GCP 的 provisioned throughput、Bedrock/Vertex 等。 3. 专业推理提供商（如 Base10）：拥有模型权重，做专用部署，按 GPU 时间付费而非按 token。 4. 自建平台或边缘推理：用自己的团队搭建推理平台，或者做大规模边缘部署。

Philip 观察到越来越少的公司选择"买一堆 GPU 放地下室"的路线（医疗和金融除外），更多人倾向于 buy 而非 build。

GPU 生命周期与硬件趋势 [27:59]

Philip 经历了三代 GPU 周期：Ampere → Hopper → Blackwell。

Hopper 的持久力惊人：

  • 大量开源工作来自中国实验室，受出口管制限制，他们在 Hopper 上开发
  • 开源社区产出的 FP8 kernel、异步编程范式都是为 Hopper 优化的
  • 模型尺寸是为 8×H200 节点设计的，而非 GB300 NVL72
  • H100 的租赁价格现在比一年前更贵

Ampere 已经过时：主要因为不支持 FP8 量化，必须全精度运行。

小模型的需求：embedding 模型、语音模型只有 1-8B 参数，用 MIG（多实例 GPU）切分一片 Hopper 就够了，不需要最新的 Blackwell。

Philip 对 GPU 代际的有效寿命非常乐观——从 Hopper 开始，5-6 年后仍在大量使用。

推理工程作为职业方向 [32:22]

AI 辅助编码确实在加速推理工程的某些部分，比如 CUDA kernel 编写——已经有一堆开源项目和创业公司在做按需定制 kernel。

但推理系统相对于模型来说仍然非常通用。当前是用通用框架、通用 kernel、通用硬件来跑特定架构。未来的推理系统可能比今天复杂 10 倍——更加针对具体 workload 做特化。

Base10 的说法是："You can't vibe code uptime." 对于承载数亿美元经济价值的关键系统，仍然需要能对结果负责的人类 owner。

Agent 时代对推理的影响 [37:23]

Agent 对推理的需求是驱动专业化优化的核心动力。

  • 聊天世界：用户每次操作 → 1 个请求 → 1 个模型
  • Agent 世界：用户每次操作 → 几十、几百甚至上千个请求 → 跨多个模型

如果你想让 agent 又快又可靠，每一个模型以及它们之间的每一个连接都必须快且可靠。这让推理成为更关键的挑战。

能够快速优化单个模型和单个 workload（可能借助 AI 加速编程）意味着你可以更可靠地构建和扩展 agent。

多模态与工具推理 [38:39]

分类任务的例子：你可以用 Opus 4.6 + Max Thinking High 来分类数据，得到极好的结果但花很多钱。或者用传统 ML 分类器，同样好的结果但几乎免费。

关键不只是省钱，还有省时间。命名实体识别（NER）用 flash 模型可能需要 500ms，Base10 刚发布的专用运行时只需要 1ms。如果 agent 每次用户请求要做 100 次 NER，这就是"看转圈"和"瞬间完成"的区别。

VLM 的痛点：视觉语言模型前面有个小小的 1B 参数视觉编码器，后面是万亿参数的 LLM。这个小编码器反而经常比 LLM 本身造成更多运行时问题——因为各家的视觉编码器太异构了，软件支持远不够。

TTS 模型的意外收益：现代 TTS 本质上是极度微调的 LLM，扩展了词表来包含音频波形 token。可以直接塞进 TensorRT-LLM 就跑起来。但即使架构相似，性能目标不同——TTS 只需要 ~100 tokens/s 的实时速率，达到后应该增大 batch size 来跑更多并发流，而不是继续追求更高 TPS。

推理引擎生态 [47:34]

开源推理引擎的集中度非常高，主要就三个：vLLM、SGLang、TensorRT-LLM。

原因是从零搭建一个完整推理引擎的复杂度极高，大多数人更愿意贡献到已有项目。即使是推理提供商，也倾向于拿开源引擎做定制，而非完全重写——除非他们有自研硬件或自研编程语言。

围绕推理优化的开源工作很活跃：kernel 库、量化工具、KV cache 复用工具、投机解码等。

· · ·

硬件层面的专业化 [49:51]

  • Talos ASIC：把 Llama 3.1 8B 直接烧到芯片上，达到 16,000 tokens/s
  • Disaggregation 趋势：NVIDIA 收购 Groq 做专用 prefill 计算 vs decode 计算；AWS 把 Trainium 和 Cerebras 组合做 decode
  • 2026 可能是 disaggregation 之年——对超大规模 workload（单模型百万并发请求）特别有意义

硬件专业化刚刚开始，会带来大量行业解锁，但不会完全取代对精密软件的需求。

· · ·

2026 年展望 [51:29]

Philip 最兴奋的趋势是企业开始拥有自己的智能：

  • Shopify 迁移到 Qwen 模型，节省了数千万美元
  • COSO 推出 Composer 等复杂模型，为用户创造差异化体验

如果你想构建真正差异化的产品，你需要在每一层都做差异化——包括模型层。
