Claude Code 是一个 agentic 编码环境。与回答问题然后等待的聊天机器人不同，Claude Code 可以读取你的文件、运行命令、做出修改，并在你观看、重定向或完全离开时自主解决问题。

这改变了你的工作方式。你不再自己写代码然后让 Claude 审查，而是描述你想要什么，Claude 来弄清楚如何构建它。Claude 探索、规划、实现。但这种自主性仍然有学习曲线——Claude 在你需要理解的某些约束内工作。

本指南涵盖了在 Anthropic 内部团队和各种代码库、语言、环境中使用 Claude Code 的工程师中被证明有效的模式。

---

## 核心约束：上下文窗口

大多数最佳实践基于一个约束：**Claude 的上下文窗口填充得很快，性能随着填充而下降。**

Claude 的上下文窗口保存你的整个对话，包括每条消息、Claude 读取的每个文件和每个命令输出。然而，这可能很快填满。一次调试会话或代码库探索可能生成和消耗数万 token。

这很重要，因为 LLM 性能随着上下文填充而下降。当上下文窗口快满时，Claude 可能开始"忘记"早期指令或犯更多错误。**上下文窗口是最重要的需要管理的资源。**

## 给 Claude 验证自身工作的方式

包含测试、截图或预期输出，让 Claude 可以自我检查。**这是你能做的最高杠杆的事情。**

当 Claude 能验证自己的工作时——运行测试、比较截图、验证输出——它的表现会显著提升。没有明确的成功标准，它可能产出看起来对但实际不工作的东西。你成为唯一的反馈循环，每个错误都需要你的注意。

| 策略 | 之前 | 之后 |
|------|------|------|
| 提供验证标准 | "实现一个验证邮箱的函数" | "写一个 validateEmail 函数。测试用例：user@example.com 为 true，invalid 为 false，user@.com 为 false。实现后运行测试" |
| 视觉验证 UI 变更 | "让仪表盘更好看" | "[粘贴截图] 实现这个设计。截图结果并与原始对比。列出差异并修复" |
| 解决根本原因 | "构建失败了" | "构建失败，错误是：[粘贴错误]。修复它并验证构建成功。解决根本原因，不要压制错误" |

你的验证也可以是测试套件、linter 或检查输出的 Bash 命令。投资让你的验证坚如磐石。

## 先探索，再规划，再编码

将研究和规划与实现分开，避免解决错误的问题。让 Claude 直接跳到编码可能产出解决错误问题的代码。使用 plan mode 将探索与执行分开。

推荐的工作流有四个阶段：

1. **探索：** 进入 plan mode。Claude 读取文件并回答问题，不做修改。
2. **规划：** 让 Claude 创建详细的实现计划。按 Ctrl+G 在文本编辑器中打开计划直接编辑。
3. **实现：** 退出 plan mode，让 Claude 编码，对照计划验证。
4. **提交：** 让 Claude 用描述性消息提交并创建 PR。

Plan mode 有用但也增加开销。对于范围明确且修复小的任务（如修复拼写错误、添加日志行或重命名变量），直接让 Claude 做。规划在你不确定方法、变更涉及多个文件、或你不熟悉被修改的代码时最有用。如果你能用一句话描述 diff，跳过规划。

## 在 prompt 中提供具体上下文

指令越精确，需要的修正越少。Claude 能推断意图，但不能读心。引用具体文件，提及约束，指向示例模式。

| 策略 | 之前 | 之后 |
|------|------|------|
| 限定任务范围 | "给 foo.py 加测试" | "为 foo.py 写测试，覆盖用户已登出的边缘情况。避免 mock。" |
| 指向来源 | "为什么 ExecutionFactory 的 API 这么奇怪？" | "查看 ExecutionFactory 的 git 历史，总结它的 API 是如何演变的" |
| 引用现有模式 | "添加日历组件" | "看看首页现有组件是如何实现的来理解模式。HotDogWidget.php 是个好例子。按照模式实现新的日历组件..." |
| 描述症状 | "修复登录 bug" | "用户报告会话超时后登录失败。检查 src/auth/ 中的认证流程，特别是 token 刷新。写一个复现问题的失败测试，然后修复" |

模糊 prompt 在你探索且能承受纠正时也有用。像"你会改进这个文件的什么？"这样的 prompt 可以浮现你不会想到要问的东西。

## 提供丰富内容

用 `@` 引用文件、粘贴截图/图片，或直接管道传入数据。你可以通过多种方式向 Claude 提供丰富数据：
- 用 `@` 引用文件而不是描述代码位置
- 直接粘贴图片
- 给出文档和 API 参考的 URL
- 用 `cat error.log | claude` 管道传入数据
- 让 Claude 自己获取需要的内容

## 配置你的环境

### 编写有效的 CLAUDE.md

运行 `/init` 生成基于当前项目结构的起始 CLAUDE.md 文件，然后随时间精炼。

CLAUDE.md 是 Claude 在每次对话开始时读取的特殊文件。包含 Bash 命令、代码风格和工作流规则。这给 Claude 提供了它无法从代码中推断的持久上下文。

保持简洁和人类可读。对每一行问："删除这行会导致 Claude 犯错吗？"如果不会，删掉它。**臃肿的 CLAUDE.md 文件会导致 Claude 忽略你的实际指令！**

✅ 包含：Claude 猜不到的 Bash 命令、与默认不同的代码风格规则、测试指令、仓库礼仪、架构决策、环境怪癖、常见陷阱

❌ 排除：Claude 通过读代码能弄清的东西、标准语言约定、详细 API 文档（改为链接）、经常变化的信息、长解释或教程、文件逐个描述、不言自明的实践

像对待代码一样对待 CLAUDE.md：出问题时审查它，定期修剪，通过观察 Claude 的行为是否实际改变来测试变更。

### 配置权限

使用 auto mode 让分类器处理审批，`/permissions` 允许列出特定命令，或 `/sandbox` 进行 OS 级隔离。每种都减少中断同时保持你的控制。

### 使用 CLI 工具

告诉 Claude Code 在与外部服务交互时使用 `gh`、`aws`、`gcloud`、`sentry-cli` 等 CLI 工具。CLI 工具是与外部服务交互最上下文高效的方式。

### 连接 MCP 服务器

运行 `claude mcp add` 连接 Notion、Figma 或数据库等外部工具。

### 设置 Hooks

对必须每次无例外发生的操作使用 hooks。Hooks 在 Claude 工作流的特定点自动运行脚本。与 CLAUDE.md 指令（建议性的）不同，hooks 是确定性的，保证操作发生。

### 创建 Skills

在 `.claude/skills/` 中创建 SKILL.md 文件，给 Claude 领域知识和可复用工作流。Skills 用特定于你项目、团队或领域的信息扩展 Claude 的知识。Claude 在相关时自动应用它们，或你可以用 `/skill-name` 直接调用。

### 创建自定义子 Agent

在 `.claude/agents/` 中定义专门的助手，Claude 可以将隔离任务委派给它们。子 agent 在自己的上下文中运行，有自己的允许工具集。

### 安装插件

运行 `/plugin` 浏览市场。插件无需配置即可添加 skills、工具和集成。

## 交互策略

### 提问代码库问题

像问高级工程师一样问 Claude 问题。在新代码库入职时，用 Claude Code 进行学习和探索。

### 让 Claude 采访你

对于较大功能，先让 Claude 采访你。从最小 prompt 开始，让 Claude 用 AskUserQuestion 工具采访你。Claude 会问你可能没考虑到的事情。

### 尽早且频繁地纠正方向

一旦注意到 Claude 偏离轨道就纠正它。最好的结果来自紧密的反馈循环。
- **Esc：** 中途停止 Claude
- **Esc + Esc 或 /rewind：** 恢复之前的对话和代码状态
- **"撤销那个"：** 让 Claude 回退更改
- **/clear：** 在不相关任务之间重置上下文

如果你在同一会话中对同一问题纠正了 Claude 两次以上，上下文已经被失败方法搞乱了。运行 `/clear` 并用更具体的 prompt 重新开始。

### 积极管理上下文

在不相关任务之间运行 `/clear` 重置上下文。Claude Code 在接近上下文限制时自动压缩对话历史。在长会话中，频繁使用 `/clear`。对于不需要留在上下文中的快速问题，使用 `/btw`。

### 使用子 Agent 进行调查

用"使用子 agent 调查 X"来委派研究。它们在单独的上下文中探索，保持你的主对话干净用于实现。

### 用检查点回退

你发送的每个 prompt 都创建一个检查点。你可以将对话、代码或两者恢复到任何之前的检查点。双击 Escape 或运行 `/rewind` 打开回退菜单。

### 恢复对话

用 `/rename` 命名会话，像分支一样对待它们。运行 `claude --continue` 继续最近的会话，或 `claude --resume` 从列表中选择。

## 自动化与扩展

一旦你能有效使用一个 Claude，用并行会话、非交互模式和扇出模式来倍增你的产出。

### 运行非交互模式

使用 `claude -p "prompt"` 在 CI、pre-commit hooks 或脚本中运行。添加 `--output-format stream-json` 获取流式 JSON 输出。

### 运行多个 Claude 会话

并行运行多个 Claude 会话来加速开发、运行隔离实验或启动复杂工作流。选择适合你想要多少协调的并行方法：Worktrees、桌面应用、Web 上的 Claude Code、Agent 团队。

也可以使用 Writer/Reviewer 模式：一个会话写代码，另一个审查。

### 跨文件扇出

循环遍历任务，对每个调用 `claude -p`。使用 `--allowedTools` 限定批量操作的权限。

### 用 Auto Mode 自主运行

对于无中断执行加后台安全检查，使用 auto mode。分类器模型在命令运行前审查，阻止范围升级、未知基础设施或恶意内容驱动的操作。

## 避免常见失败模式

- **厨房水槽会话：** 一个任务开始，然后问不相关的东西，再回到第一个任务。修复：任务之间 `/clear`。
- **反复纠正：** Claude 做错了，你纠正，还是错，再纠正。修复：两次失败纠正后，`/clear` 并写更好的初始 prompt。
- **过度指定的 CLAUDE.md：** 太长导致 Claude 忽略一半。修复：无情修剪。
- **信任-验证差距：** Claude 产出看似合理但不处理边缘情况的实现。修复：始终提供验证。
- **无限探索：** 让 Claude "调查"某事但不限定范围。修复：缩小调查范围或使用子 agent。

## 培养你的直觉

本指南中的模式不是一成不变的。它们是通常有效的起点，但可能不是每种情况的最优解。

有时你应该让上下文积累，因为你深入一个复杂问题且历史有价值。有时你应该跳过规划让 Claude 自己弄清楚。有时模糊 prompt 恰好正确。

注意什么有效。当 Claude 产出优秀输出时，注意你做了什么：prompt 结构、你提供的上下文、你所在的模式。当 Claude 挣扎时，问为什么。上下文太嘈杂？Prompt 太模糊？任务对一次 pass 来说太大？

随着时间推移，你会发展出任何指南都无法捕捉的直觉。
