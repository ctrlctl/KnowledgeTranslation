Claude 现在具备了 Research 能力，可以跨网页、Google Workspace 以及各种集成工具来完成复杂任务。

这个 multi-agent 系统从原型走到生产的过程，教会了我们关于系统架构、工具设计和 prompt engineering 的关键经验。Multi-agent 系统由多个 agent（LLM 在循环中自主使用工具）协同工作组成。我们的 Research 功能涉及一个 agent 根据用户查询规划研究过程，然后用工具创建并行的 agent 同时搜索信息。多 agent 系统引入了 agent 协调、评估和可靠性方面的新挑战。

这篇文章拆解了对我们有效的原则——希望你在构建自己的 multi-agent 系统时也能用上。

## 为什么用 Multi-Agent

研究工作涉及开放式问题，很难提前预测所需步骤。你无法为探索复杂主题硬编码一条固定路径——过程本质上是动态的、路径依赖的。人们做研究时，倾向于根据发现持续更新方法，追踪调查中涌现的线索。

这种不可预测性使 AI agent 特别适合研究任务。研究需要灵活性——在调查展开时随时转向或探索旁支联系。模型必须自主运行很多轮，根据中间发现决定追求哪些方向。线性的 one-shot 流水线无法处理这类任务。

**搜索的本质是压缩**：从庞大语料库中提炼洞察。Sub-agent 通过在各自的 context window 中并行运行来促进压缩——同时探索问题的不同方面，然后为主研究 agent 浓缩最重要的 token。每个 sub-agent 还提供了**关注点分离**（separation of concerns）——不同的工具、prompt 和探索轨迹——减少路径依赖，实现彻底、独立的调查。

一旦智能达到某个阈值，multi-agent 系统就成为扩展性能的关键方式。举个例子：虽然个体人类在过去 10 万年里变得更聪明了，但人类社会在信息时代的能力呈指数级增长，原因在于我们的**集体智能**和协调能力。即使是通用智能的 agent，作为个体也有极限；一群 agent 能做到的远远更多。

我们的内部评估显示，multi-agent 研究系统在**广度优先查询**（同时追求多个独立方向）上尤其出色。以 Claude Opus 4 为主 agent、Claude Sonnet 4 为 sub-agent 的 multi-agent 系统，在内部研究 eval 上**比单 agent Claude Opus 4 高出 90.2%**。例如，当被要求找出信息技术领域 S&P 500 公司的所有董事会成员时，multi-agent 系统通过将任务分解给 sub-agent 找到了正确答案，而单 agent 系统用缓慢的顺序搜索未能找到答案。

Multi-agent 系统之所以有效，主要是因为它们帮助花费足够多的 token 来解决问题。在我们的分析中，三个因素解释了 [BrowseComp](https://openai.com/index/browsecomp/) 评估（测试浏览 agent 定位难找信息的能力）中 95% 的性能方差。我们发现 token 使用量本身解释了 80% 的方差，工具调用次数和模型选择是另外两个解释因素。这一发现验证了我们将工作分布到具有独立 context window 的 agent 的架构决策——为并行推理增加更多容量。最新的 Claude 模型在 token 使用效率上是巨大的乘数：升级到 Claude Sonnet 4 带来的性能提升，比在 Claude Sonnet 3.7 上翻倍 token 预算还要大。Multi-agent 架构有效地为超出单 agent 极限的任务扩展了 token 使用。

当然也有代价：实践中，这些架构消耗 token 很快。在我们的数据中，agent 通常使用约 4× 于聊天交互的 token，multi-agent 系统使用约 15× 于聊天的 token。要实现经济可行性，multi-agent 系统需要任务价值足够高，能够为增加的性能买单。此外，有些领域目前不适合 multi-agent 系统——需要所有 agent 共享同一 context 的场景，或 agent 之间存在大量依赖关系的场景。例如，大多数编码任务的真正可并行化部分比研究少，而且 LLM agent 目前还不擅长实时协调和委派给其他 agent。我们发现 multi-agent 系统擅长的是重度并行化的高价值任务、超出单个 context window 的信息量、以及需要与大量复杂工具交互的场景。

## 架构概览

我们的 Research 系统使用**编排者-工人（orchestrator-worker）模式**的 multi-agent 架构：主 agent 协调整个过程，同时委派给并行运行的专门化 sub-agent。

![Multi-agent 架构图](images/fig_02.png)

*图：用户查询流经主 agent，主 agent 创建专门化 sub-agent 并行搜索不同方面*

用户提交查询时，主 agent 分析查询、制定策略、生成 sub-agent 同时探索不同方面。如上图所示，sub-agent 充当智能过滤器——迭代使用搜索工具收集信息（这个例子中是搜索 2025 年的 AI agent 公司），然后将公司列表返回给主 agent，由主 agent 编译最终答案。

传统的 RAG（Retrieval Augmented Generation，检索增强生成）方法使用静态检索：获取与输入查询最相似的一组 chunk，然后用这些 chunk 生成回答。相比之下，我们的架构使用**多步搜索**——动态发现相关信息、适应新发现、分析结果以形成高质量答案。

![完整工作流程图](images/fig_03.png)

*图：Research 系统完整工作流。用户提交查询后，系统创建 LeadResearcher agent 进入迭代研究过程。LeadResearcher 先思考方法并将计划保存到 Memory 以持久化 context（因为超过 200K token 时 context 会被截断，保留计划很重要）。然后创建专门化 Sub-agent（图中展示了两个，但数量不限）执行具体研究任务。每个 Sub-agent 独立执行网络搜索，用 [interleaved thinking](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking#interleaved-thinking) 评估工具结果，然后将发现返回给 LeadResearcher。LeadResearcher 综合这些结果，决定是否需要更多研究——如果需要，可以创建额外的 sub-agent 或调整策略。信息充足后，系统退出研究循环，将所有发现传给 CitationAgent，由它处理文档和研究报告以标注引用位置。这确保所有主张都正确归因到来源。最终带引用的研究结果返回给用户。*

## Prompt Engineering 与工具设计

Multi-agent 系统与单 agent 系统有关键区别，其中之一是协调复杂度的快速增长。早期 agent 犯过的错误包括：为简单查询生成 50 个 sub-agent、无休止地搜索不存在的来源、用过多更新互相干扰。由于每个 agent 都由 prompt 驱动，prompt engineering 是我们改进这些行为的主要杠杆。以下是我们学到的 agent prompting 原则：

### 1. 像你的 Agent 一样思考

要迭代 prompt，你必须理解它们的效果。为此，我们在 [Console](https://console.anthropic.com/) 中用系统的精确 prompt 和工具构建模拟，然后逐步观察 agent 工作。这立即揭示了失败模式：agent 在已有足够结果时继续搜索、使用过于冗长的搜索查询、选择错误的工具。有效的 prompting 依赖于建立对 agent 的准确心智模型——有了这个模型，最有影响力的改动往往显而易见。

### 2. 教编排者如何委派

在我们的系统中，主 agent 将查询分解为子任务并描述给 sub-agent。每个 sub-agent 需要：**目标、输出格式、工具和来源指导、清晰的任务边界**。没有详细任务描述时，agent 会重复工作、留下空白、或找不到必要信息。

我们最初允许主 agent 给出简短指令，比如"研究半导体短缺"，但发现这些指令往往模糊到 sub-agent 误解任务或执行与其他 agent 完全相同的搜索。例如，一个 sub-agent 在探索 2021 年汽车芯片危机，另外两个在重复调查 2025 年当前供应链——没有有效的分工。

### 3. 按查询复杂度缩放努力

Agent 难以判断不同任务的适当努力程度，所以我们在 prompt 中嵌入了缩放规则。简单事实查找只需要 1 个 agent 加 3-10 次工具调用，直接比较可能需要 2-4 个 sub-agent、每个 10-15 次调用，而复杂研究可能用到 10 个以上 sub-agent 并明确分工。这些显式指南帮助主 agent 高效分配资源，防止在简单查询上过度投入——这是我们早期版本的常见失败模式。

### 4. 工具设计和选择至关重要

Agent-工具接口与人机接口同等关键。使用正确的工具是高效的——通常也是严格必要的。例如，一个 agent 在网上搜索只存在于 Slack 中的上下文，从一开始就注定失败。有了 [MCP server](https://modelcontextprotocol.io/introduction) 让模型访问外部工具后，这个问题更加复杂——agent 会遇到从未见过的工具，而这些工具的描述质量参差不齐。

我们给 agent 显式的启发式规则：先检查所有可用工具、匹配工具使用与用户意图、用网络搜索做广泛外部探索、优先使用专门工具而非通用工具。糟糕的工具描述会把 agent 引向完全错误的路径，所以每个工具都需要明确的用途和清晰的描述。

### 5. 让 Agent 改进自身

我们发现 Claude 4 模型可以是出色的 prompt 工程师。给定一个 prompt 和一个失败模式，它们能诊断 agent 为何失败并建议改进。我们甚至创建了一个**工具测试 agent**——给定有缺陷的 MCP 工具，它尝试使用工具然后重写工具描述以避免失败。通过数十次测试，这个 agent 发现了关键的细微差别和 bug。这个改进工具人体工学的过程使未来 agent 的任务完成时间**减少了 40%**，因为它们能避免大多数错误。

### 6. 先广后窄

搜索策略应镜像专家人类研究：先探索全景再深入细节。Agent 常默认使用过长、过具体的查询，返回很少结果。我们通过提示 agent 从短而广的查询开始、评估可用内容、然后逐步缩小焦点来对抗这种倾向。

### 7. 引导思考过程

[Extended thinking 模式](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking)让 Claude 输出额外的 token 作为可见的思考过程，可以充当可控的草稿本。主 agent 用 thinking 来规划方法——评估哪些工具适合任务、确定查询复杂度和 sub-agent 数量、定义每个 sub-agent 的角色。我们的测试表明 extended thinking 改善了指令遵循、推理和效率。Sub-agent 也会先规划，然后在工具结果后用 [interleaved thinking](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking#interleaved-thinking) 评估质量、识别空白、精炼下一个查询。这使 sub-agent 在适应任何任务时更加有效。

### 8. 并行工具调用变革速度和性能

复杂研究任务天然涉及探索大量来源。我们早期的 agent 执行顺序搜索，慢得令人痛苦。为了提速，我们引入了两种并行化：(1) 主 agent 并行启动 3-5 个 sub-agent 而非串行；(2) sub-agent 并行使用 3+ 工具。这些改变使复杂查询的研究时间**减少高达 90%**，让 Research 在几分钟内完成原本需要几小时的工作，同时覆盖比其他系统更多的信息。

---

我们的 prompting 策略聚焦于灌输好的启发式规则，而非僵硬的规则。我们研究了熟练的人类如何做研究任务，并将这些策略编码到 prompt 中——比如将困难问题分解为更小的任务、仔细评估来源质量、根据新信息调整搜索方法、以及识别何时该聚焦深度（深入调查一个主题）vs. 广度（并行探索多个主题）。我们还主动设置显式护栏来防止 agent 失控，缓解意外副作用。最后，我们聚焦于快速迭代循环——配合可观测性和测试用例。

## 评估 Multi-Agent 系统

好的评估对构建可靠的 AI 应用至关重要，agent 也不例外。然而，评估 multi-agent 系统面临独特挑战。传统评估通常假设 AI 每次遵循相同步骤：给定输入 X，系统应遵循路径 Y 产出输出 Z。但 multi-agent 系统不是这样工作的——即使起点相同，agent 可能走完全不同的有效路径达到目标。一个 agent 可能搜索三个来源，另一个搜索十个，或者它们可能用不同工具找到相同答案。因为我们并不总是知道"正确步骤"是什么，通常不能只检查 agent 是否遵循了我们预先规定的"正确"步骤。相反，我们需要灵活的评估方法，判断 agent 是否达成了正确结果，同时遵循了合理的过程。

### 立即用小样本开始评估

早期 agent 开发中，变化往往有戏剧性影响，因为有大量唾手可得的改进空间。一个 prompt 调整可能将成功率从 30% 提升到 80%。效果量这么大时，几个测试用例就能发现变化。我们从约 20 个代表真实使用模式的查询开始，测试这些查询通常就能清楚看到变化的影响。我们经常听到 AI 开发团队推迟创建 eval，因为他们认为只有包含数百个测试用例的大规模 eval 才有用。然而，**最好立即用几个例子开始小规模测试，而不是等到能构建更全面的 eval 时再开始**。

### LLM-as-judge 评估可扩展

研究输出难以程序化评估——它们是自由文本，很少有单一正确答案。LLM 天然适合给输出打分。我们使用 LLM judge 按 rubric 评估每个输出，评估维度包括：事实准确性（主张是否与来源匹配？）、引用准确性（引用的来源是否与主张匹配？）、完整性（是否覆盖了所有请求的方面？）、来源质量（是否使用了一手来源而非低质量的二手来源？）、以及工具效率（是否合理次数地使用了正确的工具？）。我们尝试过用多个 judge 评估每个组件，但发现单个 LLM 调用、单个 prompt、输出 0.0-1.0 分数和 pass-fail 评级是最一致的，也最符合人类判断。这种方法在 eval 测试用例确实有明确答案时尤其有效——我们可以用 LLM judge 简单检查答案是否正确（比如：它是否准确列出了研发预算最高的前三家制药公司？）。用 LLM 作为 judge 让我们能可扩展地评估数百个输出。

### 人工评估捕获自动化遗漏的问题

人类测试者能发现 eval 遗漏的边界情况，包括对不寻常查询的幻觉回答、系统故障、或微妙的来源选择偏差。在我们的案例中，人类测试者注意到早期 agent 一致选择 SEO 优化的内容农场，而非权威但排名较低的来源（如学术 PDF 或个人博客）。在 prompt 中添加来源质量启发式规则帮助解决了这个问题。即使在自动化评估的时代，手动测试仍然不可或缺。

### 涌现行为

Multi-agent 系统具有**涌现行为**（emergent behaviors）——无需特定编程就会出现的行为。例如，对主 agent 的小改动可能不可预测地改变 sub-agent 的行为。成功需要理解交互模式，而不仅仅是单个 agent 的行为。因此，这些 agent 的最佳 prompt 不仅仅是严格的指令，而是**协作框架**——定义分工、问题解决方法和努力预算。要做好这一点，需要仔细的 prompting 和工具设计、可靠的启发式规则、可观测性和紧密的反馈循环。参见 [Cookbook 中的开源 prompt](https://platform.claude.com/cookbook/patterns-agents-basic-workflows) 获取我们系统的示例 prompt。

## 生产可靠性与工程挑战

在传统软件中，一个 bug 可能破坏功能、降低性能或导致宕机。在 agentic 系统中，**微小变化级联为大的行为变化**，这使得为必须在长时间运行过程中维护状态的复杂 agent 编写代码极其困难。

### Agent 是有状态的，错误会累积

Agent 可以长时间运行，跨多次工具调用维护状态。这意味着我们需要持久地执行代码并在过程中处理错误。没有有效缓解措施，小的系统故障对 agent 可能是灾难性的。

错误发生时，我们不能从头重启——重启昂贵且令用户沮丧。相反，我们构建了能从错误发生处恢复的系统。我们还利用模型的智能优雅处理问题：例如，**让 agent 知道工具正在失败并让它适应**，效果出奇地好。我们将基于 Claude 的 AI agent 的适应性与确定性保障（如重试逻辑和定期检查点）结合起来。

### 调试需要新方法

Agent 做动态决策，即使 prompt 相同，不同运行之间也是非确定性的。这使调试更难。例如，用户报告 agent"找不到明显信息"，但我们看不到原因——是 agent 使用了糟糕的搜索查询？选择了差的来源？还是遇到了工具故障？

添加完整的生产追踪让我们能诊断 agent 为何失败并系统性修复问题。除了标准可观测性，我们还监控 agent 决策模式和交互结构——同时不监控个别对话内容以维护用户隐私。这种高层可观测性帮助我们诊断根因、发现意外行为、修复常见故障。

### 部署需要仔细协调

Agent 系统是高度有状态的 prompt、工具和执行逻辑网络，几乎持续运行。这意味着每当我们部署更新时，agent 可能在其过程的任何位置。我们需要防止善意的代码变更破坏正在运行的 agent。我们不能同时将所有 agent 更新到新版本。

相反，我们使用 **[rainbow deployments](https://brandon.dimcheff.com/2018/02/rainbow-deploys-with-kubernetes/)**——逐步将流量从旧版本转移到新版本，同时保持两者同时运行，避免中断正在运行的 agent。

### 同步执行创造瓶颈

目前，我们的主 agent 同步执行 sub-agent，等待每组完成后再继续。这简化了协调，但在 agent 之间的信息流中创造了瓶颈。例如：主 agent 无法引导 sub-agent、sub-agent 之间无法协调、整个系统可能因等待单个 sub-agent 完成搜索而阻塞。

异步执行将实现额外并行性：agent 并发工作，在需要时创建新的 sub-agent。但异步性增加了结果协调、状态一致性和跨 sub-agent 错误传播的挑战。随着模型能处理更长更复杂的研究任务，我们预期性能收益将证明复杂性是值得的。

## 结论

构建 AI agent 时，最后一英里往往成为大部分旅程。在开发机器上工作的代码库需要大量工程才能成为可靠的生产系统。Agentic 系统中错误的复合性质意味着，对传统软件来说的小问题可能完全使 agent 脱轨。一个步骤失败可能导致 agent 探索完全不同的轨迹，产生不可预测的结果。基于本文描述的所有原因，原型与生产之间的差距往往比预期更大。

尽管有这些挑战，multi-agent 系统已证明对开放式研究任务有价值。用户表示 Claude 帮助他们发现未考虑过的商业机会、导航复杂的医疗选项、解决棘手的技术 bug、通过发现他们独自不会找到的研究联系节省数天工作。

Multi-agent 研究系统可以在规模化运行中保持可靠——前提是仔细的工程、全面的测试、注重细节的 prompt 和工具设计、稳健的运维实践、以及研究、产品和工程团队之间的紧密协作（这些团队需要对当前 agent 能力有深入理解）。我们已经看到这些系统正在改变人们解决复杂问题的方式。

## 附录：额外技巧

以下是一些关于 multi-agent 系统的额外杂项建议。

### 变更状态的 Agent 的终态评估

评估跨多轮对话修改持久状态的 agent 面临独特挑战。与只读的研究任务不同，每个动作都可能改变后续步骤的环境，创造出传统评估方法难以处理的依赖关系。

我们发现聚焦**终态评估**而非逐轮分析效果更好。不要判断 agent 是否遵循了特定过程，而是评估它是否达成了正确的最终状态。这种方法承认 agent 可能找到通往同一目标的替代路径，同时仍确保它们交付预期结果。对于复杂工作流，将评估拆分为离散的检查点——在这些点上特定的状态变更应该已经发生——而不是试图验证每个中间步骤。

### 长周期对话管理

生产 agent 经常参与跨越数百轮的对话，需要仔细的 context 管理策略。随着对话延伸，标准 context window 变得不够用，需要智能压缩和记忆机制。

我们实现了这样的模式：agent 在进入新任务前总结已完成的工作阶段，并将关键信息存储到外部记忆中。接近 context 限制时，agent 可以生成带干净 context 的新 sub-agent，同时通过仔细交接维护连续性。此外，它们可以从记忆中检索存储的 context（如研究计划），而不是在达到 context 限制时丢失之前的工作。这种分布式方法防止了 context 溢出，同时在扩展交互中保持对话连贯性。

### Sub-agent 输出到文件系统以最小化"传话游戏"

Sub-agent 的直接输出可以绕过主协调者处理某些类型的结果，同时提升保真度和性能。不要求 sub-agent 通过主 agent 传达所有内容，而是实现 artifact 系统——专门化 agent 可以创建独立持久的输出。Sub-agent 调用工具将工作存储在外部系统中，然后传回轻量级引用给协调者。

这防止了多阶段处理中的信息丢失，减少了通过对话历史复制大输出的 token 开销。这个模式对结构化输出（如代码、报告或数据可视化）特别有效——在这些场景中，sub-agent 的专门化 prompt 产生的结果比通过通用协调者过滤更好。
