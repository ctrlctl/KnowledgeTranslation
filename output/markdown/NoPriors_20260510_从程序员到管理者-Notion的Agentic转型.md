## 开场：Notion 的 AI 起源故事 [00:00]

欢迎回到 NoPriors。今天我跟 Notion 联合创始人 Simon Last 在一起。我们聊了他们在 AI 时代对 Notion 的新愿景——作为人类和 agent 协作的平台，Notion 的工程和产品组织如何变化，以及这些新的思维工具。

Notion 已经有规模了，很棒的平台，很多用户。你们确实很早就开始了。我觉得 Notion 是真正积极拥抱 AI 的公司之一。我听说你第一次接触 GPT-4 是在墨西哥的公司 offsite？

对，那是 2022 年。我一直在关注发生的事情，对技术超级好奇。直到我玩了 GPT-4，它才变得真正真实。当我们获得访问权时，它是一种原型 ChatGPT 式的界面。我和联合创始人 Ivan 都获得了访问权，立刻清楚了两件大事：

一是它相当聪明——能遵循相当复杂的指令，能为你写东西、编辑东西。二是它的知识范围极其有趣——超级深入和广泛的世界知识。

我们玩了之后，对我们俩来说立刻清楚了：好，现在是开始的时候了，但要思考如何应用它，它只会变得更好。

## 短期与长期愿景 [01:57]

你们是从一个特定愿景开始的，还是开始实验？

我们立刻有了长期和短期愿景。短期的立刻明显的是：它可以是一个**写作助手**。在你的文档中，你可以选择一些文本，重写它，让它为你写文本，也许查找一些东西然后给你来源或更多信息。我们立刻开始做这个，组了一个 Tiger team，两三个月后就发布了。

长期愿景是：看起来可能实现的是一个**通用助手**。如果你能给它 Notion 内人类拥有的所有工具——能创建自己的数据库、查询、操作它们、创建文档、编辑它们——把所有这些编织在一起做更长程的任务。

短期的我们很快就发了，长期的还不能工作，花了更长时间。

## 产品演进：从 AI Writer 到全索引 Q&A [03:05]

第一个 AI 特定的 Notion 功能是什么时候发布的？2023 年 2 月。

给你一个时间线。第一个是我们的写作系统——AI Writer。最容易做因为是单步任务，重写、编辑文本。没有检索方面，就是原始访问模型来写文本。

下一个大事是 **Q&A**——对整个工作空间做语义索引，然后让你问问题，给你基于来源的答案。这也是立刻明显会超级有用的。我们 2023 年 10 月 GA。那是一个大得多的工程——不只是接入 LLM，而是做实时更新索引。我们必须在 eval 和质量上更认真。

Q&A 是一个多年旅程。一旦 Notion 索引工作了，明显应该索引其他一切。所以我们索引了 Slack 和 Google Drive，现在定期发布新的。现在我们有一个相当完整的索引。

有人可能会说这些是那些产品本身还没完美解决的非常困难的问题。你怎么想的？

确实如此。我们经常讨论这个——我们甚至有什么权利做这个？但事实证明大多数公司在做索引方面相当差。这让我们有点困惑。

我的看法是：需要一点 AI-pilled 的精明，然后大部分是工艺和注意力。特别是索引检索这些东西，要真正让它工作，你必须相当经验性和迭代性——实际尝试查询。每个数据源都有点特殊。你不能对查询 Slack vs 查询 Google Drive 用一刀切的方法。它们是完全不同种类的信息。需要一点工艺和爱——实际尝试一堆不同查询，每天实际使用它，不断迭代和重新思考检索如何工作。

你怎么想人们组织工作空间的多样性？即使 Notion 的使用也不是同质的。
## 索引与检索的工艺 [06:23]

有趣的是，有了 embeddings，组织方式几乎不那么重要了。AI 不关心树结构是什么。AI 关心的只是有一段文本包含你需要的上下文，然后它能检索到。所以我们现在建议人们：不要太担心组织。找到方法把所有东西导入扔进去就行。

你仍然会做可能大幅改变性能的决策，比如分块策略。那超级重要。但那对用户是透明的，独立于他们特定的组织方法。

Ivan 说我应该问你重建了多少次 Notion 和你们的 harness。

这几乎是一个笑话了。我们大概每六个月重写一次 AI harness，重写时间一直在缩短因为进展在加速。我觉得这真的是一个关键点——很多公司做错的就是做一件事然后就坚持它。你真的必须敏锐地意识到模型和技术的当前状态，然后围绕它深度设计 harness、系统和产品。这基本上意味着你**每六个月必须重写一次**。

我觉得挺有趣的。这是过程的一部分。你可以重新开始和重新思考。我们即将在下一两周发布新版本的 harness，同时已经在想之后的那个了。

## Coding Agent 如何改变工程组织 [08:12]

这引出了一组问题：Notion 作为工程、产品和研究组织现在怎么工作——既然你们有了 coding agent 的力量？因为我想象你重写 harness 的意愿会大幅上升——agent 会帮我做。

非常对。用 coding agent 真的很有趣。我甚至考虑构建什么的野心都大幅上升了。

你觉得过去两三年中，你对 Notion 的工程和产品应该如何工作的想法最戏剧性地改变了什么？

在 coding agent 方面，我们经历了多个时代。有 tab 自动补全时代，然后是插入、重写一些代码。但直到 agent 开始工作——我会说去年初——我们才开始采用 agent。我大约去年四月开始用 Claude Code。那是一个巨大的解锁。

大的转变是：你真的可以推动让这些 agent 端到端地实现、验证和维护东西。但这需要在架构和验证循环方面相当深入的思考。好处是如果你做得好，你可以对你在构建的东西更有野心，也让它比人类写的更健壮。反面是如果你做得差，全是垃圾。

## 团队规模与 10x 工程师的差距 [09:49]

这改变了你对 Notion 团队应该是什么样的看法吗？大小、资历？

根本效应是每个人的个人产出影响可以高得多，你的产出越来越取决于你使用工具的能力和意愿。

我不觉得我们看到对团队规模有太大影响。我们喜欢用小的 Tiger team。如果你能让团队小，几乎总是更好。这之前就是对的，现在仍然是对的。

你觉得中位数工程师和 10x 工程师（或 10x 更愿意使用工具的工程师）之间会发生不同的事情吗？

差距更大了。你现在可以是 **100x 或 1000x 工程师**如果你正确使用工具。最低标准没变，但最高标准极大地提高了。

一个内部影响是：广泛来说，事情感觉更混乱了。但我有点喜欢那样。有更多原型。比如我们的设计团队做了一整个 git repo，他们叫它"设计游乐场"——本质上是一个简化的 Notion 加上一堆 UI 原语。他们做得很精致，里面有一个 agent。所有设计师都能快速搭建超高保真原型。不再是指着一个 mock 说"这会是什么样"——他们给你一个已部署的 URL。

这在整个栈上下都是如此。更混乱，更多事情在发生。**所有 PR 都更有野心了。**

你在某处画线吗——比如更危险或敏感的东西，可能有数据丢失风险？

我们仍然对所有 PR 做 review。所有 PR 现在都是 agent 写的。它们通常更大更复杂——这是最差的部分。但更好的部分是它们通常测试得更好，我们可以要求更好的测试。我再也不会产出一个没有被完全 intent 测试的 PR。

但这要求你不只是 vibe coding。你要仔细思考你在做什么改变、怎么验证、怎么安全部署，然后让 agent 帮你完成那个过程。

## Notion Agent：从个人助手到自定义 Agent [12:50]

你说通用助手还不完全存在。你想象 Notion 的 agent 在未来一两年能做什么？

我们挣扎了几年来构建 agent。它总是有点工作但不太有用。主要是太早了。我们尝试构建 agent 三四次。然后去年秋天终于发布了——去年八九月。

现在 Notion AI 是完整的 agent，可以访问 Notion 中几乎所有东西。原始愿景的很多现在完全工作了。每个 Notion 用户都有一个 agent。它可以访问用户能访问的所有东西——创建数据库、更新东西、创建文档、搜索、搜索网络、做研究。

第二个大事是我们上周刚发布的**自定义 agent**。你可以创建一个新的自定义 agent，给它一个名字。跟个人 agent 不同，默认它没有访问任何东西。你必须授权。但一旦你授权了，它可以在后台自主运行。

比如你可以给它访问自己的数据库来归档任务，然后把它附加到一个 Slack 频道，它就会开始在 Slack 上回复人并归档任务。另一个用例是给它访问周报数据库，让它搜索网络或你的工作空间。

自定义 agent 代表某些你想自主完成的工作或任务。我真正兴奋的是：我们想让它极其擅长**从初始内核引导自己的能力**——基本上引导自己做任何事。甚至比如构建一个我们还不支持的集成，部署它，然后使用它。

所以你想象 Notion agent 是更广义的 agent 定义——写代码是它能访问的工具之一？

对，我觉得这很关键。我把 **coding agent 看作 AGI 的内核**。AGI 将是一个 coding agent。代码是表示确定性逻辑的一个非常有用的原语。把它应用到知识工作 agent 上真正令人兴奋的是：它可以引导一种能力。
## Notion 在 AI 格局中的定位 [15:30]

Notion 在规模上运营，但在一个有更大规模的生产力和平台玩家的格局中。很多这些会有自己的 agent。实验室、微软世界的人都在尝试集成其他数据源。你怎么看这会怎么发展？

如果你看格局——有实验室，有软件平台，有基础设施。在实验室方面，我们把自己看作**模型的瑞士**。我们的客户不想被锁定在某个实验室的模型上。它们总在发布新版本，任何给定月份一个比另一个好。所以我们想成为一个你可以随时轻松获取所有最好模型、轻松切换的地方。

开源也参与其中吗？绝对的。开源模型真的越来越好了。现在有四个不同的中国模型很好。我们上周刚在 agent 中发布了其中一个，肯定会做全部四个。它们相当好而且比前沿模型便宜得多。

我们的角色是：取所有最好的模型，创建真正高质量的 SOTA agent 实现，让人们方便地获取，然后做一个对人类和 agent 协调都很好的协作工作空间。

## 为 Agent 重新设计 API [17:34]

你怎么想 Notion 的结构——blocks 和 databases——对 agent 有用还是不有用？

都仍然非常有用。挑战是让它对 agent 真正方便。过去它对人类方便，然后我们也让 API 对写代码的人类方便。现在我们本质上有了一个**新客户——agent**。

一开始这确实是个问题。比如我们的 API 用这种疯狂的 JSON 格式表示 blocks，默认超级冗长，对 agent 来说很糟糕。但我们接受了这个挑战，为 agent 设计了真正方便的 API。

我们创建了一种 **markdown 方言**——看起来像默认的普通 markdown，但用所有 Notion blocks 增强了。模型非常擅长它，工作得很好。这是它读写页面的方式。对于数据库，我们用 **SQLite**——基本上就是说 SQLite，也工作得很好。

默认的东西不太好用。但我们把它当作工程挑战来解决。现在我们有极其方便的 API，agent 自然就很擅长。

怎么理解或弄清楚什么会让 API 对 agent 更好？很经验性的——玩一玩，注意到"哦，它不太擅长那个"、"哦，那太多 token 了，怎么让它更小"。然后一点第一性原理思考——模型被训练在什么上？它们的先验中有什么？它们自然会擅长什么？Agent 循环怎么工作？访问这些东西的方便高效模式是什么？

我听到的是用户研究，但用户实际上是 agent，然后持续 eval。对，你就跟它聊。用户随时在那里准备跟你说话。你有无限访问权。

## Simon 的日常 Agent 工作流 [20:12]

你现在在跑什么？告诉我你的设置。

我在做一个新原型。有几个 agent 在做那个。我的设置这些天就是 Claude Code 或 Codex。我喜欢 CLI 工具——超级简单而且工作得很好。

我的整个目标这些天本质上就是**尽可能多地同时运行，一直运行**。比如每天晚上睡觉前我说"好，走吧伙计们"。基本上我要做的是确保我给了它足够多的东西，到我早上醒来时它还没做完。那就是胜利。

我的个人记录是一个 coding agent 连续运行了 **13 天**不停，就是在处理任务。

我承认这周至少多次半夜醒来就是"你还在跑吗？"对，有点紧张。我总是睡前最后检查一次确保它还在转。

Notion agent 方面呢？你有核心日常工作流吗？

我一直用我们的个人 agent。它有关于我们公司和所有正在发生的事情的所有上下文。比如昨晚我在问它自定义 agent 发布进展如何、我们得到什么信号——超级有用。

我有很多自定义 agent 在运行。我个人最喜欢的是一个**邮件分类 agent**——它可以访问我所有工作和个人邮件，每天醒来把我不需要看的东西全部归档。我随时间训练它学习我的偏好。

你实际上为它标注数据吗？其实很容易做。你创建 agent，给它访问你的邮件，然后你可以做一个空白页面作为它的记忆，让它编辑那个页面。然后你说"好，现在去看我的邮件然后采访我。问我哪些东西……"它会提议它认为应该归档的东西，你可以纠正它。然后它会用那个生成一个关于什么是对什么是错的规则列表。

前几天我在纠正它。几周后我完全放弃了审批，它现在自动归档所有我不需要看的东西。
## 自定义 Agent 的记忆模式与内部推广 [23:01]

邮件 agent 完全解决了我的邮件问题。我工作上不怎么用邮件——大部分在 Slack。95% 的个人和工作邮件我根本不需要看。所以它完全解决了这个问题。现在我的收件箱里只有我需要看的东西。

我还有另一个 agent 分类所有内部反馈和 bug。我们有一个 Slack 频道，人们就在里面随便发产品反馈和 bug。过去有时候会被回复，有时候就被随意忽略了。它的全部工作就是把它路由到正确的地方。它用类似的记忆模式——在运行中学习应该把 bug 归档到哪里。随时间它建立了数百条规则。比如有一个关于移动 app 的 bug，它知道路由到移动团队然后在他们的数据库中归档任务。

你看那个生成和更新的记忆吗？因为它对你是可读的。我一开始看了。但一旦你信任它在工作，你就忽略它了。如果它坏了我会去修。它偶尔会坏。

一般模式是：作为原型构建，在审批模式下密切观察，运行一堆次后你信任它在工作。

## 让非技术团队构建 Agent [24:54]

你们内部做什么来确保非技术团队有构建 agent 的直觉？

我们相当频繁地做 workshop 和 hackathon。比如一个月前我跟 People 团队做了一个 hackathon。People 团队很棒——他们实际上是自定义 agent 的最高采用者之一。他们做所有那些 Slack 和 Notion 之间的手动工作流。

人们超级兴奋去尝试，也许只需要一点直觉上的推动和帮他们开始。但然后我真的很impressed。概念其实挺直觉的——一旦你过了"什么是 prompt、什么是 agent、它怎么被触发和唤醒"的技术障碍。过了那个之后，它实际上是一个非常人性化的界面。

也许最大的障碍实际上只是让人们去尝试并假设它会工作。

## Tools for Thought 的演变：从程序员到管理者 [26:06]

你和 Ivan 最初在互联网 tools for thought 社区认识。我们用来思考的工具现在非常不同了。你对 Notion 的核心概念在过去几年因为 AI 改变了吗？

变了很多。广泛来说，AI 之前，我们的目标是创建人类直接执行工作的最好工具。现在目标是创建**人类管理 agent 为他们做工作的最好工具**。

这是一个很大的转变。相当根本。但事实证明你需要大部分相同的原语。我们构建的所有原语实际上仍然极其有用。只是我们需要一些新原语——比如表示什么是 agent、它如何跟你的页面和数据库交互。

但你仍然需要文档——一种非结构化的写东西的方式。Agent 喜欢写 markdown 文档。你仍然需要数据库——仍然需要结构化数据。如果你在跟 100 个后台 coding agent 的 swarm 工作，你不想有 100 个聊天线程。你想要一个看板。跟以前一样。你仍然需要协调结构。

---

## 从写代码到管理 Agent [27:35]

有什么是你个人在过去六个月中构建方式真正改变的？

完全改变了。我从去年夏天起就没写过代码了。我不再打字写代码了。

我们从人类打所有代码 → 还在打但 tab 补全 → 跟 agent 说话它做小任务但我们还在外循环 → 现在我设计一个端到端任务（包括做某个改变然后验证它），我只是最外层的验证者——最后双重检查它是否正确，如果它跑偏了就监控它。

这是一个完全的转变。我现在是 **agent 管理者而不是程序员**。

---

好的，谢谢 Simon。这是一个关于我们如何都将成为 agent 管理者的超棒讨论——希望是在 Notion 中。
