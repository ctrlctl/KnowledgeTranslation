过去一个月，我们一直在调查用户报告的 Claude 回复质量下降问题。我们将这些报告追溯到三个分别影响 Claude Code、Claude Agent SDK 和 Claude Cowork 的独立变更。API 未受影响。截至 4 月 20 日（v2.1.116），三个问题均已解决。

我们非常重视关于质量下降的报告。我们从不故意降低模型质量，并且能够立即确认 API 和推理层未受影响。经过调查，我们识别出三个不同的问题：

· · ·

三个问题概述

1. 3 月 4 日：我们将 Claude Code 的默认推理努力从 high 改为 medium，以减少部分用户在 high 模式下看到的极长延迟。这是错误的权衡。4 月 7 日在用户反馈后回退。影响 Sonnet 4.6 和 Opus 4.6。

2. 3 月 26 日：我们发布了一个变更，清除空闲超过一小时的 session 中 Claude 的旧 thinking，以减少用户恢复这些 session 时的延迟。一个 bug 导致这在 session 的剩余时间里每个 turn 都持续发生，而不是只发生一次，使 Claude 看起来健忘和重复。4 月 10 日修复。影响 Sonnet 4.6 和 Opus 4.6。

3. 4 月 16 日：我们添加了一个系统 prompt 指令来减少冗长。与其他 prompt 变更结合后，它损害了编码质量，4 月 20 日回退。影响 Sonnet 4.6、Opus 4.6 和 Opus 4.7。

因为每个变更在不同时间表上影响不同的流量切片，聚合效果看起来像广泛的、不一致的质量下降。

· · ·

问题一：推理努力级别默认值变更

当我们在 2 月发布 Opus 4.6 时，将默认推理努力设为 high。很快收到反馈说 Opus 4.6 在 high 模式下偶尔会思考太久，导致 UI 看起来冻结，并对这些用户造成不成比例的延迟和 token 使用。

一般来说，模型思考越久，输出越好。Effort level 是 Claude Code 让用户设置这个权衡的方式。在我们的内部 eval 和测试中，medium effort 以显著更少的延迟实现了略低的智能。因此我们推出了将 medium 设为默认的变更。

推出后不久，用户开始报告 Claude Code 感觉不那么聪明了。我们做了多次设计迭代让当前 effort 设置更清晰，但大多数用户保留了 medium 默认值。在听到更多客户反馈后，我们在 4 月 7 日逆转了这个决定。所有用户现在默认 Opus 4.7 使用 xhigh effort，其他模型使用 high effort。

· · ·

问题二：Thinking 历史清除 Bug

当 Claude 推理一个任务时，推理通常保留在对话历史中，这样在每个后续 turn，Claude 都能看到它为什么做了那些编辑和 tool call。3 月 26 日，我们发布了一个旨在提高效率的改进。

设计应该很简单：如果 session 空闲超过一小时，我们可以通过清除旧的 thinking 部分来降低用户恢复 session 的成本。我们使用 clear_thinking_20251015 API header 配合 keep:1。

实现有一个 bug。 它不是清除一次 thinking 历史，而是在 session 的剩余时间里每个 turn 都清除。session 一旦跨过空闲阈值，该进程剩余的每个请求都告诉 API 只保留最近的推理块并丢弃之前的所有内容。这会累积：如果你在 Claude 正在使用工具时发送后续消息，那会在损坏的标志下开始新 turn，所以即使当前 turn 的推理也被丢弃。

Claude 会继续执行，但越来越不记得为什么选择做它正在做的事情。这表现为用户报告的健忘、重复和奇怪的工具选择。因为这会持续从后续请求中丢弃 thinking 块，这些请求也导致缓存未命中。我们相信这就是驱动用量限制消耗比预期更快的单独报告的原因。

两个不相关的实验使我们最初难以复现问题。这个 bug 处于 Claude Code 的上下文管理、Anthropic API 和 extended thinking 的交叉点。它引入的变更通过了多次人工和自动化代码审查、单元测试、端到端测试、自动化验证和 dogfooding。结合这只在边缘情况（过期 session）中发生以及复现困难，我们花了超过一周才发现并确认根本原因。

作为调查的一部分，我们用 Opus 4.7 对有问题的 PR 进行了回测代码审查。当提供了收集完整上下文所需的代码仓库时，Opus 4.7 找到了 bug，而 Opus 4.6 没有。

· · ·

问题三：系统 Prompt 中的简洁性指令

我们最新的模型 Claude Opus 4.7 相对于前代有一个显著的行为特点：它倾向于相当冗长。这使它在难题上更聪明，但也产生更多输出 token。

在 Opus 4.7 发布前几周，我们开始调优 Claude Code 做准备。我们有多种工具来减少冗长：模型训练、prompting 和改进产品中的 thinking UX。最终我们全部使用了，但系统 prompt 中的一个添加对 Claude Code 中的智能造成了过大影响：

"Length limits: keep text between tool calls to ≤25 words. Keep final responses to ≤100 words unless the task requires more detail."

经过多周内部测试且在我们运行的评估集中没有回退后，我们有信心地在 4 月 16 日随 Opus 4.7 一起发布了这个变更。作为调查的一部分，我们使用更广泛的评估集运行了更多消融实验。其中一个评估显示 Opus 4.6 和 4.7 都有 3% 的下降。我们立即在 4 月 20 日的发布中回退了 prompt。

· · ·

后续改进措施

我们将做几件不同的事情来避免这些问题：

  • 确保更大比例的内部员工使用与公开版完全相同的 Claude Code 构建（而非我们用来测试新功能的版本）
  • 改进我们内部使用的 Code Review 工具，并将改进版本发布给客户
  • 对系统 prompt 变更添加更严格的控制：对 Claude Code 的每次系统 prompt 变更运行广泛的逐模型 eval suite，继续消融实验以理解每行的影响
  • 对任何可能与智能权衡的变更，添加浸泡期、更广泛的 eval suite 和渐进式发布
  • 我们最近在 X 上创建了 @ClaudeDevs，给我们空间深入解释产品决策及其背后的推理

最后，我们要感谢用户：使用 /feedback 命令分享问题的人（或在网上发布具体、可复现示例的人）最终让我们能够识别和修复这些问题。今天我们为所有订阅者重置了用量限制。
