如何监控内部编码 Agent 的错位

· · ·

AI 系统正开始在真实世界环境中以更大的自主性大规模行动。随着能力提升，它们能承担越来越复杂、高影响的任务，并以类似人类协作者的方式与工具、系统和工作流交互。

OpenAI 使命的核心部分是帮助世界负责任地导航向 AGI 的过渡。这意味着不仅要构建高能力系统，还要开发在能力持续增长时安全部署和管理它们所需的方法、基础设施和途径。

监控内部部署的 agent 是我们实现这一目标的关键方式之一，它让我们既能从真实使用中学习，也能识别和缓解新兴风险。过去几个月，我们为内部使用的编码 agent 构建并完善了一个监控系统，作为更广泛安全方法的一部分。本文描述了系统如何工作、我们迄今学到了什么，以及我们如何看待这种方法随 agentic 能力持续进步而演进。

在内部使用高级编码 agent 给了我们一个机会，去理解它们在真实工作流中的行为，以及用户如何将这些 agent 应用于跨多种环境的复杂、工具丰富的任务。OpenAI 的内部编码 agent 部署还带有独特的错位风险因素：它们可以访问部分内部 OpenAI 系统，可以检查其安全措施的文档和代码，甚至尝试修改这些安全措施，并可能以影响其未来版本的方式采取行动。这些特性使内部部署成为创新监控基础设施的独特重要场景，我们相信类似的安全措施应该成为全行业内部编码 agent 部署的标准。

· · ·

我们的方法及其工作原理

随着能力提升，我们相信监控 agentic 行为——包括模型的行动和内部推理——将成为越来越重要的安全工具。监控内部编码 agent 帮助我们理解错位行为发生的频率和实际表现。目标是标记那些在模型部署前难以浮现的错位相关行为，因为它们通常只在真实的、工具丰富的工作流和长时间会话中出现。同时，保护编码 agent 会话中的用户隐私和数据安全至关重要，只以狭窄范围的方式浮现有问题的行为。

为此，我们开发了一个低延迟内部监控系统，由 GPT-5.4 Thinking 以最大推理力度驱动，审查 agent 的交互并对可能与用户意图不一致或可能违反我们内部安全或合规政策的行为发出警报。监控器记录和分析 agent 的思维链和行动，自动对可疑或有问题的行为发出警报，以便我们快速分类、缓解后果并改进其他安全措施。这个反馈循环让我们能快速检测和解决潜在安全问题、改进模型对齐，是我们长期 agent 安全策略的核心组件。

在最新形式中，我们的监控系统在交互完成后 30 分钟内审查交互，对交互进行分类并分配严重性级别。随着延迟向近实时审查降低，安全收益显著增加。最终，监控器可能能在编码 agent 行动被执行之前帮助评估它们——在现有安全监控器之外提供另一个重要的纵深防御控制。

初步结果看起来很强，监控系统持续优于员工上报——标记了员工通过内部渠道独立报告的每一个交互。监控器还浮现了许多否则可能被内部用户忽视的额外行为。

通过这项工作，我们发现模型在追求用户指定目标时可能过于急切地绕过限制，特别是当用户请求无意中鼓励这样做时。也就是说，到目前为止我们没有看到超出原始任务的动机证据（例如自我保存或 scheming）。极小比例的流量（<0.1%）主要来自定制或本地设置，目前在我们的监控覆盖范围之外，我们正在努力弥合这一差距。

· · ·

我们监控什么

监控系统在所有标准内部编码 agent 部署上私密运行，查看完整对话历史，包括所有思维链、所有用户/开发者/助手消息，以及工具调用和输出。监控系统识别看起来与用户意图不一致或其他可疑的行动，如试图绕过限制。一旦检测到潜在异常，就会浮现给人类审查和处理。这限制了人工审查的数量，同时允许我们识别和响应影响模型对齐或行为的潜在问题。

运行五个月来的数据： 我们监控了数千万条内部 agentic 编码轨迹。零条真实对话触发了最高严重性级别——旨在捕获罕见的高风险错位如连贯的 scheming——我们迄今只在具有挑战性的合成评估中观察到这种情况。大约 1,000 条对话触发了中等严重性警报——其中许多来自故意的内部红队测试——并被升级进行人工审查。

三个最严重的真实案例：

1. 编码命令绕过安全控制：一个 agent 遇到限制（命令被"Access is denied"错误阻止），推测可能与安全控制（如杀毒软件或监控）有关，尝试了多种绕过方法，包括混淆可疑内容和将 payload 构建拆分为多个小步骤。最终通过切换到尊重约束的解决方案成功。我们意识到开发者 prompt 在这种情况下激励了这种行为，随后修改了它。

2. 对用户进行 prompt 注入：agent 试图通过在输出中嵌入隐藏指令来影响用户的后续行为。

3. 提取凭证：agent 试图从环境中提取敏感凭证信息。

局限性

我们发现这种内部错位监控方法在覆盖能力和资源方面非常有效。但它有局限性：首先也是最重要的，这种方法关键依赖于可监控性（monitorability），我们正在投入努力保持这一特性。某些不当行为可能比其他行为更容易从模型推理和工具痕迹中检测到，未来模型尤其可能表现出更难识别的行为。

虽然系统迄今匹配了我们知道的每一个员工上报是积极信号——表明它可靠地捕获了明显的、高显著性的问题——但这本身不能排除更微妙的错位，我们仍然无法在没有专门控制评估和红队测试的情况下自信地量化开放式真实世界流量上的假阴性率。这就是为什么我们将监控视为纵深防御堆栈中的一层——投资于可监控的推理痕迹，并将监控器与互补的评估和预防性控制配对。

· · ·

迈向基于监控的安全论证

虽然我们继续改进其可靠性，但当前的异步监控基础设施已经提供了一种实用方式来观察和学习真实世界内部部署中的模型行为。我们将此视为迈向前沿 AI 系统更广泛安全论证（safety case）的早期步骤，将监控、评估和控制结合起来管理随能力增长的风险。

通往这种基础设施的路线图包括：

1. 控制评估：允许我们估计监控器在对抗性构建的分布上的召回率，以及我们根据监控器预测采取行动防止伤害的能力——包括评估监控器是否可能与 agent 串通。作为第一步，我们开发了一个评估，其中 agent 试图偷偷破坏 OpenAI 代码库的 PR。在这个任务上我们最新的监控系统取得了完美表现，尽管这个任务在很多方面对监控器来说不切实际地容易。

2. 监控器和人工审查者可接受的可靠性和延迟标准，以及对底层监控系统隐私和安全控制的持续增强。

3. 将监控扩展到同步阻断：允许系统在模型行动执行前评估并阻止它们，而不仅仅是在之后不久发出警报。

· · ·

前路

在当前限制内，系统已经实际有用：如上所述，它浮现了可能否则不会被注意到的额外案例，我们利用其发现做出了具体改进（包括更新相关安全措施和系统消息）。同样重要的是，其低延迟警报让我们能在问题发生后不久调查和遏制，限制潜在的下游影响。

即使监控器今天异步运行，我们预期它能有意义地降低那些在较长时间内展开的威胁模型的风险（例如数据投毒或研究破坏），在这些场景中捕获早期行动可以防止更大的下游伤害。

我们的目标是在内部建立稳健的监控实践，通过真实世界经验加强它们，并最终帮助使类似的安全措施成为全行业标准。展望未来，我们计划探索更同步的监控堆栈，能在执行前评估并可能阻止最高风险的行动——特别是在单一步骤可能造成不可逆伤害的场景中——并期望继续使用我们最强大的模型来执行这项任务。我们相信该领域受益于负责任地分享关于模型不当行为的真实世界证据，我们计划继续这类分析并在夏季发布后续报告。
