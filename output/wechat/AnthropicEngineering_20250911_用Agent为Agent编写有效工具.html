· · ·

Model Context Protocol（MCP）可以赋予 LLM agent 数百种工具来解决真实世界的任务。但我们如何让这些工具发挥最大效果？在这篇文章中，我们描述了在各种 agentic AI 系统中提升性能的最有效技术¹。

我们首先介绍如何：

  • 构建和测试工具原型
  • 创建和运行工具与 agent 的综合评估
  • 与 Claude Code 等 agent 协作，自动提升工具性能

然后总结我们在过程中发现的编写高质量工具的关键原则：

  • 选择正确的工具来实现（以及不实现）
  • 用命名空间定义功能的清晰边界
  • 从工具返回有意义的上下文给 agent
  • 优化工具响应的 token 效率
  • 对工具描述和规范进行 prompt engineering

构建评估让你能系统地衡量工具的性能。你可以使用 Claude Code 来自动优化工具以提升评估表现。

· · ·

什么是工具？

在计算中，确定性系统在相同输入下每次都产生相同输出，而非确定性系统——如 agent——即使在相同起始条件下也可能生成不同的响应。当我们传统地编写软件时，我们是在确定性系统之间建立契约。例如，getWeather("NYC") 这样的函数调用每次都会以完全相同的方式获取纽约市的天气。

工具是一种新型软件，它反映的是确定性系统与非确定性 agent 之间的契约。 当用户问"今天需要带伞吗？"时，agent 可能调用天气工具、从通用知识中回答，甚至先问一个关于位置的澄清问题。偶尔，agent 可能会产生幻觉，甚至无法理解如何使用工具。

这意味着我们在为 agent 编写软件时需要从根本上重新思考方法：不是像为其他开发者或系统编写函数和 API 那样编写工具和 MCP 服务器，而是需要为 agent 设计它们。我们的目标是扩大 agent 能有效解决各种任务的范围——通过使用工具来追求多种成功策略。

幸运的是，根据我们的经验，对 agent 最"符合人体工学"的工具，对人类来说也出奇地直观易懂。

· · ·

如何编写工具

本节描述如何与 agent 协作来编写和改进你给它们的工具。先快速搭建工具原型并在本地测试。然后运行综合评估来衡量后续变更。与 agent 并肩工作，你可以重复评估和改进工具的过程，直到 agent 在真实世界任务上达到强劲表现。

· · ·

构建原型

不亲自动手很难预判哪些工具 agent 会觉得好用、哪些不会。先快速搭建工具原型。如果你用 Claude Code 来编写工具（可能一次性完成），给 Claude 提供工具将依赖的软件库、API 或 SDK（包括 MCP SDK）的文档会很有帮助。LLM 友好的文档通常可以在官方文档站点的扁平 llms.txt 文件中找到（这是我们 API 的）。

将工具包装在本地 MCP 服务器或桌面扩展（DXT）中，可以让你在 Claude Code 或 Claude Desktop 应用中连接和测试工具。要将本地 MCP 服务器连接到 Claude Code，运行 claude mcp add <name> <command> [args...]。要连接到 Claude Desktop 应用，分别导航到 Settings > Developer 或 Settings > Extensions。工具也可以直接传入 Anthropic API 调用进行程序化测试。

自己测试工具以发现粗糙之处。收集用户反馈，建立对你期望工具支持的用例和 prompt 的直觉。

· · ·

运行评估

接下来，你需要通过运行评估来衡量 Claude 使用工具的效果。从生成大量基于真实世界用途的评估任务开始。我们建议与 agent 协作来帮助分析结果并确定如何改进工具。在我们的工具评估 cookbook 中可以看到这个端到端流程。

图：我们内部 Slack 工具的留出测试集表现

生成评估任务

有了早期原型，Claude Code 可以快速探索你的工具并创建数十个 prompt-response 对。Prompt 应该受真实世界用途启发，基于真实的数据源和服务（例如内部知识库和微服务）。我们建议避免过于简单或肤浅的"沙箱"环境——它们无法用足够的复杂度来压力测试你的工具。

强评估任务可能需要多次工具调用——可能数十次。以下是一些强任务示例：

  • "安排下周与 Jane 开会讨论我们最新的 Acme Corp 项目。附上上次项目规划会议的笔记并预订会议室。"
  • "客户 ID 9182 报告他们在一次购买尝试中被收费三次。找到所有相关日志条目，确定是否有其他客户受到同一问题影响。"
  • "客户 Sarah Chen 刚提交了取消请求。准备一个留存方案。确定：(1) 她为什么要离开，(2) 什么留存方案最有说服力，(3) 在提出方案前我们应注意的风险因素。"

以下是一些较弱的任务：

  • "安排下周与 jane@acme.corp 的会议。"
  • "在支付日志中搜索 purchase_complete 和 customer_id=9182。"
  • "找到客户 ID 45892 的取消请求。"

每个评估 prompt 应配对一个可验证的响应或结果。验证器可以简单到精确字符串比较，也可以复杂到让 Claude 来判断响应。避免过于严格的验证器——它们可能因格式、标点或有效的替代表述等无关差异而拒绝正确响应。

对于每个 prompt-response 对，你还可以选择性地指定你期望 agent 在解决任务时调用的工具，以衡量 agent 是否成功理解了每个工具的用途。但因为可能存在多条有效路径来正确解决任务，尽量避免过度指定或过拟合到特定策略。

运行评估

我们建议用直接的 LLM API 调用以程序化方式运行评估。使用简单的 agentic 循环（交替 LLM API 和工具调用的 while 循环）：每个评估任务一个循环。每个评估 agent 应被给予单个任务 prompt 和你的工具。

在评估 agent 的 system prompt 中，我们建议指示 agent 不仅输出结构化响应块（用于验证），还输出推理和反馈块。指示 agent 在工具调用和响应块之前输出这些内容，可能通过触发 chain-of-thought（CoT）行为来提升 LLM 的有效智能。如果你用 Claude 运行评估，可以开启 interleaved thinking 获得类似的开箱即用功能。

这将帮助你探究 agent 为什么调用或不调用某些工具，并突出工具描述和规范中的具体改进领域。

除了顶层准确率，我们建议收集其他指标：单个工具调用和任务的总运行时间、工具调用总数、总 token 消耗和工具错误。跟踪工具调用可以揭示 agent 追求的常见工作流，并提供工具整合的机会。

分析结果

Agent 是你发现问题和提供反馈的有力伙伴——从矛盾的工具描述到低效的工具实现和令人困惑的工具 schema。然而，请记住 agent 在反馈和响应中省略的内容往往比它们包含的更重要。LLM 并不总是说出它们的意思。

观察你的 agent 在哪里卡住或困惑。通读评估 agent 的推理和反馈（或 CoT）来识别粗糙之处。审查原始 transcript（包括工具调用和工具响应）以捕捉 agent CoT 中未明确描述的行为。读出言外之意；记住你的评估 agent 不一定知道正确答案和策略。

分析工具调用指标。大量冗余工具调用可能表明需要调整分页或 token 限制参数；大量因无效参数导致的工具错误可能表明工具需要更清晰的描述或更好的示例。当我们推出 Claude 的网页搜索工具时，我们发现 Claude 不必要地在工具的 query 参数后附加"2025"，导致搜索结果偏差和性能下降（我们通过改进工具描述引导 Claude 走上正轨）。

· · ·

与 Agent 协作

你甚至可以让 agent 分析结果并为你改进工具。只需将评估 agent 的 transcript 拼接起来粘贴到 Claude Code 中。Claude 擅长分析 transcript 并一次性重构大量工具——例如，确保在做出新更改时工具实现和描述保持自洽。

事实上，这篇文章中的大部分建议都来自用 Claude Code 反复优化我们内部工具实现的过程。我们的评估建立在内部工作空间之上，镜像了内部工作流的复杂度，包括真实的项目、文档和消息。我们依赖留出测试集来确保不会过拟合到"训练"评估。这些测试集揭示了我们可以在"专家"工具实现之上提取额外的性能改进——无论这些工具是由研究人员手动编写还是由 Claude 自己生成的。

在下一节中，我们将分享从这个过程中学到的一些经验。

· · ·

为 Agent 选择正确的工具

更多工具并不总是带来更好的结果。我们观察到的一个常见错误是：工具仅仅包装了现有的软件功能或 API 端点——不管这些工具是否适合 agent。这是因为 agent 与传统软件有不同的"可供性"（affordances）——也就是说，它们感知可用工具的潜在操作的方式不同。

LLM agent 的"上下文"有限（即它们一次能处理的信息量有限），而计算机内存便宜且充裕。考虑在通讯录中搜索联系人的任务。传统软件程序可以高效地逐个存储和处理联系人列表，逐一检查后继续。但如果 LLM agent 使用一个返回所有联系人的工具，然后必须逐 token 阅读每一个，它就在浪费有限的上下文空间在无关信息上（想象一下通过从头到尾逐页阅读来搜索通讯录中的联系人——即暴力搜索）。

更好、更自然的方法（对 agent 和人类都是如此）是先跳到相关页面（也许按字母顺序找到它）。

我们建议构建少量针对特定高影响力工作流的精心设计的工具，与你的评估任务匹配，然后从那里扩展。在通讯录的例子中，你可能选择实现 search_contacts 或 message_contact 工具，而不是 list_contacts 工具。

工具可以整合功能，在底层处理可能多个离散操作（或 API 调用）。例如，工具可以用相关元数据丰富工具响应，或在单次工具调用中处理经常链式执行的多步骤任务。以下是一些示例：

  • 不要实现 list_users、list_events 和 create_event 工具，考虑实现一个 schedule_event 工具来查找可用时间并安排事件
  • 不要实现 read_logs 工具，考虑实现一个 search_logs 工具，只返回相关日志行和一些周围上下文
  • 不要实现 get_customer_by_id、list_transactions 和 list_notes 工具，实现一个 get_customer_context 工具，一次性编译客户所有近期和相关信息

确保你构建的每个工具都有清晰、独特的用途。工具应该让 agent 能够以人类在拥有相同底层资源时会采用的方式来细分和解决任务，同时减少中间输出本来会消耗的上下文。太多工具或重叠的工具也会分散 agent 追求高效策略的注意力。对你构建（或不构建）的工具进行仔细、有选择性的规划确实能带来回报。

为工具添加命名空间

你的 AI agent 可能会获得数十个 MCP 服务器和数百种不同工具的访问权——包括其他开发者的工具。当工具在功能上重叠或用途模糊时，agent 会对使用哪个感到困惑。

命名空间（将相关工具归入共同前缀下）可以帮助划分大量工具之间的边界；MCP 客户端有时默认这样做。例如，按服务命名空间（如 asana_search、jira_search）和按资源命名空间（如 asana_projects_search、asana_users_search），可以帮助 agent 在正确的时间选择正确的工具。

我们发现，选择基于前缀还是基于后缀的命名空间对工具使用评估有非平凡的影响。效果因 LLM 而异，我们鼓励你根据自己的评估来选择命名方案。

Agent 可能调用错误的工具、用错误的参数调用正确的工具、调用太少的工具，或错误地处理工具响应。通过有选择性地实现名称反映任务自然细分的工具，你同时减少了加载到 agent 上下文中的工具数量和工具描述，并将 agentic 计算从 agent 的上下文卸载回工具调用本身。这降低了 agent 犯错的整体风险。

· · ·

从工具返回有意义的上下文

同样地，工具实现应注意只向 agent 返回高信号信息。它们应优先考虑上下文相关性而非灵活性，避免低级技术标识符（例如：uuid、256px_image_url、mime_type）。像 name、image_url 和 file_type 这样的字段更可能直接指导 agent 的下游行动和响应。

Agent 处理自然语言名称、术语或标识符的能力也明显优于处理晦涩标识符。我们发现，仅仅将任意字母数字 UUID 解析为更具语义意义和可解释性的语言（甚至是从 0 开始的 ID 方案），就能通过减少幻觉显著提升 Claude 在检索任务中的精确度。

在某些情况下，agent 可能需要灵活地与自然语言和技术标识符输出交互——哪怕只是为了触发下游工具调用（例如 search_user(name='jane') → send_message(id=12345)）。你可以通过在工具中暴露一个简单的 response_format 枚举参数来同时支持两者，让 agent 控制工具返回"简洁"还是"详细"响应。你可以添加更多格式以获得更大灵活性，类似于 GraphQL 中你可以精确选择想接收哪些信息。

以下是控制工具响应详细程度的 ResponseFormat 枚举示例：

enum ResponseFormat {
  DETAILED = "detailed",
  CONCISE = "concise"
}

详细工具响应示例（206 tokens）vs 简洁工具响应示例（72 tokens）：Slack 线程和回复通过唯一的 thread_ts 标识，获取线程回复需要它。thread_ts 和其他 ID（channel_id、user_id）可以从"详细"工具响应中获取以支持后续工具调用。"简洁"工具响应只返回线程内容，不包含 ID。在这个例子中，使用"简洁"响应只用了约 ⅓ 的 token。

甚至你的工具响应结构——例如 XML、JSON 或 Markdown——都可能影响评估性能：没有万能方案。这是因为 LLM 基于下一 token 预测训练，倾向于在与训练数据匹配的格式上表现更好。最优响应结构因任务和 agent 而异。我们鼓励你根据自己的评估选择最佳响应结构。

· · ·

优化工具响应的 Token 效率

优化上下文质量很重要，但优化返回给 agent 的上下文数量同样重要。我们建议对任何可能消耗大量上下文的工具响应实现分页、范围选择、过滤和/或截断的某种组合，并设置合理的默认参数值。对于 Claude Code，我们默认将工具响应限制在 25,000 token。我们预期 agent 的有效上下文长度会随时间增长，但对上下文高效工具的需求将持续存在。

如果你选择截断响应，确保用有帮助的指令引导 agent。你可以直接鼓励 agent 追求更 token 高效的策略，比如在知识检索任务中进行多次小而有针对性的搜索，而不是单次宽泛搜索。类似地，如果工具调用引发错误（例如输入验证期间），你可以对错误响应进行 prompt engineering，清晰传达具体且可操作的改进建议，而不是不透明的错误代码或堆栈跟踪。

工具截断和错误响应可以引导 agent 走向更 token 高效的工具使用行为（使用过滤器或分页），或给出正确格式化工具输入的示例。

· · ·

Prompt Engineering 你的工具描述

现在来到改进工具最有效的方法之一：对工具描述和规范进行 prompt engineering。因为这些会被加载到 agent 的上下文中，它们可以集体引导 agent 走向有效的工具调用行为。

编写工具描述和规范时，想想你会如何向团队新人描述你的工具。考虑你可能隐含带入的上下文——专门的查询格式、小众术语的定义、底层资源之间的关系——并将其显式化。通过清晰描述（并用严格数据模型强制执行）预期输入和输出来避免歧义。特别是，输入参数应该命名无歧义：不要用名为 user 的参数，试试 user_id。

有了评估，你可以更有信心地衡量 prompt engineering 的影响。即使是对工具描述的小改进也能带来巨大提升。Claude Sonnet 3.5 在我们对工具描述做出精确改进后，在 SWE-bench Verified 评估上达到了 state-of-the-art 表现，显著降低了错误率并提升了任务完成率。

你可以在我们的开发者指南中找到工具定义的其他最佳实践。如果你为 Claude 构建工具，我们还建议阅读关于工具如何动态加载到 Claude 的 system prompt 中的内容。最后，如果你为 MCP 服务器编写工具，工具注解有助于披露哪些工具需要开放世界访问或进行破坏性更改。

展望

要为 agent 构建有效的工具，我们需要将软件开发实践从可预测的确定性模式重新定向到非确定性模式。通过本文描述的迭代式、评估驱动的过程，我们发现了工具成功的一致模式：

有效的工具是有意图且清晰定义的，审慎使用 agent 上下文，可以在多样化工作流中组合，并让 agent 能直觉地解决真实世界任务。

未来，我们预期 agent 与世界交互的具体机制会演进——从 MCP 协议的更新到底层 LLM 本身的升级。通过系统化、评估驱动的方法来改进 agent 工具，我们可以确保随着 agent 变得更强大，它们使用的工具也会随之演进。
