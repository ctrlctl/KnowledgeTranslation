Designing AI-Resistant Technical Evaluations：设计 AI 无法攻破的技术评估

作者：Tristan Hume，Anthropic 性能优化团队负责人。

随着 AI 能力提升，评估技术候选人变得越来越难。一个今天能很好区分人类技能水平的 take-home 测试，明天可能被模型轻松解决——使其失去评估价值。

自 2024 年初以来，我们的性能工程团队使用一个 take-home 测试，候选人在模拟加速器上优化代码。超过 1000 名候选人完成了它，数十人现在在这里工作，包括启动我们 Trainium 集群和发布自 Claude 3 Opus 以来每个模型的工程师。

但每个新的 Claude 模型都迫使我们重新设计测试。在相同时间限制下，Claude Opus 4 超越了大多数人类申请者。这仍然允许我们区分最强的候选人——但随后 Claude Opus 4.5 甚至匹配了那些人。人类在无限时间下仍能超越模型，但在 take-home 的约束下，我们已经无法区分顶尖候选人的输出和我们最强模型的输出。

这篇文章描述了原始 take-home 设计、每个 Claude 模型如何击败它，以及我为确保测试领先于顶级模型能力而不得不采取的越来越不寻常的方法。

· · ·

Take-home 的起源

2023 年 11 月，我们正准备训练和发布 Claude Opus 3。我们获得了新的 TPU 和 GPU 集群，大型 Trainium 集群即将到来，但我们没有足够的性能工程师来应对新规模。我在 Twitter 上发帖招人，带来了比标准面试流程能评估的更多有前途的候选人。我们需要一种更高效评估候选人的方式。所以我花了两周设计了一个 take-home 测试。

· · ·

设计目标

Take-home 名声不好——通常充满通用问题，工程师觉得无聊，过滤效果也差。我的目标不同：创造真正有吸引力的东西，让候选人兴奋参与，并以高分辨率捕捉他们的技术能力。

格式相比现场面试的优势：更长的时间范围（4 小时窗口，后来缩短到 2 小时）、真实环境（无人观看，在自己的编辑器中工作）、理解和工具构建的时间、与 AI 辅助兼容（我们明确允许使用 AI 工具）。

设计原则：代表真实工作、高信号（避免依赖单一洞察的问题）、不要求特定领域知识、有趣。

· · ·

模拟机器

我构建了一个 Python 模拟器，模拟一个特征类似 TPU 的假加速器。候选人在这台机器上优化代码，使用热重载的 Perfetto trace 查看每条指令。机器包含：手动管理的 scratchpad 内存、VLIW（多执行单元并行）、SIMD（向量操作）和多核。

任务是并行树遍历，故意不是深度学习风格的——因为大多数性能工程师还没做过深度学习，可以在工作中学习。候选人从完全串行的实现开始，逐步利用机器的并行性。

· · ·

早期成果

最初的 take-home 效果很好。Twitter 批次中有一个人得分远超其他所有人。他在 2 月初入职，两周后就开始优化 kernel，并找到了一个涉及张量索引数学溢出 32 位的发布阻塞编译器 bug 的变通方案。

在接下来的一年半中，约 1000 名候选人完成了 take-home，它帮助我们雇用了当前性能工程团队的大部分人。对于纸面经验有限的候选人尤其有价值：我们几位表现最好的工程师直接从本科来，但在 take-home 上展示了足够的技能让我们有信心录用。

· · ·

Claude Opus 4 击败了它

到 2025 年 5 月，Claude 3.7 Sonnet 已经爬升到超过 50% 的候选人完全委托给 Claude Code 会更好的程度。然后我在 take-home 上测试了 Claude Opus 4 的预发布版本。它在 4 小时限制内想出了比几乎所有人类更优化的解决方案。

有一个直接的修复方案。问题的深度远超任何人能在 4 小时内探索的，所以我用 Claude Opus 4 来识别它开始挣扎的地方。那成为了版本 2 的新起点。我写了更干净的起始代码，添加了新的机器特性以增加深度，移除了多核（Claude 已经解决了），并将时间限制从 4 小时缩短到 2 小时。版本 2 强调巧妙的优化洞察而非调试和代码量。

· · ·

Claude Opus 4.5 又击败了那个

当我测试 Claude Opus 4.5 的预发布 checkpoint 时，我看着 Claude Code 在问题上工作了 2 小时，逐步改进解决方案。它在不到一小时内解决了初始瓶颈、实现了所有常见微优化并达到了我们的通过阈值。然后它停下来，确信遇到了不可逾越的内存带宽瓶颈。

大多数人类得出相同结论。但有巧妙的技巧可以利用问题结构绕过那个瓶颈。当我告诉 Claude 可能达到的 cycle 数时，它思考了一会儿找到了技巧。到 2 小时标记时，它的分数匹配了该时间限制内最好的人类表现。

· · ·

考虑选项

一些同事建议禁止 AI 辅助。我不想这样做——除了执行挑战外，我觉得既然人类在我们的工作中继续扮演重要角色，我应该能找到某种方式让他们在有 AI 的环境中脱颖而出。

其他人建议提高标准到"大幅超越 Claude Code 单独达到的水平"。问题是 Claude 工作很快。人类通常花一半的 2 小时阅读和理解问题才开始优化。试图引导 Claude 的人可能会不断落后。

如今 Anthropic 的性能工程师仍有大量工作要做，但看起来更像是困难的调试、系统设计、性能分析、弄清楚如何验证系统正确性。不幸的是这些东西很难在没有大量时间或共同上下文的情况下客观测试。

· · ·

尝试 1：不同的优化问题

我选择了一个基于我在 Anthropic 做过的更棘手的 kernel 优化的问题：在 2D TPU 寄存器上高效数据转置同时避免 bank conflict。我将其提炼为模拟机器上的更简单问题，让 Claude 在不到一天内实现了变更。

Claude Opus 4.5 找到了一个我都没想到的优化。通过仔细分析，它意识到可以转置整个计算而不是弄清楚如何转置数据。我修补了问题移除了那种方法。Claude 然后取得了进展但找不到最高效的解决方案。看起来我有了新问题——但我用 Claude Code 的"ultrathink"功能双重检查……它解决了。它甚至知道修复 bank conflict 的技巧。

回想起来，这不是正确的问题。许多平台的工程师都与数据转置和 bank conflict 斗争过，所以 Claude 有大量训练数据可以借鉴。

· · ·

尝试 2：更奇怪的方向

我需要一个人类推理能胜过 Claude 更大经验库的问题：足够 out of distribution 的东西。我想到了 Zachtronics 游戏——这些编程解谜游戏使用不寻常的、高度受限的指令集，迫使你以非常规方式编程。

我设计了一个新的 take-home，由使用微小、高度受限指令集的谜题组成，优化解决方案以最小化指令数。我实现了一个中等难度的谜题并在 Claude Opus 4.5 上测试。它失败了。

与 Zachtronics 游戏不同，我故意不提供可视化或调试工具。起始代码只检查解决方案是否有效。构建调试工具是被测试的一部分。

我对新的 take-home 相当满意。早期结果有前景：分数与候选人过去工作的水平相关良好。我仍然遗憾放弃了原版的真实性和多样深度。但真实性可能是我们不再拥有的奢侈品。原版有效是因为它像真实工作。替代版有效是因为它模拟了新颖的工作。

· · ·

开放挑战

我们发布原始 take-home 供任何人在无限时间下尝试。人类专家在足够长的时间范围内仍然优于当前模型。

性能基准（模拟机器的时钟周期，越低越好）：

  • 2164 cycles：Claude Opus 4 在 test-time compute harness 中多小时后
  • 1790 cycles：Claude Opus 4.5 在随意的 Claude Code session 中，约匹配 2 小时内最好的人类表现
  • 1579 cycles：Claude Opus 4.5 在 test-time compute harness 中 2 小时后
  • 1487 cycles：Claude Opus 4.5 在 harness 中 11.5 小时后
  • 1363 cycles：Claude Opus 4.5 在改进的 test-time compute harness 中多小时后
