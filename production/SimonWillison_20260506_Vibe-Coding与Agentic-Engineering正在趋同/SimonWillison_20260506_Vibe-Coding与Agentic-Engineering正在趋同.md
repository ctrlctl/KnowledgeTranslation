## Vibe coding 和 agentic engineering 开始重叠

几周前 Simon 还坚定地认为"vibe coding"和负责任地使用 AI 写代码（他称之为 agentic engineering）是完全不同的东西。但当被问到两者的区别时，他突然意识到它们对他来说已经不像以前那么泾渭分明了：

> 奇怪的是，这两件事对我来说已经开始模糊了，这让我很不安。

他原来的划分很清晰：

- **Vibe coding**：完全不看代码。可能不是程序员。要个东西，得到个东西，能用就行。不关心代码质量。适用于个人工具——如果有 bug 只伤害你自己，随便搞。但如果为他人构建软件，vibe coding 是**极不负责任的**，因为涉及他人的信息。

- **Agentic engineering**：你是专业软件工程师。理解安全性、可维护性、运维、性能等。用这些工具发挥你自身能力的最大值。目标是构建**更高质量**的生产系统——不是更快地构建低质量的东西，而是更快地构建在各方面都比以前更好的东西。

问题在于：随着编码 agent 越来越可靠，**他不再审查它们写的每一行代码了**，即使是生产级别的东西。

> 我很清楚，如果你让 Claude Code 构建一个运行 SQL 查询并输出 JSON 的 API 端点，它就是会做对。它不会搞砸。你让它加自动化测试，加文档，你知道它会做好。
>
> 但我没有审查那些代码。现在我有了那种负罪感：如果我没有审查代码，在生产中使用它真的负责任吗？

他找到的心理模型是回想在大组织工作时的经验：

> 如果另一个团队交付了一个东西说"这是图片缩放服务，这样用它来缩放图片"……我不会去读他们写的每一行代码。我会看他们的文档，用它缩放一些图片，然后开始交付我自己的功能。只有当我遇到问题时才可能去翻他们的 Git 仓库。大部分时候我把它当作一个半黑盒。
>
> 我开始以同样的方式对待 agent。这仍然让人不舒服，因为人类要为自己做的事负责。一个团队可以建立声誉。Claude Code 没有职业声誉！它不能为自己做的事承担责任。但它一直在证明自己——一次又一次地产出直接的东西并做对了。

这里有**偏差正常化**（normalization of deviance）的成分——每次模型在没有密切监控的情况下写出正确代码，都有风险让你在未来错误的时刻信任它而被坑。

## 评估软件的新挑战

> 以前如果你找到一个有一百个 commit、好的 readme、自动化测试的 GitHub 仓库，你可以相当确定写它的人投入了大量心血。
>
> 现在我能在半小时内搞出一个有一百个 commit、漂亮 readme、每行代码都有全面测试的 git 仓库！它看起来和那些精心打造的项目一模一样。也许它确实一样好。我不知道。从外表看不出来。即使是我**自己的**项目，我也分不清。

他意识到，比测试和文档质量更有价值的是：**有人实际使用过这个东西**。

> 如果你有一个 vibe coded 的东西，你过去两周每天都在用，对我来说这比你刚吐出来几乎没怎么运行过的东西有价值得多。

---

## 瓶颈已经转移

> 如果你能从每天产出 200 行代码变成每天 2000 行，还有什么会崩溃？整个软件开发生命周期，事实证明，是围绕"产出几百行代码需要一天"这个假设设计的。现在不是了。

不只是下游的东西，上游也是。Simon 引用了 Anthropic 设计负责人 Jenny Wen 的演讲：

> 我们所有的设计流程都基于一个假设——你需要把设计做**对**，因为如果你交给工程师，他们花三个月构建了错误的东西，那是灾难性的。
>
> 但如果构建不需要三个月，也许设计流程可以冒更大的风险，因为犯错的成本已经大幅降低了。

## 为什么我仍然不担心自己的职业

> 当我看我和 agent 的对话时，很明显这对绝大多数人来说是天书。
>
> 我不害怕我作为软件工程师的职业结束了，部分原因是这些东西是**现有经验的放大器**。如果你知道自己在做什么，你可以用它们跑得快得多。
>
> 我在使用这些工具时不断被提醒我们做的事有多难。生产软件是一件**极其**困难的事。你可以给我世界上所有的 AI 工具，我们试图实现的东西仍然真的很难。

关于 SaaS 提供商面临的威胁——公司自己搞解决方案而不是买：

> 我只想用你的 side project 如果你已经用了几周。企业版本就是：我不想要一个 CRM，除非至少两个其他大企业已经成功使用了六个月。你想要经过验证能工作的解决方案。

Matthew Yglesias 的推文总结得很好："五个月了，我决定我不想 vibecode——我想要专业管理的软件公司使用 AI 编码辅助来制造更多/更好/更便宜的软件产品，然后卖给我。"
