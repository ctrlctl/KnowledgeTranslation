## Vibe coding 和 agentic engineering 开始重叠

"vibe coding"这个词被造出来几周后，我发表了[《不是所有 AI 辅助编程都是 vibe coding》](https://simonwillison.net/2025/Mar/19/vibe-coding/)，坚定地表明我的信念：vibe coding 和负责任地使用 AI 写代码是非常不同的东西——后者我后来开始称为 agentic engineering。

当 Joseph 提到两者的区别时，我突然意识到它们对我来说已经不像以前那么泾渭分明了：

> 奇怪的是，这两件事对我来说已经开始模糊了，这让我很不安。我以为我们有一个非常清晰的界限——vibe coding 是你完全不看代码的那种东西。你甚至可能不会编程。你可能是一个非程序员，要求一个东西，得到一个东西，如果东西能用就太好了！如果不行，你告诉它不行然后祈祷。但你从来不真正关心代码质量或任何额外的约束。
>
> 我对 vibe coding 的看法是：它很棒，前提是你理解什么时候可以用、什么时候不行。给你自己用的个人工具，如果有 bug 只伤害你自己，尽管去做！如果你在为别人构建软件，vibe coding 是极不负责任的，因为那是别人的信息。别人会被你的愚蠢 bug 伤害。你需要有更高的标准。
>
> 这与 agentic engineering 形成对比——你是一个专业软件工程师。你理解安全性、可维护性、运维、性能等等。你在用这些工具发挥你自己能力的最高水平。我发现我能承担的挑战范围已经显著增加了，因为有这些工具的支持。但我仍然依赖我 25 年的软件工程经验。目标是构建高质量的生产系统：如果你只是更快地构建低质量的东西，我认为那是坏事。我想更快地构建更高质量的东西。

**问题是：随着编程 agent 变得更可靠，我不再审查它们写的每一行代码了，即使是我的生产级别的东西。**

我很清楚，如果你让 Claude Code 构建一个运行 SQL 查询并输出 JSON 结果的 API 端点，它就是会做对。它不会搞砸。你让它加自动化测试，让它加文档，你知道它会是好的。但我没有审查那些代码。

现在我有了那种负罪感：如果我没有审查代码，在生产中使用它真的负责任吗？

真正帮助我的是回想在大型组织工作时的经历。其他团队构建我的团队依赖的软件。如果另一个团队交给我一个东西说"嘿，这是图片缩放服务，这是怎么用它来缩放图片"……我不会去读他们写的每一行代码。我会看他们的文档，用它来缩放一些图片，然后开始发布我自己的功能。如果我开始遇到问题，那时我可能会去看他们的 Git 仓库。但大部分时候我把它当作一个半黑盒，直到需要时才去看。

**我开始以同样的方式对待 agent。** 这仍然让人不舒服，因为人类要为自己做的事负责。一个团队可以建立声誉。我可以说"我信任那边那个团队。他们过去构建了好软件。"Claude Code 没有职业声誉！它不能为自己做的事负责。但它一直在证明自己——一次又一次地产出直接的东西并以我喜欢的风格做对。

这里有一个**偏差正常化**（normalization of deviance）的元素——每次模型在我没有密切监控的情况下写出了正确的代码，都有风险让我在未来错误的时刻信任它而被烧到。

## 评估软件的新挑战

> 过去，如果你找到一个有一百个 commit、好的 readme 和自动化测试的 GitHub 仓库，你可以相当确定写它的人在这个项目上投入了大量的关注和心血。现在我可以在半小时内产出一个有一百个 commit、漂亮 readme 和全面测试的 git 仓库！它看起来和那些投入了大量关注的项目一模一样。也许它确实一样好。我不知道。我从看它无法判断。即使是我自己的项目，我也无法判断。

所以我意识到，比测试和文档的质量更重要的是：**我想要有人用过这个东西。** 如果你有一个 vibe coded 的东西，你过去两周每天都在用，那对我来说比你刚吐出来几乎没有运行过的东西有价值得多。

## 瓶颈已经转移

如果你能从每天产出 200 行代码变成每天 2000 行，还有什么会崩溃？

事实证明，整个软件开发生命周期都是围绕"产出几百行代码需要一天"这个假设设计的。现在不是了。不仅是下游的东西，上游的也是。

我看了 Jenny Wen（Anthropic 的设计负责人）的一个很棒的演讲，她说我们所有这些设计流程都基于一个假设：你需要把设计做对——因为如果你交给工程师，他们花三个月构建了错误的东西，那是灾难性的。有一整套非常广泛的设计流程，因为设计导致昂贵的工作。

但如果构建不需要三个月，也许设计流程可以冒更大的风险，因为犯错的成本已经大幅降低了。

## 为什么我仍然不担心自己的职业

> 当我看我和 agent 的对话时，对我来说很清楚，这对绝大多数人来说是天书。我不害怕我作为软件工程师的职业已经结束的原因有很多，部分是因为这些东西是现有经验的放大器。如果你知道自己在做什么，你可以用它们跑得快得多。
>
> 我在使用这些工具时不断被提醒我们做的事情有多难。产出软件是一件极其困难的事情。你可以给我世界上所有的 AI 工具，我们试图实现的东西仍然真的很难。

Matthew Yglesias（政治评论员）昨天发推说："五个月了，我想我已经决定我不想 vibecode——我想要专业管理的软件公司使用 AI 编程辅助来制造更多/更好/更便宜的软件产品，然后卖给我。"

这对我来说感觉差不多对。我可以看够 YouTube 视频自己修水管。但我宁愿雇一个水管工。

关于 SaaS 提供商面临公司自建解决方案的威胁：

> 我刚意识到这就是我之前说的——我只想用你的副项目如果你已经用了几周。企业版本就是：我不想要一个 CRM，除非至少两个其他大型企业已经成功使用那个 CRM 六个月了。你想要被证明有效的解决方案，然后才冒险使用它们。
