## 核心论点：预训练需要为 Agent 重新设计 [02:54]

Aakanksha 的核心观点：过去三年的进步（推理、tool use）几乎全部来自 post-training（RLHF、RL），预训练本身没有根本性变化。但这种方式**从根本上限制了模型能达到的能力上限**。

如果我们希望模型成为真正的 agent——能与环境交互、执行多步目标导向任务——预训练就需要从基础重新思考。这不仅仅是 post-training 能解决的问题。

---

## Agent 需要什么能力 [05:46]

Agent 需要的核心能力清单：

1. **规划（planning）**：能预判多步之后的状态
2. **长上下文推理**：在很长的上下文中推理，而不仅仅是检索
3. **从失败轨迹中学习**：遇到短期挫折后能纠正方向
4. **动态学习新工具**：探索未知环境中的工具并学会使用

当前的限制：企业构建 agentic 系统时，本质上受限于"能塞进 context length 的东西"——context engineering 就是在这个约束下做文章。agent 的边界就是 context 的边界，超出的部分只能交给下一个 sub-agent。

## 注意力机制的演进方向 [11:26]

Aakanksha 对架构变革持**极度保守**态度——她训练过 5 个大规模模型，每次都要在 war room 里 debug。经验教训：

- 在规模上，看起来无害的改动经常失效
- 每个 bet 都必须经过极其严格的验证
- Transformer 相对于"下一个最好的东西"已经被充分验证

但注意力机制确实需要演进：模型需要能**引用上下文中很远处的信息**，而不仅仅是局部注意。例如深度研究 agent 收集了 100 篇文章后，需要将它们组织成主题——这对注意力机制的要求远超简单检索。

关键区分：**长上下文检索**（needle in a haystack）已经解决了；**长上下文推理**（multi-hop reasoning，如 MRCR V2、Loft 基准）才是真正的难题。即使有百万 token 的 context length，模型也不一定能对所有内容进行综合推理。

## 损失函数的重新设计 [16:08]

Next-token prediction 作为损失函数，意外地产生了强大的推理能力。但它是最优的吗？

已有的损失函数技巧：
- **Fill-in-the-middle**：打乱代码文件顺序，让模型预测中间部分
- **Masking**：训练 tool use 时，mask 掉特定部分（如搜索查询、工具选择），让模型学习预测这些关键决策点

核心思路：**把 post-training 中有效的东西拉回到预训练阶段**，统一两个范式。问题不再是"推理能力应该在最后阶段赋予还是前移"，而是"我们是否需要严格区分 pre 和 post"。

## 训练数据：推理轨迹的规模化 [19:36]

预训练数据的三个演进方向：

1. **数据质量 > 数据规模**：来自中国实验室（Qwen、DeepSeek、Kimi）的经验表明，精心策划的高质量数据能显著提升计算效率
2. **推理轨迹（reasoning traces）**：如何获取各领域专家解决问题的过程记录？目前通过 RL 环境让模型自己探索生成，但规模有限
3. **合成数据增强**：用互联网文章作为基础，转化为 QA 对、对话形式、问题求解任务——关键是**不能改变底层数据分布**，否则模型会退化

成本问题：如果预训练用了数十万亿 token，对其中一部分做推理增强（每百万 token 不到一美元），总成本其实可控。

"smoking your own exhaust"问题的应对：保持合成数据的分布与自然数据分布高度一致，不能让合成数据主导。

## 长程推理：两种含义 [33:33]

**含义一：跨距离的信息综合**

例子：理解整个代码库，包括其他团队写的部分。模型需要将位置上相距很远的信息关联起来推理——这不是检索问题，是推理问题。

**含义二：轨迹层面的前瞻规划**

像下棋一样，当前动作需要考虑它会把你带向目标的哪个方向。但 next-token prediction 天然是局部的——模型不知道"这组 token 会把我带到哪里"。

当前的失败模式：模型陷入重复循环，因为它**不知道自己之前失败过**——最高概率的下一步仍然是重复同样的动作。

---

## 从失败中恢复 [38:09]

轨迹（trajectory）的定义：计划 → 执行 → 验证 → 根据反馈调整。

恢复能力需要两个层面的支持：

1. **RL 层面**：模型需要选择新的动作空间（不重复失败动作）
2. **预训练层面**：模型是否注意到了哪些是失败步骤？轨迹的格式是否让模型能识别出需要纠正的部分？

这不是幻觉问题的简单翻版。Aakanksha 将幻觉重新定义为"概率上最高的下一组 token"——问题是：**是否有额外的上下文或工具反馈能改变这个概率分布？**

目标：让模型学会"学习如何学习"和"学习如何自我纠正"。

---

## 学习使用新工具 [44:01]

当前状态：模型只知道放进 context 里的工具。MCP 的困境——工具描述撑爆 context，但不放又不知道有什么工具可用。

理想状态：模型通过**探索和交互反馈**学习新工具，类似机器人领域的"观察模仿学习"。

有前景的方向：统一的领域特定语言（可能是代码格式），让模型通过这种语言来推理和探索工具。

这比当前的三种方案都更灵活：
- 全部塞进 context（太贵）
- 用正确轨迹微调（不够通用）
- 精心工程化的工具系统（太脆弱）

但这还远未解决——"不是现成可用的"。

## 评估基准的缺失 [26:01]

当前状态：每年出新基准，很快被刷满，再出新的。前沿实验室都在内部构建自己的基准。

需要的基准特征：
- **变化的复杂度**：从简单到多步
- **变化的能力维度**：规划、推理、恢复、工具学习
- **真实工作流的分解**：把一天的工作拆成子问题，找到模型做不好的部分

有前景的方向：METR 的 Software Atomic Actions（变长任务）、SWE-bench 风格的编码任务。

关键洞察：**好的基准是发现能力的前提**。PaLM 训练到一半时，在一个众包推理基准上发现了 step change——如果没有那个基准，就不会注意到模型已经开始展现推理能力。

## 规模与能力涌现 [31:03]

Aakanksha 的立场：

- **能力涌现需要规模**：很多能力只在大模型中首先出现
- **发现后可以蒸馏**：一旦在大模型中发现了某种能力并理解了 recipe，下一代小模型就能获得同样能力
- **小实验室不能只做小模型**：必须先做到足够大的规模来发现能力，然后再做成本优化

路径：最强大的模型 → 发现能力 → 理解 recipe → 蒸馏到小模型 → 成本效率。

这也是 Reflection 的策略：先追求最强能力，再追求最高性价比。
