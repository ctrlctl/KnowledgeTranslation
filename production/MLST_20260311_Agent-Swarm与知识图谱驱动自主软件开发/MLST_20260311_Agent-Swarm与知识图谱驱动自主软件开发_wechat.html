Agent Swarm与知识图谱驱动自主软件开发

引言与背景 [00:48]

我们采取的方法是动态招募多个 agent swarm，并将数据库作为编排层（orchestration layer）的一部分。你可以招募数万个 agent，而不必担心有一个单一的编排器在追踪所有正在发生的事情。我们已经成功应用了这种方法，经常编写数十万行、数百万行代码——全部能编译、全部能运行、所有测试通过、UI 完美呈现。我们确实已经把这件事做到了极致。

在 NVIDIA 的经历非常精彩。NVIDIA 的运作方式很像一家创业公司，从 2016 年到 2022 年一直如此。当"Attention Is All You Need"论文发表时，我就在那里。我在 NVIDIA 的生成式 AI 领域做发明——深入研究 GAN（生成对抗网络）和各种自编码器，也接触 NLP。当时还很早期，有 BERT，我们用 BERT 做翻译之类的事。Transformer 是突破性的技术。

软件开发的分类 [04:12]

AI 影响最大的领域之一确实是软件开发。原因在于：软件是可验证的——可编译、可测试、可视化，而且存在"正确答案"的概念。可能有多个正确答案，但确实有对错之分，这在其他领域并不总是如此。

整个空间可以这样划分：

一方面是 AI 辅助开发——copilot、带嵌入式 AI 的 IDE 工具。它们可以异步执行任务，给它一个可能需要几小时的工作，它会思考一段时间，异步处理，问你后续问题。

另一方面是自主开发（autonomous development）。Cognition 的 Devin 属于这个类别，我们也在这个类别。核心理念是：你点击"构建"，出来一个 PR。这个 PR 已经经过测试、验证，一切正常，完全符合你的意图，没有错误，代码可接受。

最大的挑战是代码接受度（code acceptance）。让 AI 写代码很容易——代码现在是商品。但让代码遵循你的标准、真正优秀、安全、可投入生产，那是完全不同的故事。

AI 在绿地项目（greenfield builds）上表现很好——实验室的演示看起来很惊艳。但当你把同样的 AI 放到企业代码库上，要求它与现有代码协作时，它就搞砸了。这难度高了几个数量级，因为 AI 要处理大量信息和边界条件，导致工具失败。

Spec 的角色与局限 [07:12]

Sam：从接受度回溯到 agent 写代码，另一端必须有某种规格说明（spec）。你是不是本质上把编码的所有复杂性都推到了 spec 开发上？

Sudant：是也不是。如果你能写 spec，那就应该写。所有我们熟悉的工具都有 plan mode。Spec 帮助 agent 锚定自己。但人们很快发现 spec 不够好，因为还有其他通用规则需要 agent 遵循。传统做法是用 agents.md、添加 skills 等，试图保持 spec 轻量——因为模型在一段时间后会遗忘，或者经过 compaction 之后。

但还有另一类任务，依赖关系不明确。比如你不知道后端数据库的 schema 是什么样的，你没法为它写 spec，因为你不知道约束条件。你不能只信任 AI 去搞清楚 schema 然后做 X，因为当你搞清楚 schema 时会获得新信息，这会影响你正在编写的代码的决策和架构。

所以你总是在一个频谱上工作——与 agent 一对一协作，它给你更多信息，你帮它做决策。

未来如果能构建更智能的模型，能做出人类级别甚至更好的架构决策，那么确实可以有一整类工作专注于写 spec，然后指导其他更便宜、更快的 agent 来写代码。

传统工作流的挑战 [09:35]

Sam：如果 spec 不够，人类还在循环中，那"自主开发"到底有多自主？

Sudant：即使你有一个很好的 spec，如果它是一个复杂的 spec，覆盖 50,000 到 100,000 行代码——比如大型代码库的 Java 升级，或者在复杂后端上添加 UI——这些是跨多个文件的巨大变更。

你可以写 spec，给 agent，用你喜欢的 CLI（比如 Claude Code）。它会花时间执行，但在某个点上，它会遇到需要人类回答的问题，或者它会经历多次 context compaction，因为它只有大约 100 万 token 的上下文。compaction 之后输出质量就不一样了——信息会丢失。

它确实会很智能地尝试保留所有相关信息，但不完美。如果它花时间去找回丢失的东西，很可能因为体量太大又触发 compaction，陷入循环。

这就是为什么 Anthropic 发布的那个 C 编译器大项目，最热门的 issue 是"这个 repo 不应该存在，因为 Hello World 都编译不了"。当你试图对现有工具应用所谓的 Ralph Vigam loop（本质上就是反复运行直到得到正确答案）时，就会出现这种问题。

关键不仅仅是给 AI 一个 spec。核心在于 context engineering 和 agent engineering。

Context engineering 是在正确的时间给 AI 正确数量的上下文。在企业规模下，当你有成百上千的开发者时，不是每个人都能以同样的效率使用工具。所有 CLI 工具——Codex、Claude Code 等——都需要大量设置：连接了正确的 MCP 吗？用了正确的 skills 吗？用了正确的 prompt 吗？对 Anthropic 有效的 prompt 对 OpenAI 不一定有效（OpenAI 训练中不用 XML token，但 Anthropic 用）。

Agent engineering 是为正确的任务招募正确的 agent，配备正确的 prompt 和工具集，以及正确级别的 prompt engineering。因为确实有些任务 GPT 比 Opus 做得更好。

无限上下文与知识图谱 [14:28]

当你把 context engineering 和 agent engineering 结合起来，解决一些最重要的挑战——比如上下文限制——你就能实现自主开发。至少对 Blitzi 来说，我们有一个非常创造性的解决方案：有效实现了无限上下文，因为我们应用了 context engineering 和 agent engineering。

传统工作流的具体痛点 [15:00]

以 Java 升级为例。用典型的开发工作流（假设你在用 Codex 或 Claude Code）：你会制定一个 spec，用 Claude Code 进入 plan mode 构建 spec，然后拿到 Codex 让它审查，希望你遵循了正确的 prompting 指南，给了它正确的上下文。

但在 spec 生成阶段就会出问题。对于非常大的代码库，不使用深度索引技术的工具依赖浅层索引——几分钟就完成索引，不会建立对代码库关系的深度理解。它们依赖 grep 来查找东西。

比如你要修改认证提供者（auth provider），在一个 1000 万行的代码库中查找所有使用 auth 的函数。可能有成千上万个地方用到了 auth provider，而且不是所有函数都叫 "login"。它依赖模型的智能来找到所有这些地方并正确更新——经常会遗漏。

然后当它尝试编译时会出错，试图修 bug，开始偏离计划，修改计划中没有的东西。你在违背计划，因为计划本身就不完美。

即使你拿到了计划，接下来要执行。如果项目非常复杂，每个任务可能需要几小时甚至几天。然后有 sub-agent 的概念——并行或串行运行。但很难确定哪些任务应该并行、哪些串行，以及它们之间的重叠。agent 可能会互相对抗。

还有工具的问题。比如你想让 agent 实时测试 web 应用，给它 Chrome MCP——一下子就从上下文中丢失了 20,000 token。你可能有 5 个不同的 MCP，如果每个都像 Chrome 那么复杂，你就丢失了 100,000 token。

这些 LLM 的有效操作前沿仍然不到 100K-150K token。 即使它们有 100 万 token 的上下文，根据 needle-in-the-haystack 排行榜，一旦加载超过 80K-100K token（Opus 4.6 的水平），agent 就无法以最佳状态运行。

你加载了 spec，又加载了所有其他东西，还没算上 skills 和 agents.md。当你有百万行代码库、多个模块、不同团队各有不同的 agents.md 和大量 skills 时——你很容易超过有效前沿。而你甚至还没加载实际要工作的文件。

图+向量的混合方案 [20:24]

Sudant：我们从一开始就做的一件事是构建一个锚点，让 agent 能在代码库中定位自己、跨代码库查找东西。

我们构建了一个图和向量的混合体——有一个摄取过程，理解整个代码库、映射关系、做语义摘要和聚合。现在你有了整个代码库的地图。如果我想从一个点到另一个 1000 万行深处的点，我可以在一次请求中瞬间完成，而不是烧掉大量 token 去遍历不同文件找到链路。

Sam：这在很多方面与传统工具的演进方向相悖。我们从 RAG 开始——早期的 copilot 版本本质上是基于 RAG 的，用语义向量搜索代码库、识别 chunk、作为上下文传递。然后我们都兴奋的 Codex 和 Claude Code 不再这样做了——它们只用 grep。你说 grep 在规模上不行。

Sudant：我们应用向量和图的方式是与 grep 结合。就像 Find My 给你方向，然后你沿着方向走直到找到东西——它不告诉你确切位置，但这极其有帮助。语义让你方向性地接近，然后 grep 让你到达确切的行。你用语义来缩小搜索空间。

阈值大概是：如果代码库大于你最大上下文窗口的两倍。粗略来说，如果你做的变更超过 10,000 行，在一个 70K-100K 行左右或更大的 repo 中，那么 RAG 支持的优势就会明显体现——搜索时间会大幅下降。在 70K-100K 行的代码库中，你可能有多个模块、多个团队，可以真正利用 multi-agent 和这些锚点。

Multi-Agent：从多线程到超级并行 [25:04]

有效上下文窗口没有在变化。 从 10,000 token 到 100 万 token，但有效上下文一直停留在 80K-120K token——最新模型也是如此，两年来没变。即使每三个月出一个新模型，有效上下文窗口没有改变。物理约束——计算容量、电力、规模——这些问题在未来三个月、六个月甚至三年内都不会有根本性改变。

Multi-agent 的第一种技术是 sub-agent：一个编排器/领导模型招募多个 sub-agent。可以并行搜索、并行化任务（前端一个、后端一个）。优势是速度和有效智能，而且显著减少了头部 agent 的上下文使用——它不再需要自己做所有搜索和遍历，而是从不同 agent 获取结果。

但仍有瓶颈：领导 agent。所有人都要向它汇报，所以你不能运行数百个 agent——你压缩了上下文，但没有克服上下文作为根本限制。你只是把问题踢远了一点。对于数百万行的代码库，用 Claude Code 让它做所有事情是不够的——你甚至不能用 Opus 4.6 的 Claude Code 构建一个 100K 行的 C 编译器。

我们的方法：动态招募多个 agent swarm，并将数据库作为编排层的一部分。你有 spec，要执行 spec，用 AI 将其分解为任务，然后为不同任务使用不同的 agent 集合——递归地做这件事。最终你为每个 agent 得到一个高效的任务，可以招募数万个 agent，而不必担心单一编排器追踪所有事情。

你可以大规模并行化，就像 GPU 的工作方式。我在 NVIDIA 待过，我知道 GPU 怎么工作。与其说是多线程（sub-agent 模式的效果），不如说是超级扩展（hyper scaling）。这就是我认为的未来。

· · ·

防止 Agent 互相踩踏 [29:26]

Sam：很多 agent 在相邻任务上大规模运行，怎么防止它们互相踩踏？

Sudant：几种技术：

1. 多环境：给 agent 不只一个而是多个沙箱环境来操作，然后用源代码汇聚结果。每个 agent 都在向 GitHub 提交，沿着链路确认路径是否可行。 2. 周期性审查：定期重新审视代码，检查是否仍能编译、是否仍符合 spec。在交付代码给用户之前，有 agent 审查所有代码确保没有偏移，有 QA agent 测试所有代码，有开发 agent 处理反馈。 3. 图数据库：因为你有整个代码库的关系映射——文件依赖什么、导入什么库、库的版本是什么、为什么用这个库。有这个锚点是巨大的改变。每个 agent 都在这个图的节点上操作，所以 agent 不太容易踩到其他 agent 的脚。

Agent 角色：静态 vs 动态 [32:06]

Sam：agent 的角色/人格是固定的还是动态的？你是花大量时间做 prompt engineering——"这是代码编写 agent"、"这是代码审查 agent"——还是 agent 根据任务自己搞清楚？

Sudant：我们刚开始时，所有 agent 都是 100% 静态的，因为模型不够聪明——我们用的是 Claude 3.5、3.6。完全不同的世界。当时甚至没有 tool calling。

但随着 agent 变得非常聪明，我们现在有一套基础指南，尽量保持轻量——不超过 5,000 token，这非常难做到。另一个杠杆是 prompt 指南——我们有指南发布位置的 URL 引用，给了 agent 查找 prompt 指南的能力。

在最新版本的平台中，agent 设计 agent。你有一套我们实现的工具、一套预写的 MCP 或外部工具集成。我们写所有工具、写 harness、设置环境。我们不给 agent 直接访问 SCM 或数据库的权限——我们都知道 agent 能干什么。但我们有工具让 agent 使用：推送变更到 origin、拉取最新变更、提交、编辑文件、启动浏览器等。

然后 agent 看 spec（甚至是 spec 的部分，因为我们把不同部分分配给不同 agent），决定什么 agent 最适合解决这个任务。

我们一直看到的是：如果你给 agent 一个人格（persona），然后给它一个使命和专用工具集，它的表现会与没有这些的 agent 截然不同。很多模型智能的魔力来自推理（reasoning），推理的质量受人格影响。

所以给 agent 设计正确的人格和正确的工具集非常重要——不能过载上下文。我们有检查机制：当这个 agent 启动时，它会加载多少上下文？它是否仍在有效上下文窗口内操作？

Persona 的实际效果 [36:10]

Sam：这让我想到早期那种"你是一个专家文案"的 prompt 开头。我们看到很多这种做法，然后又看到人们远离它。但听起来你的经验是，给 agent 一个强烈的专业身份对性能很重要？

Sudant：是的。我们内部有 eval 来评估 LLM 和 agent 在规模上的表现。我们确切知道一行指令会对 agent 的轨迹产生什么影响。

一个例子：我们为一家银行写文档，agent 没有金融专家的 persona。结果它使用的语言和术语不符合银行的期望。然后我们做了同样的事，但改变了写文档 agent 的 persona——结果大幅改善，因为它使用了银行开发者能理解的术语。

有人把这描述为：模型有整个语义空间，通过告诉它角色，你把它放到了任务的正确语义邻域。

人们不再建议这样做，是因为对大多数日常用例你不需要它——性能已经够好了。但当你在超大规模、真正复杂的企业用例中工作时，这是真正有帮助的小事之一。

· · ·

Agents.md 的局限性 [39:00]

Sam：最近有研究说 agents.md 实际上可能适得其反。你有什么经验？

Sudant：100% 同意。agents.md 无法扩展。对于小于 70-100K 行的代码库，它应该很好用——你可以有一个扁平文件，一到三个团队，把所有指南放在那里。

但它无法泛化。你不能用文本来泛化。你不能把团队开发者的所有经验放在一个文件里，然后期望它在整个代码库中泛化——无论模型多聪明，它就是在用不充分的信息工作。而且有太多其他东西在争夺注意力。

一个具体例子：我们用 Blitzi 来构建 Blitzi。我们有一条规则说"在 Python 中只用 fakes 不用 mocks 写测试"。但代码库中已经大量使用了 mocks。我们还有另一条指令说"始终模仿代码库中已有的模式"。你觉得 agent 会怎么做？结果是有时用 fakes 有时用 mocks，完全随机。

所以 agents.md 在很多情况下确实可能适得其反。但在大多数较小规模的用例中，它是一个相当有效的技术。

· · ·

Eval 的困境 [41:25]

Sam：这让人反思，与 agent 的工作有多少是任务和上下文相关的。我们到处看到各种指令——"你应该这样 prompt"——但归根结底还是 eval 的重要性。

Sudant：Eval 一直在表现不佳。就在昨天，OpenAI 发布了一份备忘录说他们停止在 SWE-bench Verified 上测试，因为问题定义不够好——而他们参与创建了 SWE-bench Verified。他们现在在 SWE-bench Pro 上测试。

但即使你看在 SWE-bench Verified 或 SWE-bench Pro 或 Terminal Bench 上表现相似的模型，在真实世界中的表现截然不同。

比如 Gemini 和 Anthropic——我喜欢这两个模型，它们分数相似。但给它们同样的问题，不加额外指令：Gemini 倾向于更创造性、更冗长的方法；Opus 则更精确。这些差异在真实世界中非常显著，因为你很难为每种可能性都 prompt agent。如果你在做那件事，那 agent 的意义何在？让 agent 自己搞清楚才是重点。

没有任何排行榜能捕捉到这一点。 对某些人来说，这关乎智能。如果你为一个应该一行搞定的事写了 100 行代码，对资深工程师来说，这个人就是不够聪明。即使排行榜上你最终能得到正确答案，轨迹很重要、风格很重要、方法很重要——因为你最终在考虑扩展性。

我们也在尝试公开我们的内部 eval。Eval 绝对是最令人兴奋的空间，因为一年前 Anthropic 在编码领域是明确的领导者，但现在 OpenAI 已经追上来了，开源和 Google 也在很多领域追赶。拥有真正好的、健壮的 eval 至关重要。

· · ·

模型选择与任务分配 [45:10]

Sam：模型性能如此任务特定，这对你的任务分解和分配会造成很多挑战。你怎么知道该把任务给哪个模型？

Sudant：如果变量太多就很难找到解决方案，所以你需要让一些变量成为常量。我们让内容常量、prompt 常量。但挑战是如果 prompting 指南不同，你怎么知道它真的是常量？

我们的做法是：选一个 LLM 作为最终裁判，让它写 prompt。我们用英文写 eval 的 prompt，然后让 LLM 根据最新指南改进 prompt。现在你有了一个遵循模型提供商所有推荐指南的 prompt，任务指令是常量，然后你在那个任务上运行模型。

任务可以是：构建一个与 Figma 保真的前端、构建新 API、让一个有大量错误的代码库编译通过。你可以创建模拟真实世界的 eval——真正复杂的、涉及多个文件的、可能数百万行的。用合成数据创建这样的 eval。

然后看 trace，评估模型：最终是否得到正确答案？烧了多少 token？多少轮？经历了多少次 compaction？总时间？推理 trace 中模型多快理解了问题是什么？harness 是否误导了模型？

即使工具不够有效、问题本身很复杂，但如果某个模型表现极好——烧的 token 少得多、做了更多 tool call、做出了明智决策——那在真实世界项目中我更愿意用这个模型。

如何判断输出质量 [49:03]

Sam：代码能编译、能通过 linter、能通过测试套件——这些 agent 都在自动做。但还有其他特征——你叫它 smell 也好、vibes 也好。你怎么评估这类东西？

Sudant：在项目结束时，当你准备产出 PR 或最终输出时，我们创建一个叫 project guide 的东西。它基于对代码库的分析，追踪相对于初始 spec 的完成度。我们不是在想代码本身——我们在想客户和企业如何把它投入生产。

企业需要花多少时间在这个代码库上才能投入生产？基于我们在代码中看到的，我们自主完成了多少？我们给出一个完成度指标。通常我们能自主完成 80% 的工作（以小时计）。

可维护性与代码质量 [53:05]

Sam：如果你要留给我 20% 的工作，你给我的 80% 必须是人类能理解和使用的——不能是某种虽然技术上通过测试但不可穿透、不可用的 slop。

Sudant：圈复杂度（cyclomatic complexity）是代表可维护性的指标之一——代码有多难维护。比如如果你有非常脆弱的 if 块，添加新条件时你得审查所有东西。变量名、结构——如果你用太多 AABV 变量，你得想象你还得让 agent 来处理这些。

安全性是另一个方面——如果你写了一堆代码但没检查安全考虑，代码不可防御，你不能期望它通过代码审查。可解释性也是重要方面。

关于可维护性是否容易评估——有工具可以做。MIT 有相关研究，我的 HBS 教授正在与一家创业公司合作，他们在这个领域做了 10 年，成功地为美国政府估算圈复杂度和代码质量。

因为我们有图数据库能计算代码之间的关系、理解每一行代码在做什么，我们能构建算法来估算复杂度。可以用 AI 检测文档中的空白——让代码更容易被人类理解。Claude Code 现在甚至能检测出人类和工具多年来遗漏的漏洞。

所以我们整合了这些东西：交付的代码是可维护的、有良好文档的、通过了所有安全检查。这些才是企业真正想让我们解决的有价值的问题。

失败的早期信号 [57:12]

Sam：不是所有产出都成功的。你能识别出这个过程中最早的具体信号——预示部署或产品会成功还是失败吗？

Sudant：有趣的是，客户通常拿到我们的输出后，接上 AI，让 AI 来评估。

我们可以用客户使用的同样模型，我们知道它们怎么思考，可以在交付前就对自己的代码运行它们。我们已经知道客户从 agent action plan 或 spec 中表达的意图，可以预先阻止反馈循环。

怎么做：我们在思考过程中设置检查点。比如我要实现 20 个功能，在某个点我应该完成了 4 个，这 4 个是可测试的，我应该能审查我的工作确保与 agent action plan 一致、没有偏移。

让所有 agent 暂停，引入审查 agent，审查代码，处理差距，分类风险（critical、major、minor），然后继续。QA 也一样——停止开发、测试所有东西、修复差距、然后前进。

这给你的能力是防止问题在代码库中放大。你有一个被 50 个其他文件使用的 models 文件，你搞砸了接口，现在要去改所有那些文件——这些是你不想犯的错误，因为更新那些文件时你会发现级联问题。

人类因素与变革心态 [01:00:02]

Sam：人类在被要求接受之前、在写完 spec 之后，以什么方式在循环中？开发者的怀疑、对控制的担忧——不同开发者的 prompt 或 spec 写法会产生截然不同的结果吗？

Sudant：我们试图抽象和标准化这一点。在我们的情况下，你可以去五个不同的 agent 工具构建 spec 然后来找我们，但我们会用我们称为 agent action plan 的东西重写它——你可以编辑。我们为整个工作中每个 agent 写的规则也是标准化的。我们看 prompting 指南，让 agent 写指令。这帮助标准化结果。

相比之下，如果企业有 10,000 个开发者，不是每个人都知道怎么 prompt 或有效使用工具。你会看到巨大的结果差异。比如 copilot 有时会损害资深工程师的生产力——这不意味着 copilot 是坏工具，可能是那些工程师不需要用它，或者没有正确 prompt。

我们的客户在做的是：从 JIRA ticket 复制粘贴（或者我们直接集成 JIRA），给它 spec，点击执行，拿回结果。不需要考虑 prompt engineering，不需要担心跟上最新模型和工具的细微差别。

关于人类在循环中：如果你围绕人类设计系统、有人类在循环中，那把人类从循环中移除就极其困难。Claude Code 或 Codex 被设计为给人类快速反馈——如果我问一个问题要等六分钟才得到回复，那非常令人沮丧。它经常被说成"你可以散个步回来"，但那不是我想要的。

但自主性是关于解决问题——思考一会儿、考虑边缘情况、然后给出最终答案。这两者互相对抗。当你只为自主性或只为即时响应设计系统时，系统不会与自己斗争，你获得自然的效率提升。

关于变革心态：我根本性地相信，总会有一类任务和软件可以完全 spec 出来——你已经知道正确答案是什么样的。"我只想升级 Java 版本"、"我想从 Angular 切换到 React"、"我想实现这个新功能，产品经理 spec 已经写好了"。自主开发在这个空间会根本性地胜出——你不需要来回沟通，点按钮就能拿到已经验证过的结果。

但总会有另一类任务是极度研究密集的、有未知数的。在那些情况下，你需要与智能 agent 一对一协作。

风险管理 [01:05:07]

Sam：企业看到你给他们一个巨大的代码库要部署到生产环境，但他们不真正理解它因为不是他们写的。你怎么处理这种风险担忧？

Sudant：这是共同责任。企业需要感受到痛点——比如"这是 COBOL，写这些代码的开发者都退休了"。或者是关于速度——我们能实现 5 倍加速。不是 40% 或 50% 的生产力提升，是 5 倍。18 个月的工作变成 3-4 个月。对企业来说，这是赢得市场还是错失机会的区别。

我们做的事来缓解风险： 1. 自动文档化：Blitzi 总是自动为代码库创建文档（我们叫 tech spec），并随着使用保持更新 2. 可对话：你可以与 Blitzi 聊天，理解做了什么变更，要求文档化变更、添加有用注释、做代码审查 3. 测试：客户经常从写测试开始——能给他们信心的测试，证明代码在做他们期望的事

在快速演进的技术上构建 [01:07:58]

Sam：你怎么在底层技术演进如此快的环境中构建技术？怎么适应新模型发布？

Sudant：我们总是在推所有模型的极限。因为我们在极端场景工作——数百万行代码库——每次新模型比前一版好 2 倍，在 Blitzi 中实际上好 10 倍，因为你已经在推极限。它解锁新能力——我们从静态 agent 人格变成了动态的。

我们与实验室紧密合作。即使实验室在同一空间，思维方式完全不同——实验室从"如何让用户与 LLM 工作"的角度出发。但事实是没有任何实验室在所有方面都是冠军。有些情况 Opus 失败，有些情况 GPT 失败，Gemini 也一样。

真正的价值在于能让 Opus 对抗 GPT，取两者之长。 拿一个 bug，看两个模型怎么想，选最合适的。客户做的决策是：你愿意每天手动做这些、在多个工具间切换，还是去一个工具搞定所有事、拿到最终最佳版本？

我们用所有模型的混合。即使实验室进入这个空间，它们也只是触及了自主性的表面。我们在这个空间已经完善了两年多。

自我强化的知识图谱 [01:10:38]

我们真正构建的独特且特别的东西是自我强化的知识图谱（self-reinforcing knowledge graph）。每次你用 Blitzi 构建东西，你的 Blitzi 实例就会为你变得更好。

你可能拿到一个 PR 然后做了修改——我们允许你精炼 PR。如果你遗漏了什么或忘了什么，可以添加，agent 会处理。我们获取信号：你是否接受了 PR、是否做了编辑。当你聊天、问问题、声明规则时，所有这些都用来改进你的实例。

Sam：这不就是在维护记忆文件吗？那是你需要在上下文中管理的另一个东西。

Sudant：其他人确实在用基于文本的记忆，维护在某处。但这正是重点——因为我们有知识图谱，我们不需要维护文件。我们不需要代码中的 agents.md。它在图数据库中。

比如你对一个 PR 的反馈是"用这种方式组织函数"或"用这种变量命名约定"。因为图数据库有关系，你有模块、文件、文件内容。你得到反馈，它是关于这个项目、这个模块、这个文件的。你只需要判断用户的反馈是关于这个特定工作实例，还是关于这个 repo 整体，还是用户偏好。

反馈可以作为一个实体存在于图中，靠近它所引用的东西。关键区别：在基于文本的世界中，反馈总是被注入 prompt，不管 agent 在做什么。在我们的世界中，它只在与 agent 实际工作的东西相近时才被吸入。这就是全部区别——你不会过载上下文窗口，不会超过有效上下文的阈值。
