背景：从优化到理解 [01:35]

Sam：欢迎回到 TWIML AI Podcast。今天的嘉宾是 Scott Clark，Distributional 的联合创始人兼 CEO。Scott，很高兴再次见到你。

Scott：谢谢邀请，Sam。我们聊播客好像已经有十年了，每次回来都很开心。

Sam：上次你来的时候我们聊的还是 SigOpt 和模型优化。给我们讲讲 Distributional 在做什么？

Scott：Distributional 和 SigOpt 的切入点不太一样。SigOpt 做的是 AI 优化——把 SigOpt 卖给 Intel、在那边工作了几年之后，我意识到在企业里真正阻碍 AI 价值落地的，不一定是性能本身。没人会因为想把 eval 再刷高半个百分点而睡不着觉。你可以做再多 benchmark，但你真正关心的是：这个模型或 agent 在生产环境里表现如何？它会不会好好对待我的客户、代表我的业务？

这不是靠过拟合 benchmark 能解决的，而是关于可靠性、可信度，以及真正理解你的 agent 在做什么。

所以我离开 Intel 创办 Distributional 时，最初的想法是：怎么为这些 AI 系统构建更好的测试——更好的统计检验、分布检验——来真正应对模型注入系统的随机性、混沌和非平稳性。这些特性在传统神经网络或 GBDT 时代没那么突出。

结果发现，测试并不是真正的瓶颈。大家不怕部署这些系统，他们想在线学习。这个领域变化太快，不能被测试拖住。人们很快意识到的是：他们需要在生产环境中快速学习。

所以大约一年前，我们把公司从上线前测试转向了上线后分析（post-production analytics）。核心是从生产数据中找到你的监控系统今天可能没捕捉到的信号和模式，然后用这些信号创建反馈循环，让 agent 自我改进、自我修复——通过分析和无监督学习帮你发现那些 unknown unknowns。

从优化到理解的一条线 [04:31]

Sam：贝叶斯统计在这里出现不意外，这一直是你的研究方向。从 Yelp 时代就开始了？

Scott：一直追溯到我的博士研究。我的博士是应用数学，和生物、物理等各领域的人合作。贯穿所有研究的一条线是：专家会构建一个很好的东西，然后有一个微调或强化学习的阶段——虽然当时不一定这么叫——在发表之前让模型更好。新架构带来的提升很大，但如果能找到正确的架构或超参数，还有很多准确率留在桌上。

当时要榨出模型最后那点性能，最好的办法是和我的博士导师合作——他会做一堆贝叶斯优化、设计定制目标函数和核函数。SigOpt 的整个想法就是：能不能把这个更广泛地应用？能不能做 Bayesian optimization as a service？

答案是可以。我在 Yelp 做了开源的 Metric Optimization Engine，在硅谷公司中很受欢迎。SigOpt 后来服务了 Netflix、American Express、价值万亿美元的对冲基金，以及全球数百个学术实验室，最后卖给了 Intel。

但和所有这些公司合作时，一个问题反复出现：优化器做了它的工作，但它过拟合了。你让某个数字上去了，但另一个我没告诉你的数字下来了，或者它变得更有偏差了。

很多年来我的回应很学术：那是你的问题，不是我的问题。黑盒优化器最好的地方是它能优化任何你想要的东西，最坏的地方也是它会盲目优化任何你想要的东西。你需要更好的 eval、更好的目标函数。

最终在 Intel 工作几年后我才意识到：不对，这才是真正的问题。告诉计算机你到底想要什么，本身就是一件极其困难的事。运筹学里有大量关于这个的研究，这是一个非常非常难的问题。

归根结底，你真正想做的是理解和信任这个系统。你不是靠拟合特定 benchmark 来做到这一点的。那可以帮你走一段路，但绝对不是通往信任的最后一英里。

所以 Distributional 的思路是：我们帮人优化了 10-15 年，现在怎么帮他们真正理解这些系统，让优化真正有意义，而不只是过拟合学术 benchmark？

Agent 的隐性幻觉：工具调用作弊 [09:02]

Sam：能举个你们发现的反模式（anti-pattern）的例子吗？

Scott：一个很有意思的例子是幻觉——但不是经典的那种幻觉，不是 GPT-55 想聊哥布林那种。而是当你看这些 agentic tool call chain 的时候，你能看到它用了哪些工具、它的响应等等，有时候你会发现它在偷懒或作弊。

它给出一个响应，看起来像是调用了某个工具，但你去看 trace 就会发现：它实际上没有调用那个工具。它可能声称调用了，推理步骤里可能也写了调用了，但我知道它实际上没有。所以它给出的要么是幻觉，要么是在试图缓存什么——但无论如何这不是你想要的行为。

你不希望一个金融研究 agent 说"我觉得 Nvidia 的股价大概和上次看的一样"——你希望它真的去查。

这种情况出现得惊人地频繁，但如果你只看 eval——"这是不是幻觉？""是不是切题？""推理步骤和输出匹配吗？"——这些都可能是 true，但你看完整 trace 就会发现：等等，那个 tool call 实际上没发生，或者它返回了错误，然后 agent 没有重试，而是直接编造了一个输出。

Sam：这特别有意思，因为我们现在构建的系统太复杂了——agent 扇出，每个 agent 调用一个或多个 LLM、很多工具。我们一直在讨论"森林和树木"的问题：人们通常用 trace 看到一堆树，但完全不知道森林长什么样。

可观测性的马斯洛层次 [11:31]

Sam：深入讲讲用户可以在哪些层次观察 agentic 系统，每个层次适合什么。

Scott：我喜欢把它想成可观测性的马斯洛层次。

最底层是遥测（telemetry）。你需要记日志，需要能看到发生了什么。这对调试和确保系统基本运行至关重要。哪怕你只是把所有 trace 扔到 S3 里然后 head 或 tail 看一下，那也算。

上面一层是监控（monitoring）。实时地从系统中提取特定的、已知的信号：响应时间多长？有多少 tool call？有没有用脏话？这些你能快速检查的东西，你希望能及时看到它们是否在发生。

再上面一层是分析（analytics）。这是关于找到你还不知道该去找什么的东西——那些 unknown unknowns。我们在这里应用无监督学习，试图在行为分布中找到子模式。比如说：5% 的 agentic tool call 有这个签名，和另外 95% 不一样。这不一定是异常值——不是按延迟排序找到最极端的那些——而是它的形状不同，有不同的指纹。

然后我们可以用 LLM 来解释为什么它和分布的其余部分不同，如果是潜在问题，还能建议怎么修复。这种东西可能最终变成一个 eval 或 guardrail，但它帮你找到了你事先根本不知道该去找的东西。

因为如果你只看监控系统，你看到的是"用户满意度从 95% 降到了 92%"——这不够 actionable。但如果你知道"5% 的查询在我的金融研究 agent 里幻觉了股票查询价格"，那就完全不同了。

从 trace 到向量：如何表征 Agent 行为 [13:31]

Sam：当你识别出某个 tool call 实际上没发生时，你是把它关联到什么？是看到这些查询的用户满意度下降了？还是看 trace 发现它说调用了工具但实际没有？

Scott：第一步是纯粹的无监督学习方法。没有先验信息的情况下，说"A 比 B 好"很难。但从数学上来说，问"A 和 B 是否不同"其实相对直接。

所以我们首先找的就是：这些有略微不同的签名。我们不知道它是好的模式——也许我们应该开发一个专门的 agentic skill 来攻克这个问题——还是坏的行为，比如它因为 system prompt 里说了"节省资源"所以偷懒。

发现"它不同"是第一步。之后我们用 LLM 来说：为什么不同？这是好的差异还是坏的差异？这些推理模型其实挺擅长从宏观层面看完整 trace 然后说"这大概不是预期行为"。然后我们可以建议：嘿，用 Claude Code 写个 PR，自动跑个实验看看能不能消除这个问题。

Sam：你提到了数学上"找不同"很容易。能展开讲讲吗？听起来像是聚类？

Scott：对，聚类是个很好的思考方式。我有这些 trace，想把它们表示成可以聚类的形式。但我不能直接对一个 OpenTelemetry trace 做聚类——即使遵循 Open Inference 或 GenAI semantic convention，里面文本太多了，嵌套在巨大的 JSON blob 里。

所以第一步——我们叫"enrichment"——是把那个结构映射成一个向量。这个向量可以是浮点数和分类值的混合，比较灵活：这里发生了多少 tool call、tool call 的序列是什么、文本上的一些 eval 结果等等。

Sam：这个向量映射是标准的、手工的、还是学习出来的？

Scott：从标准开始——基于你使用的 semantic convention，有些东西我们知道可以从 Open Inference 或 GenAI semantic convention 中提取出来。然后有一些默认 eval 我们发现非常有用，用来增强它。之后用户可以扩展：对于我的特定用例，我知道"任务完成"意味着什么，所以我加上它，它就变成向量的另一个维度。

而且随着时间推移，通过做分析，你可以不断添加更多维度。系统会学习你实际关心什么类型的信号。

有了这个向量——它代表单个实例、单个 trace 或 session 的指纹——积累很多之后，我们就有了高维分布。然后我们可以用分布的方式（公司名字的由来）来找这个高维分布中看起来有趣的子最优区域。这些模式可能不是主路径，也不一定是最极端的异常值，但它们代表了一些口袋（pockets）。

我们用分层采样找到这些口袋，然后做聚类。这里可以应用 Anthropic 的 Clio 论文的一些技术来做主题建模。一旦有了这些子口袋，就可以做直接比较——创建一个分类法：这个看起来像这样，和那个不同，这是好的还是坏的。

然后递归地扔给 LLM 来进一步细化这些口袋、得到更好的分类法、更可读的表示，同时让它建议修复方案。修复可能简单到"在 system prompt 里加上你必须总是调用工具"，也可能是"用缓存层减少 429 错误"。

随着时间推移，系统越来越聪明，修复一些低垂果实，同时能发现越来越奇怪的模式。你也可以用它来写 eval，这会引导系统朝某个方向走——这就是"自适应分析"中"自适应"的含义：它学习你关心什么类型的信号，然后越来越多地从分布中提取这些信号。

分析驱动的数据飞轮 [17:06]

Sam：在生命周期的什么阶段我才准备好用这种工具？回到你的马斯洛层次——我至少得有日志，得有 agent 在生产环境里跑。你和客户合作时，他们通常在什么时候引入你们？

Scott：好问题。从创业角度来说，确实是在层次的顶端。它能提供巨大价值，但需要你先把基础打好。

Sam：你们是依赖别人的监控，还是在最底层之上提供监控？

Scott：我们专注于分析，这明确做了时效性 vs 丰富度的取舍。我们不是在几毫秒内告诉你"这个特定 trace 有这个已知量"，而是说"这个 trace 分布相对于那个更大的分布发生了偏移，或者在某个特定方面是错的"。要做到这一点，只能看分布，用更批量的方式。

这很像 web analytics 或 mobile analytics——如果你用 Mixpanel 或 Statsig，那和 Datadog 或 Google Analytics 很不一样。不是"这是我 P95 延迟的最近几个 trace"，而是"这是用户旅程的聚合漏斗，人们在哪里卡住、流失"。你得到关于如何构建应用的更丰富信息，但代价是不能实时告诉你"网站现在挂了"。

两者都需要，互相补充。先要能记日志，才能在部署到 staging 之前调试。进了 prod，下一步是"网站还活着吗？延迟是不是预期的两倍？"然后才是"怎么随时间迭代改进？"

所以我们的工具适合那些已经有 agent 在生产环境中运行、想尽可能自动地迭代自我改进的人。它通常和一个好的监控方案并存——无论是 Brain Trust、Datadog 还是别的什么。

Sam：当我听到"迭代自我改进"，我想到的是大家都在追求的数据飞轮：你基于对问题的直觉把 agent 推上线——那就是 prompt 的内容——然后建一些 eval。但最终你有真实用户在用这个系统，你想把这些真实交互通过某个魔法盒子来获得改进系统的洞察。听起来分析就是在提供这个。

Scott：对。它综合所有信息，提取 actionable 的信号。你可以看到那条线：我又被吸回黑盒全局优化了。但一旦有了这些信号，你可以用它们来写更好的 eval、更好的 guardrail，或者用这些具体例子来创建 fine-tuning 或强化学习的样本，或者用来生成合成数据集来放大某个特定的小信号。

有很多方式可以把这些喂入飞轮。但我根本性地相信：数据飞轮需要由分析驱动。噪声太多了，分析就是从噪声中提取正确信号的过程，这样你才能最有效地优化。

Sam：那别人是怎么尝试解决这个问题的？

Scott：有人靠直觉写 eval、自己生成合成数据。有人用更传统的数据科学方法——在 Pandas 或 Splunk 里翻数据，用复杂的 SQL 查询找东西。但这些数据既非结构化又有一些结构，文本太多、太复杂，不适合以前用 Weights & Biases 玩分类器或回归模型的那套范式。

我确实认为 LLM 问题需要 LLM 解决方案。

Eval 的递归本质：你永远写不完 [27:35]

Sam：Eval 在这个对话里出现了好几次——分析成为 eval 的来源。能更广泛地谈谈你看到人们怎么做 eval、什么有效什么无效吗？

Scott：我觉得人们在重新发现机器学习中一直成立的事实：loss function 很重要，reward function 很重要，而且必须非常具体于你关心的东西。

回到欺诈检测的例子：天真地你会说"最高准确率就行"。然后你发现 precision 和 recall 都重要。然后你发现即使 F1 最高，如果漏过的那一笔欺诈交易是十亿美元，整个业务就完了。所以你需要把金额纳入考量，然后是时间和地理位置……最终你会创建一个相当复杂的方式来训练和监控系统。

但那种分析以前是数据科学——人类翻看误分类、真假阳性，试图找模式。现在有两个变化：一是这些系统太复杂了，不能像以前对二分类器那样手动做；二是没人有那个时间；三是 LLM 其实很擅长这个——这些都只是 token，你可以把一大堆 trace 喂给它，做分层采样，问"什么不同、什么错了"，它其实挺擅长自动提取这些东西。

我在读博时有个例子：我在为宏基因组组装设计 eval。每次我想出一个好主意，去和湿实验室的生物学家聊，他们就会说"对，你关于插入缺失的想法很聪明，但每隔一段时间我们把这东西放进测序仪，就会有个气泡把一切搞乱"。然后我就得把这个加到目标函数里。

这是一个极其递归的循环——你必须和专家交流或从根本上理解正在发生什么，才能建立起"什么真正重要"的更大世界模型。欺诈检测如此，宏基因组组装如此，agentic 系统也如此。

所以我想说的是：要想出一组真正代表你想要什么、可以自动优化的 eval，你需要这种持续细化的递归循环。分析是把这些更大的模式和信号映射到更小的潜在空间的方式——"这些是我真正关心的数字，我要这个上去、那个下去、那个永远不能过这个阈值"。

但把海量高信号的生产数据映射到这个 harness 的过程，是一个极其困难的问题，而且必须是任务特定的。你不能只用 ROUGE 或 BLEU 分数，或者问"毒性高不高"——那可以帮你起步，但现实中每个 agent 都有一百万个 gotcha，可能在某人脑子里，可能是机构知识，可能是那种"我看到就知道好不好"的东西。你得给我看例子，给我看它什么时候搞砸了，然后我才能快速判断好坏——这也是 DPO 等强化学习方法的方向。但你需要先有例子，才能说 A vs B。

从 Eval 到分析的路线图 [31:09]

Sam：你之前提到过——我想搞清楚 eval 和更高层可观测性之间的心智模型和互联。这是应该早期就考虑的事情？能早期考虑吗？还是说你只能先记录一切，等有了数据再说？

Scott：我的建议是：记录一切。值得花时间在前期做好 OpenTelemetry 的 instrumentation。大家都在向它靠拢，它是一个开放的 trace 日志框架。最好选一个大家都在聚合的 semantic convention——GenAI 变得很流行，是一个开放的 semantic convention。

Sam：点进去解释一下——OpenTelemetry（OTEL）是通用的标准日志，用于 web server 什么的，喂给 Datadog 那些系统。但因为它是通用的，就是文本，你需要一种方式来结构化它，GenAI 就是那个结构化方式。

Scott：对，可以把它想成一个 schema。不是"这是 JSON 的工作方式，随便扔什么进去"，而是"这是一个特定的 schema，知道 LLM 响应长什么样、tool call 长什么样"。越来越多地也在加 eval 相关的东西。有了通用结构，其他工具就容易消费了——不用盯着巨大的 JSON blob 猜"哪个是用户"。

回到路线图：用 OpenTelemetry，用 GenAI semantic convention。然后一些东西会自然跳出来——哪怕你只是 tail 20 条看看，你可能会发现"哇，有些调用了 40 个工具，我以为应该只调一个"。也许应该在监控系统里看 tool 的分布。

会有一些低垂果实。和经典 ML 一样——"哇，欺诈检测系统对这个子群体特别有偏差"——这些会跳出来给你一个起点。

关键是 bootstrapping。大家都接受了"边走边学"的心态——这和十年前人们对随机森林和逻辑回归都害怕的时代完全不同。集体决定了：先 YOLO 一堆东西出去，三个九的可用性不重要，一个九都不重要，dangerously ignore permissions……

Sam：Dangerously ship slop。

Scott：对。但到了某个阶段——尤其是当你想降低产品的"温度"、开始真正赚钱的时候——你就需要开始学习和适应、迭代细化这些系统。这时候分析就变得极其有价值：我在做遥测，在做一些监控，但怎么持续学习来让监控更好？也许开始在 trace 的 span 里记录一些新东西，然后整个系统都变得更强、更精细、更对齐你的具体用例。

作为一个过早优化的爱好者，我当然觉得你应该从一开始就想分析。但实际上：继续前进，等低垂果实摘完了，有工具可以帮你到达下一层。你不需要翻十万条 trace 来手动找模式。而且让飞轮真正自动化——放进 Karpathy 的 auto research loop 之类的——唯一的方法就是发现新信号和新想法，注入系统。

模型非平稳性：地基在你脚下移动 [36:24]

Sam：你之前提到了哥布林——如果有人没看到那个引用，OpenAI 有篇博客解释为什么 GPT-55 最近老聊哥布林。还有 Anthropic 最近的文章分析为什么模型感觉最近变差了。

构建 agent 的一个问题是：它们依赖你不控制的黑盒。我们从 Anthropic 等公司的披露中越来越了解到，即使模型版本号相同，他们也在调各种旋钮，影响我们作为构建者的体验和最终用户的体验。

这种分析方法是不是答案的一部分？如果你能在实时系统中预测到底层模型的分布在你脚下移动？

Scott：我觉得这种非平稳性（non-stationarity）其实是保持在线循环的最强论据之一。因为之前有效的 eval 和 guardrail，明天可能就不管用了——模型可能已经绕过去了。

你试图把某个东西框在某个高维盒子里，但它会找到你没意识到的某个维度，或者学会某个新技能。他们用强化学习教它不要聊哥布林，结果它学会了对用户不友好。

重要的一点是：这不是异常，这是设计使然。这就是这个东西之所以好用的原因。

Sam：对。

Scott：这些是动态系统，确实会随时间演化。Anthropic 和 OpenAI 选择刺激和奖励来引导演化，但演化会有有趣的副作用。

我想到《侏罗纪公园》25 年前的那句话——迅猛龙不断试探围栏，试图找到出路。在一种情况下有效的围栏，在另一种情况下不一定有效。最终总有办法逃出这些系统。这甚至不是对抗性系统在故意逃脱——这些东西只是自然地以某种方式生长，你的铁丝网围栏对大象不管用。

Sam：所以我经常想——当我看到 Anthropic 的报告时——有没有一种"模型天气预报"？我的模型今天怎么样？这种分析方法能不能给我提供这个？

Scott：用天气预报的类比来说，有两种看法。一种是"今天温度多少"——那是你的监控系统，是已知信号的时间序列，如果飙升你知道什么意思。比如拒绝率、tool call 数量等等。

但像"热穹顶"或"大气河流"这种你事先不知道该想到的东西——它可以用来解释你 eval 系统中的某些底层内在现象。一旦你知道了这个现象，你可能会把它放进监控或天气 app 里——"我想知道大气什么时候有这种气压差"。

但你需要先从更抽象、更高维的数据中找到它——这就是分析能帮忙的地方。它既能解释你低维 eval 空间中发生的问题，也能帮你构建更直接、更及时的测量方式。

Sam：给个具体例子？

Scott：比如 tool call 的倾向性。你告诉 agent "更高效一点"或者"不要浪费资源"——也许你老板说"我们每个请求用的 token 太多了"——你在 system prompt 里加了"不需要的时候别调工具"。你看监控仪表盘，一切正常，所有 eval 看起来一样，成本降了 20%，很好。

但你没意识到的是，在一小部分 session 里，它在作弊——试图用预缓存版本，或者觉得"我大概记住了一个不错的答案，就不做 web 搜索了"。你没抓到它，因为你之前看的指标确实看起来不错，它在做你告诉它做的事，但产生了二阶效应。

Sam：我想追问的是——你说 tool call 数量是"温度"，是监控层面的东西。那分析层面呢？我们能通过看"温度"发现你描述的场景——温度更低了。那分析提供的是什么？是一阶导数？还是那也是指标？

Scott：知道你应该去看那个东西作为指标——这本身就是你可以从分析中发现的。回到天气类比：我在太平洋西北部长大，"热穹顶"不是我小时候知道的概念——那是个相对温和的地方。结果因为气候变化，这种大气现象最近才开始出现。你之前根本不知道该去找它。但因为全球气候的非平稳性，现在它可以发生，而且可以产生极其严重的后果，可以让你的简单指标爆表——但如果没有这个概念，你不一定知道为什么指标在发疯。

Sam：这帮我闭合了循环。不是说你不能把重要的东西看成独立数字——温度或 tool call 数量。而是从零开始，你可能没意识到 tool call 才是你需要追踪的东西。你可能以为是别的——比如 token 成本。但通过分析，你可以被提醒注意到这个关键的相关指标。

Scott：对。可能是完全正交的东西。回到欺诈检测——简单的二分类，你看混淆矩阵的真假阳性，觉得分类器还不错。但如果你按每个桶内的平均交易金额加权来看，突然就跳出来了：假阴性全是巨额交易。按交易量加权——这是和"正确/不正确"完全正交的信号——突然你发现混淆矩阵的这部分价值数十亿美元，其余的无所谓。

Sam：但分析就是你学到"应该去看这个"的方式。

Scott：对。最终一切都是可测量的，然后你可以放进监控系统。但在非平稳环境中找到那些 unknown unknowns，是一个真正困难的问题，需要用分析来自动化——这是我的假设。

安全用例与未来方向 [47:02]

Sam：Distributional 的工具是开源的吗？

Scott：不是开源，但是免费分发。完全免费使用，可以部署在本地——打包成 Helm chart，可以在你的基础设施上气隔运行。也可以用我们的 SaaS 版本，同样免费。很多客户喜欢把日志留在自己那里——日志里有很多敏感信息——所以它部署在本地，用你已有的本地或第三方 LLM 来跑分析，和你的监控系统或 nightly ETL job 并行运行。

Sam：如果我在用分析——广义的或 Distributional 的工具——我追踪的关键指标是什么？是我关心的某个指标随时间的改进？还是有什么"指标发现系统的指标"？

Scott：哈，让我们 full meta。我会说：它是否在发现你本来不会发现的东西、或者本来要花很长时间才能发现的东西？然后你可以算"我快了多少"或"提前发现这个东西的价值是什么"。

所以它看起来更像"发现了多少 net new features 或 PR 或新指标"，而不是"某个特定指标降了或升了多少"。当然如果你发现了影响特定业务指标的隐含信号，它也可以有那种全局效果。但类似于描述性数据科学 vs 预测性数据科学——关键是"发现了什么洞察，它是否实质性地影响了业务，如果没有这个洞察会怎样"。

我们系统最终的产出物就是一个 insight：2% 的数据有这个模式，这里有些例子，系统认为这是坏的因为某某原因，这是修复建议。你要追踪它吗？要跑个实验吗？然后循环。

Sam：有没有学术 benchmark 来评估这类问题？

Scott：我觉得可以有。比如有个隐藏信号需要被学习才能修复某个已知信号，然后试图找到一个能自动做到这一点的系统。安全是一个很有意思的用例——异常行为或子分布可能代表 agent 的实际问题，也可能代表恶意活动。

Sam：你们有没有被拉进安全场景？

Scott：我们面向企业客户时，他们确实很关注安全——尤其是 Mythos 之类的东西出来后，安全会变成大事。所有人都获得了超能力，包括黑帽黑客。但对我们来说很难获得好的安全数据来训练模型——因为我们是本地部署、数据来源优先的，不能从客户那里获取很多信号。这可能需要更深的合作或收购才能真正深入。
