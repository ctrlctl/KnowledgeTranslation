## 快速模式与慢速模式：Batch Size 的经济学 [01:07]

Rainer，也许我们先从这个问题开始。现在有几家公司，比如 Claude、Codex 和 Cursor，提供了类似"快速模式"的东西——花 6 倍的价格，你能以 2.5 倍的速度获得流式 token。我很好奇这背后的机制是什么。为什么花更多钱就能获得更低的延迟？第二，能不能继续往上走？花 100 倍的钱能不能获得更快的速度？第三，能不能反过来？有没有类似"Claude Code 慢速模式"的东西——如果你愿意等上几分钟，就能获得更便宜的价格？

## Roofline 分析框架 [02:09]

我想先介绍分析的两个基本原则。首先，我们要对在芯片集群上运行 transformer 模型做一个 **roofline 分析**。我们取一个，比如说，Blackwell NVL72 集群——也就是一个包含 72 块 GPU 的机架。Roofline 分析的意思是我们看内存带宽和计算性能。

然后另一方面，我们只看模型的两个简单因素：处理权重的时间，和处理上下文（KV cache）的时间。

---

## 推理时间的下界估算 [02:45]

我们要尝试估算运行某种形状的推理所需的时间。我们不能精确预测时间，所以我们要做近似。我们会说时间必须大于等于某个量。我们考虑两个方面：做内存读取所需的时间，和做计算所需的时间。事实证明，即使用这么简单的模型，也能给我们非常强的预测能力。

**计算时间**方面，我需要做两件事：乘以所有活跃参数，然后做一些 attention 的工作。

乘以所有活跃参数：我有一个 batch size，然后有模型中的活跃参数数量，再除以计算吞吐量（芯片的 FLOPS）。这实际上涵盖了所有权重矩阵乘法的计算时间。有个小注意点：我们忽略了 attention 计算的时间，但一般来说它相比之下会很小。

插一句给观众解释一下——你不是一次只服务一个用户。Batch 指的是你同时服务很多不同的用户，那就是一整个 batch。

对。我可以稍微解释一下为什么 batch 是这么有利的优化。结论是：如果你不把很多用户 batch 在一起，你得到的成本和经济性可能比 batch 在一起差一千倍。我们会很明确地看到这一点。

然后是活跃参数数量。比如看 DeepSeek 模型，DeepSeek v3 有大约 370 亿活跃参数和 7000 亿总参数。我们关注的只是对单个 token 活跃的那些参数。

---

## 内存时间：权重读取与 KV Cache [05:08]

在内存方面，我们需要做什么？我们需要读取所有权重。所以有一个读取所有总参数（不只是活跃参数）的时间——这是**权重读取时间**。

然后还有 **KV cache 读取时间**。这实际上取决于 batch size。对于 batch 中的每个元素，我们必须读取整个上下文长度的 token，每个 token 有一定的字节大小。

让我快速解释一下 KV cache 是什么。当我做一次前向传播时——让我画一下自回归推理是怎么工作的。在 decode 阶段，我有一堆文本 token，我在增长一个张量，因为最终 token 被表示为某个 embedding 维度的张量。在另一个方向上，我有序列长度。

运行一次 decode 的工作是：我必须把每个 token 通过一大堆矩阵乘法，跨越很多不同的层。一般来说，我需要对所有这些 token 做这些工作。

但一步 decode 实际上只是在这里产生一个额外的 token。所以我要做的是：对整个模型中所有的权重矩阵运行一次完整的前向传播。但然后我有这个 attention 机制，这个 token 在"看"所有过去的 token。它具体在看什么？它在看模型对这些 token 产生的某种内部表示。我们把它叫做 **KV cache**。

所以这个过程——单个 token attend 到所有历史 token——就是 attention。它主要由内存读取主导，而不是矩阵乘法。我们把要读取的内存量写在这里，然后除以内存带宽（每秒字节数）。

我们说过最大的效应是 batch size 中延迟与成本的权衡。让我们画出来。我觉得我们真正需要画两张图。先画 batch size 对时间的关系。

**内存方面**：有一部分是常数——权重读取，这是一个基础偏移。然后还有 KV cache 读取，它是 batch size 的线性函数。

## 延迟下界的含义 [09:53]

这是什么意思？这是一个延迟图。如果我增大 batch size，一开始对 batch size 的依赖不是很强。所以这里有一个**延迟下界**。

这已经部分回答了问题。对于给定的硬件配置（我们可以讨论改变硬件配置），存在一个延迟下界，它就是：我需要把所有总参数从内存读入芯片，这需要一定的时间。如果我用尽了所有内存带宽，我没法做得更快。
## Compute Bound vs Memory Bound 的转换 [10:39]

看起来按你画的方式，你没法做得比那更好了。看起来按你画的计算时间斜率和 KV 增长的方式，以及 KV 对内存时间的影响——随着 batch size 增长……如果这条线在上面或下面呢？

对，或者说这是不是必然的？因为如果这总是成立的，那随着 batch size 增长，计算总是主导 KV，这意味着如果你有足够大的 batch size，内存可能永远不是问题。

对，这对上下文长度非常敏感。我觉得我们应该回来探讨这个。当你增大上下文长度时，KV 读取时间会越来越大，这会导致从 compute limited 到 memory limited 的转变。

斜率恰好等于计算时间的斜率，这有什么特别的意义吗？

对，每当我们有平衡点时，它意味着你恰好做对了。对于斜率匹配的那个特定上下文长度，它说明我同时受内存和计算约束——这是一个非常理想的位置。

这是一个很简单的代数问题，但假设最优是 100K 上下文长度，你用了 200K 上下文长度，你的 MFU 会降到 50% 吗？稍微偏离最优上下文长度范围（Goldilocks zone）对 MFU 的影响是不是巨大的？

没错。按这里的模型确实如此。但有一个关键点：我把内存读取建模为上下文长度的线性函数。这实际上取决于模型架构。对于所有使用 dense attention 的模型架构确实如此。但 **sparse attention** 的扩展性比这好得多。

sparse attention 是不是大家实际都在用的？

我对 sparse attention 很兴奋。很难知道各实验室在用什么。DeepSeek 发表了一种 sparse attention 机制。我插一句，DeepSeek 发表的一些 sparse attention 论文最终在这一项里放了一个平方根。

## 从延迟到成本：Cost per Token [12:54]

到目前为止我们看的是延迟。从这里读出成本有点难。那成本是什么意思？运行这次推理，我要用 GPU 一定的秒数——比如 1 毫秒或 20 毫秒。我得为那段时间付租金。比如每 GPU 每小时 2 美元之类的。

所以那就是这次推理的成本，但在这次推理中我处理了多少价值、多少 token？那就是 batch size。我们实际想画的是 **cost per token**（每 token 成本）对 batch size 的关系，也就是 T/B 对 batch size。

我们要想象把这三条曲线都除以 B。所以最终：计算曲线原来是线性的，除以 B 变成常数。KV 读取原来是线性的，现在也变成常数。权重读取原来是常数，除以 B 变成双曲线。

然后我们计算最大值。KV 读取和权重读取的和给我们一条更高的双曲线。然后我们取它和计算的最大值。最终得到的就是我们关心的整体形状。

---

## 成本的极限行为 [15:01]

我们看到一些极限行为。成本在 batch size 为 1 时开始非常高，几乎趋向无穷——因为我们有那么多权重读取，没有被大 batch size 摊销。但随着 batch size 增大，权重读取被摊销到很多不同的 batch 元素上，它们的成本变得很小。最终计算时间驱动了成本。所以存在一个**成本下界**。

所以 Claude Code 慢速模式或 Codex 慢速模式就会在这条线上。而且帮助不大，因为你没法把 KV 值摊销到更大的 batch 上。

对，它们是每个 batch 独有的。计算也是每个 batch 独有的。所以在摊销掉其他一切之后，每个 batch 你能做的最小工作量是多少。

---

## 求解平衡点：最优 Batch Size [16:11]

那么你不再受内存带宽约束的那个点，需要多大的 batch？实际上前沿模型的 batch 有多大？

你实际上可以直接求解。而且它对模型架构甚至不是特别敏感。让我们来做。我们要说的是：当内存时间等于计算时间。现在我先忽略 KV cache，因为我们关注的是 batch size 是多少。真正的问题是权重何时被摊销到乘法上。我把权重读取时间和权重乘法时间做比较。

写出来就是：总参数数 / 内存带宽 = batch size × 活跃参数数 / 计算性能。

看这里，上面的都是模型参数，下面的都是硬件参数。把硬件参数放到一边比较好。这等价于：

**计算性能 / 内存带宽 = batch size × 活跃参数数 / 总参数数**

左边是硬件参数。右边实际上是一个无量纲常数。看维度：FLOPS 是每秒乘法次数，内存带宽是每秒字节数。不完全是无量纲的。但如果你说——比如我用 FP4——每秒多少次 FP4 乘法，乘以每个 FP4 是半个字节。这样就能变成无量纲的。在大多数 GPU 上，这个值大约是 **300**。

这个比率随着 GPU 代际变化了吗？从 A100 到 B100，FLOPS 大幅增加了，内存带宽也大幅增加了。它保持得相当稳定。

我们也可以表达另一边。这是一个稀疏度参数。让我们求解总的 batch size。最终得到：

**batch size 需要大于约 300 × 稀疏度**

比如 DeepSeek，它从 256 个 expert 中激活 32 个，所以稀疏度大约是 8。

好的。这实际上给你一个大致估计，跟实践惊人地准确。一般来说人们会比这稍大一点。他们不想恰好在平衡点上，因为现实世界的效率不如 roofline 分析说的那么好。但取这个值然后翻倍或三倍。所以基本上是每 batch 两到三千个 token。

但如果你加入 KV cache，含义是最优 batch size 应该更大。这很好。我们求解了计算时间等于内存时间的等价点。如果我加入更多消耗内存带宽的东西，那可用于权重加载的就更少了，所以我需要增大 batch size。

这看起来小得不可思议。一个 batch——这不到一个序列吧？对。记住我说的是我要为之多生成一个 token 的 token 数量。所以实际上是两千个独立序列。我们只是在说对这些序列的一次前向传播。你把 batch 想成序列数量而不是……？没错。

## 插播：Jane Street 的 FPGA 与低延迟交易 [20:53]

我准备采访时经常跟领域专家聊。对于 Rainer 这期，我跟 Jane Street 的两位工程师 Clark 和 Axel 聊了。Clark 做低延迟交易系统，他给我讲了为什么 Jane Street 用 FPGA 来确保可预测的纳秒级延迟。

你可以很容易地构建这些巨大的计算网格，精确地做你需要的事——访问一百兆字节的 SRAM，然后在几十纳秒内得到响应。这在 CPU 上基本不可能。

他接着解释了为什么 CPU 不适合这种事情。如果你的时钟每三纳秒跳一次，你实际上每次有几个字节的信息来做决策。相比之下，CPU 会收集整个数据包——比如一个 1500 字节的包——然后说"好了，这个包准备好了，给你 CPU，你现在可以开始想了。"FPGA 允许你在数据包最早的部分到达时就做出反应，而不用等整个包。

我们还聊了液冷、网络设计和很多其他东西。

思考这个问题的方式是——我把它想成"火车什么时候发车"的模型。假设我选了一个要运行的 batch size。这个交叉点跟那边是同一个交叉点。我选了这个 batch size。我知道它大概需要——比如 20 毫秒是一个常见的落点。

## 20 毫秒从何而来：HBM 容量与带宽 [23:40]

20 毫秒是怎么来的？经验法则。但它的来源还没完全解释——到目前为止我们关注的是内存带宽和计算时间。看内存时，另一个考虑是我们想用完所有的内存容量。一般来说我们会用所有内存容量来存储权重或 KV cache。所以我们只想在一次前向传播的时间内读完所有内存容量。

所以就是**容量除以带宽**。在很多代 HBM 上这往往是 20 毫秒。单位说得通：字节除以每秒字节数。比如在 Rubin 这一代，大约是 288 GB 除以 20 TB/s，算出来大约 15 毫秒。

有两种场景。为什么我们不选一个大于 15 毫秒的延迟？如果我想想那意味着什么——意味着我实际上有时间读 HBM 两次。顺便说一下，大部分 HBM 访问是读而不是写。几乎全是读，因为权重矩阵是只读的。然后几乎所有 KV cache 访问也是读。所以在大约 30 毫秒内，我可以读完所有 HBM 两次。但那有什么意义？我不想读权重矩阵两次。我不想读 KV 两次。对，说得通。

## 最优 Batch Size 只取决于稀疏度 [25:49]

几个快速问题。如果最优 batch size 大约是 2000，而且确实如此——它完全取决于稀疏度。不取决于模型大小或其他任何东西。稀疏度出现在模型大小中，但除此之外，它只取决于稀疏度，不取决于规模。这是一个非常有趣的结果。

这似乎暗示……一个问题是：推理的规模经济在多大程度上是一种中心化的力量？但看起来不是什么大事。2000 个同时在线用户算多吗？看起来不算多。

我们可以做一点分析。你可以用用户数来想，但更有效的方式是用每秒 token 数来想。这个 batch size 意味着系统每秒多少 token？

**每秒 token 数 = batch size / T**

T 就是那个 15-20 毫秒的数字。所以最终是 batch size × 大约 64。也就是大约 2000 × 64 = **128K tokens/秒**。

这是更容易理解的单位。很难推理并发用户数，但系统的全球流量是多少？看一些公告，有时 API 提供商会炫耀他们有多少流量。我记得去年 Gemini 的一些公告是全球每秒数亿 token。所以这大约是 Gemini 的千分之一。但 Gemini 很大。所以千分之一的 Gemini 实际上很多。要在规模上有竞争力，你至少需要能服务 Gemini 的千分之一。

## 稀疏度的权衡：质量 vs 效率 [28:07]

稀疏度越高，需要的计算越少。而且看起来随着 batch size 变大，计算最终成为瓶颈。那问题是：稀疏度能走多远？也就是说，随着稀疏度比率增加、活跃参数相对于总参数越来越少，模型性能下降了多少？下降速度是否快于你通过增加稀疏度节省的计算？

对，性能指的是模型质量，而不是模型速度。不幸的是，我们没法用分析方法回答这个问题。这是一个关于模型质量的经验问题。我能做的最好的事是拉出一篇论文来经验性地回答。

这篇论文是 **Unified Laws for Routed Language Models**。到现在算是比较老的论文了，但他们做的一件事是看：如果我持续增加稀疏度，模型质量的影响是什么？这个答案对 MoE 的具体选择非常敏感。MoE 已经存在很长时间了，可能早在 2017 年。但技术变化很大。DeepSeek 的 MoE 是工作方式的一个大变化。还有更早的论文如 G-Shard、Switch Transformer。

但在这里展示的一种较老技术上，你可以看到：如果我保持活跃参数数量不变，然后增加稀疏度（他们这里叫 expert count），质量持续提升。如果你想象从 1.3B dense 画一条水平线，你会看到比如 64 expert、370M 活跃参数的模型跟 dense 1.3B 模型一样好。

所以某种意义上，回报其实不算惊人——你需要把总参数增加百倍才能获得相当于 10 倍活跃参数的效果。实际上更甚。这是一个巨大的参数量增加换来适度的提升。在这个案例中，是 64 倍换 4 倍。

所以虽然确实你能通过增加稀疏度来节省计算时间，天真地看似乎这是值得做的权衡。但如果你每次把稀疏度翻倍，这边减少 2 倍，那边增加 8 倍……

从内存角度看，记住你在把内存读取的这部分翻倍——但它被 batch 摊销了。所以只要跑更大的 batch size。从我们这里做的分析来看，**这是纯赢**。继续做。继续做直到你用完可用用户。

所以实际上有这样一个等价关系：如果我想走稀疏路线，或者如果我有很多用户，我可以用一个更稀疏的模型。从这个角度看，这是合理的权衡。另一个出现的权衡是它也消耗内存容量——而我们只推理了内存带宽。

让我确认理解。你是说我们想花更少时间计算，所以做更多稀疏。要让这工作，我们需要更大的 batch size，意味着我们需要更多内存容量。对。

## 机架内 vs 机架间：Scale Up vs Scale Out [36:03]

这种 all-to-all 通信模式跟 Blackwell 机架的配置方式是完美匹配的。

但如果你觉得一个机架太慢，想用两个机架，那就有挑战了——也许我在外面画了某种机架边界。我不再拥有两个机架中所有 GPU 之间的 all-to-all 通信。**机架间通信最终成为一个重大瓶颈。**

所以根本问题是：一个机架实际上限定了你能做的 expert 层的大小。这也是推动越来越大互连域的部分原因。

也许值得解释一下机架到底是什么，机架内和机架间的带宽差异，以及通信的 all-to-all 与非 all-to-all 性质。

这个地方在 Nvidia、Google 和其他公司（包括我们）之间确实非常不同。一般来说，机架是一个物理结构。几米高，一两米宽，取决于配置。它存储大约 64 块 GPU 或 XPU。限制它大小的是供电、重量和散热能力。由于这些物理约束，它在很多情况下就是这个大小。

部署数据中心时，一个数据中心可能有数千个这样的机架。一个高高的机架，里面一堆 GPU，然后再放一个机架。你说得好像很容易似的。对，直接放进去。

在 Nvidia 的情况下，通信拓扑是——他们把 GPU 放在机架外侧，然后把交换机放在机架内侧。里面有一组交换机，就是 **NV Switch**。然后他们跑一堆线缆。每块 GPU 都有线缆连到中间的交换机。所以所有 GPU 连接到所有其他 GPU 只需两跳——到交换机，再到另一块 GPU。

当我想离开机架时，走的是另一条路径。GPU 还有一个慢得多的连接，通常慢大约 **8 倍**。

我画的绿色在 GPU 情况下是 NVLink。更一般地叫 **scale up 网络**。你通常还有一个 **scale out 网络**，允许你连接到某个数据中心交换机。所有 GPU 都有某种连接到某个数据中心交换机。但 scale out 的带宽通常慢大约 8 倍。

## 跨机架 MoE 的瓶颈 [39:50]

挑战在于：如果你想把 MoE 层布局在两个机架上，这边一半的 GPU 会想跟那边的 GPU 通信。平均来看，当我看这些 GPU 上的 token 想去哪里——一半 token 想留在机架内，很好，它们可以用快速的 scale up 网络。但另一半 token 想离开机架去另一个机架。那就不太好了。它们需要用慢得多的网络。这就成了 all-to-all 模式的瓶颈。

另一个选择是：为什么不搞一个大交换机，把两个机架连在一起？这个方向有很多想法，但一般来说，你有这种交换机层级而不是一个大交换机的原因是为了管理布线拥塞。你就是需要跑大量的线缆。

这基本上就是在问：为什么不搞更大的 scale up？为什么不直接一百万块芯片全 scale up？

从 Hopper 到 Blackwell 再到 Rubin，是什么让规模从 8 到 72 再到 500 多成为可能？

从 Hopper 到 Blackwell 主要是决定从 tray 作为形态因子切换到 rack 作为形态因子。这是一个产品决策。没有实质性的技术障碍。

从 64 到 500 左右，有一些数学上的巧合，但至少有真正的 4 倍增长，来自更复杂、更困难的机架设计——实际上是新的物理设计来跑更多线缆。

最大的好处——在推理中有一些好处，在训练中可能好处更大。在推理中，我们在节省什么？内存时间还是计算时间？都不是——我们只是把内存时间从一块芯片移到另一块芯片，或从一个机架移到另一个机架。运行时间没有实际好处。

但我们节省的是**每个机架使用的内存容量**。如果我们认为机架中的内存是瓶颈，那就有一个速度上限。Pipeline 允许我们大幅减少这个瓶颈。

反面的含义是——在这次采访前我跟 Jane Street 的 GPU 性能工程师 Axel 聊过——他解释说，做 pipeline 你必须用 micro batch 而不是完整 batch。如果你用 micro batch，那你定义上就没法把加载权重的成本摊销到所有用户或所有序列上。

正面含义是你不需要用那么多内存。负面含义是我们没法把加载权重摊销到所有那些用户上。

## 训练中的 Pipeline：前向与反向 [58:54]

让我们画训练的图。这是推理图，我标记为 4。现在对训练做同样的事。我们有前向传播，但在某个阶段，我们要转换到反向传播。所以我们在前向传播中做若干个 batch，然后一次性把所有人转换到反向传播。

推理部分是一样的，但然后我们在这个点硬停，然后把所有人转换到反向传播。

值得澄清的是，硬停的原因是你想一次做一整个 batch 的反向步骤。然后有一个最优大小决定那个 batch 应该多大。

从 ML 收敛速率的角度看，**越小越好**——因为你从梯度下降中获得最新鲜的信息。但从总训练时间的角度看，越小越差（从系统角度）。所以最优是这两者的权衡。

你选一个 batch size，然后对那个 batch size，做一些前向然后一些反向。

Pipeline parallelism 因为有这个空闲时间（bubble），文献中有很多技术来不同地布局以避免它。有更复杂的方案叫 zero bubble 或 one forward one backward，以复杂的方式交错前向和反向。你可以在那里挖比特币。对，更有用的是你可以做权重梯度步骤。

## Pipeline 对推理的影响：中性 [01:01:00]

在推理中，pipeline 对你关心的任何东西——batch size 或延迟——实际上是中性的。不改善也不恶化。如果你看这个推理的延迟，pipeline 运行 vs 全在一个机架上——如果全在一个机架上，我们只是把所有盒子滑下来排成一行，延迟是一样的。

所以基本上推理时用 pipeline 是无脑的？实际上即使在推理中，它也没被大量使用。它减少你的内存容量需求。但实际上有巨大的盈余。一个 Blackwell 机架有很多 TB，也许几十 TB。如果那比一万亿参数模型大得多——一万亿参数模型只需要 1 TB。所以它已经能放下了。

## 内存容量分析 [01:04:23]

在我们之前的方程中，我们看的是内存时间——内存带宽和计算带宽。现在让我们开始看**内存容量**。

不考虑并行方案，内存的容量需求是：**总参数数**（这是我们需要在某个系统中放下权重的量）加上 **KV cache**（batch size × 上下文长度 × 每 token 字节数）。

我之前为 pipeline 辩护的论点是，有一些技术允许我们解决权重部分。那 KV 部分呢？有技术能解决吗？

假设我们在若干 GPU 上运行。E 是 expert parallelism 的程度——当我们把 expert 层分布在多个 GPU 上时，用了多少 GPU。比如 64。然后 P 是 pipeline 的程度——机架数量，也许我们选 4。

总内存需求除以 E×P 就是**每 GPU 内存需求**：

**c_mem = (N_total + batch × context_length × bytes_per_token) / (E × P)**

为什么这样除是对的？因为参数在一个机架内的所有 GPU 之间完美分割。层在不同机架之间完美分割。然后我们以某种方式安排上下文也同样完美分割。

## Micro Batch 与 Global Batch 的关系 [01:07:33]

这里我们需要回去分析 batch size B。你提到了 micro batching vs global batching。

回到 pipeline 图。一个 batch 在前向传播。但它不是做完就消失了。想想 decode 是怎么工作的：我有一堆已经生成的 token，做一次前向传播生成一个新 token，写入 KV cache，然后再做一次前向传播生成下一个 token。所以我实际上是在循环中运行这个 batch #0。

前向完成后，我可以在上面开始循环的下一次迭代。

让我们拆分这个 batch。B 是 global batch size：

**B = micro batch 数量 × 每个 micro batch 的 batch size**

需要多少个 micro batch？在这个图中是 4（0、1、2、3）。micro batch size 仍然是那个约 2000 的数字——300 × 稀疏度。这是每 20 毫秒发车的那班火车的大小。

所以 global batch size = micro batch 数量 × local batch size。Local batch size 由硬件参数决定。Micro batch 数量尽可能小，使得我们绕回来时不留空闲时间。你可以直观地看到它等于 pipeline 阶段数。这里是 4，那边也是 4。

这是实际在做的吗？前沿模型在推理时真的有 pipeline？在大规模训练中肯定在做。推理中可以做。但我要论证为什么它不那么有吸引力——对权重有用，但对 KV 不太有用。

## 更大 Scale-Up 域的真正好处：带宽而非容量 [01:16:53]

我们谈了跳转的延迟。还有同样的 T_mem 延迟——内存时间延迟——实际上被更大的 scale-up 域大幅改善。

回忆一下 T_mem（权重）= 总参数数 / 内存带宽。

这里的内存带宽是什么？不只是一块 GPU——实际上是我能并行用来加载权重的 GPU 数量。我不能并行使用不同 pipeline 阶段（因为它们不同时运行），但我可以并行使用 scale-up 域中的所有 GPU 来加载权重。

这非常有效。内存带宽项本身等于 **scale-up 大小 × 每 GPU 内存带宽**。

每 GPU 带宽每代可能增加 1.5-2 倍，但 scale-up 大小增加了 8 倍。所以更大 scale-up 重要的原因不是整个 scale-up 的内存容量，而是**内存带宽**。

Pipeline 完全解决了容量问题，但 scale-up 大小帮助解决带宽问题。带宽问题帮助你做更长的上下文长度——随着模型变得更 agentic，这越来越相关。它让你以更低延迟运行模型。如果我用一个很稀疏的模型放在一个小 H100 盒子上，延迟会非常高。

## Chinchilla Scaling 与过度训练 [01:19:00]

一个超级离题的问题。有 Chinchilla scaling，告诉你模型应该相对于训练数据量有多大。但现在显然你不只是在优化用训练计算能得到的最高质量模型。你想要用户能得到的最好结果——作为训练和推理计算的混合。

那问题是：你应该过度训练模型多少，使得训练和推理摊销的计算最小化以达到某个性能？

现在有了 RL 推理，还有另一个考虑：你要做一些预训练。那个预训练既用于 RL 生成，也用于最终用户的推理。

"过度训练"的意思是：从纯训练计算效率角度看，用更大模型训练更短时间会更高效（因为它学得更快）。但也许你用更小模型，花更多时间训练，但现在给用户用更便宜。

具体问题：模型比 Chinchilla 最优过度训练了多少？RL 生成改变了这个吗？

这里我们得做一些猜测，因为更新的 scaling law 和模型流量没有被报告。但一种看法是——让我先做一个一般性的启发式声明。

如果我有总成本 = 成本 A + 成本 B（比如训练成本 + 推理成本），我想最小化这个和。对于很多曲线，**最小值往往在成本相等的地方**。这是一个启发式声明，但有很多例子是对的——比如一个是 1/x 另一个是 x。它们往往在相等点最小化。

启发式地，我猜测这对你描述的设置也成立。真正证明需要看 scaling law 和拟合那些奇怪的指数，但遵循幂律的东西往往有这个性质。

## 求解每 Token 字节数 [01:36:03]

我们可以完成这个计算。假设内存时间和计算时间相等的点在 200K token。假设 batch size 足够大使得权重的内存时间可忽略。那么：

**batch × context_length × bytes_per_token / 内存带宽 = 活跃参数数 / FLOPS**

求解 bytes_per_token。Batch size 出现在两边然后抵消。

代入数字：FLOPS/带宽比大约是 300（取倒数 1/300）。活跃参数猜测 1000 亿。上下文长度 200K。

算出来大约 **1667 字节，接近 2 KB**。这实际上是合理的。

做个合理性检查。有两种机制让每 token 字节数较小：

1. **Dense attention + 跨层大量复用**：Character AI 有博客讨论这个——交替长短上下文。全局上下文跨所有层共享。要得到 2KB，比如 d_head = 128（典型值），bytes = attention 层数 × 2 × d_head × KV heads 数。在 Character AI 类模型中，层数因子是 1。d_head 是 128。KV heads 通常 1-8 个。所以完全可以通过 8 个 KV heads × d_head 128 得到这个数字。

2. **Sparse attention**：增加所有这些数字，但有很大的稀疏度项。

这个数字合理，也许稍小。有趣的是他们会通过 API 定价泄露这么多信息。你有动机定价接近成本，否则别人可以套利。

## Input vs Output 价格差异：Decode vs Prefill [01:41:37]

如果我们把 decode 想成"过去长度为 1"，prefill 是"过去长度为多"。

## Prefill vs Decode 的成本分析 [01:42:47]

如果你想这是一个聊天会话——用户说了什么，AI 生成回复，然后用户又说了什么。我们 prefill 这个。这是更常见的情况。读文件或者 AI 响应用户输入或 tool call——任何不是生成的东西。

假设我们在这里。你需要加载基本上之前所有东西的 KV。但这个的内存带宽成本是什么？如果你用 flash attention——它基本上是临时的，甚至不去主内存。忽略它。所以就是之前所有东西。实际上对内存时间完全没有调整。

好，那这一项让它贵 5 倍。为什么？这告诉我们什么？唯一可能改变的是计算贵了 5 倍。但实际上被处理的 token 量大了那么多。所以我们想要的是每 token 成本。

让我们用 len_past 作为 X 轴画图。Y 轴是 T / len_past（每 token 成本）。

**T_compute / len_past**：这除以 len_past 后就是一个常数。不随 len_past 变化。

**T_mem / len_past**：不管上面是什么，除以 len_past 后它看起来像一个递减曲线。

所以随着 prefix 长度增加，你的内存带宽时间下降。这意味着如果你之前受内存带宽瓶颈，你可以避免这个瓶颈。

他们对 prefill 收费比 decode 便宜 5 倍，这确实暗示他们在相当大程度上受内存带宽瓶颈。因为 T 等价于成本。这实际上是——decode 在 5，prefill 在 1。

所以确实是**极度内存带宽瓶颈**的。真实图形大概是这样——仍然交叉，但 decode 时内存和计算时间之间有很大差距。

## Cache Hit 为什么便宜那么多 [01:49:00]

另一个有趣的是为什么 cache hit 便宜那么多。如果我没记错，cache hit 便宜 10 倍。写入 cache 更贵。但如果你命中 cache，便宜 10 倍。

这大概是把东西保留在 HBM 中而不是清除的成本。但如果你确实保留了，再次加载就更便宜。

有两种方式产生 token 的 KV cache：从头计算（从底层 token ID 计算，那些很小）；或者之前已经产生并存储在某个内存中。成本比率就是这两种机制的比率。Cache miss 意味着你从所有内存中删除了它，必须从 token 直接重新计算。

你甚至可以更进一步想：存储在哪个内存层级。可以存在 HBM，也有比 HBM 更慢更便宜的内存——比如主机上的 DDR 或 Flash。你可以计算在每个内存层级中什么时候有意义。这跟你要存储多长时间有关。

## 重新物化 KV Cache 的成本 [01:50:37]

我们想看几个不同内存层级的存储成本，以及重新物化（rematerialization）的成本。Remat 意味着删除 KV cache 后从头重建的成本。

重新物化一个 token 的 KV cache：我只需要对整个模型运行一次前向传播。所以这是计算时间——以 GPU 的速度重新运行计算，然后乘以 GPU 的美元/秒。

非常天真的问题：为什么没有二次项？有的，它出现在计算中。作为近似我选择去掉它。快速展示一下：如果你看每 token 的 FLOPS——来自权重矩阵乘法的 FLOPS 作为上下文长度的函数是常数，来自 KV cache 的乘法随 attend 的内容量线性增长。但这个斜率非常低，画出来时很好地被一条平线近似。你要到百万 token 量级才开始注意到二次/线性项的效果。所以不太相关。

## 为什么没有公司提供超百万 Token 上下文 [01:52:30]

那为什么没有公司有超过百万 token 的上下文长度？如果这是对的？

长上下文有两个成本：内存带宽成本（我们花了很多时间分析的）和计算成本。计算成本几乎总是——而且从基本原理上被迫——比内存带宽成本的斜率小得多。所以限制你拥有真正大上下文的主要是**内存带宽和内存容量**。

Dario 在播客上说过的一个想法是：我们不需要持续学习来实现 AGI，in-context learning 就够了。如果你相信这个，那你得想我们需要到 1 亿 token 上下文长度才能有一个相当于跟你工作一个月的员工。

如果你这么想，那某些 ML 基础设施的东西必须改变才能允许 1 亿上下文长度——内存带宽必须允许。Sparse attention 确实给你一个出路——因为你得到平方根，是一个大改进。

但如果你看模型上下文长度的历史——从 GPT-3 到 GPT-4，它们从大约 8K 跳到 100K-200K。然后过去一两年，它们都在那附近徘徊。我觉得这实际上表明那是合理平衡的成本点，大幅超越会成本过高。不是因为计算成本，而是因为内存带宽成本。

我实际上看不到一条很好的解决路径。HBM 就在那里。它没有变得大幅更好。

Sparse attention 为什么不能解决？Sparse attention 是一个大改进。也许已经被定价进去了。它不是无限改进——如果你太稀疏，你会损失太多质量。
## KV Cache 存储的内存层级经济学 [01:55:01]

经验结果是上下文长度没有增加太多。我觉得是因为这里的内存墙没有解决方案。太稀疏意味着你只 attend 到 token 的很小子集，质量会变差。

那重新合成 KV cache 的不同方式的成本是什么？

**从头计算（Rematerialization）**：基于 GPU 时间。我需要做一定量的乘法来产生它。

**存储在 HBM**：我需要每 token 一定字节数。存在 HBM 中会占用 HBM 容量。思考方式是：如果我用不用的 KV cache 填满了 HBM，我就没法用那块 GPU。怎么定价？也许说成本正比于我使用的 HBM 比例。所以也是 × GPU 美元。

**存储在 DDR**：类似的事情适用于 Flash 和 DDR。

我想做的区分是：有**检索成本**（瞬时成本）和**持有成本**（每秒成本）。

- Rematerialization：有检索成本，持有成本为零（因为我们删除了它）
- HBM 存储：bytes_per_token / HBM_capacity × GPU_cost_per_second
- DDR 存储：持有成本是 bytes_per_token / DDR_capacity × DDR_cost_per_second；检索成本更高因为需要复制到 HBM：bytes_per_token / DDR_bandwidth

每个 scale-up 都有 DDR 和 Flash 吗？这是部署问题。你可以选择。Nvidia 确实以这种形式部署，两者都有。

为什么 HBM 的检索成本不是字节/内存带宽？取决于你怎么定义"检索"。我定义为"移入 HBM 使你可以开始做推理"。如果已经在 HBM 中，你可以在从 HBM 获取的同时做计算。

## 选择正确的内存层级 [01:59:01]

一般来说，如果你在平衡两个成本并且有不同的内存层级，随着持有成本上升，检索成本应该下降。

如果你要持有很短时间，那持有成本低。如果持有很长时间，检索成本的一次性支出就不重要了。

有趣的是，API 有不同的写入价格——5 分钟 vs 1 小时。这暗示 5 分钟是 HBM，1 小时是 DDR。

看具体数字：基础 input token 是每百万 token 5 美元（这是"检索"价格）。写入 5 分钟是 6.25 美元。

我们也许能通过持续时间确定是哪个内存层级。持续时间可能直接告诉你。

关键洞察：给定我知道要持有某东西 5 分钟，我想选一个能在 5 分钟内读完整个内存的层级。所以 **存储容量 / 存储带宽 ≈ 持有时间**。

对 HBM 我们知道这个数字是 20 毫秒——远太短了。DDR 可能差一两个数量级——大约 1-10 秒。Flash 大概在 1 分钟量级。旋转磁盘大概在 1 小时量级。

所以这可能表明两个层级是 **Flash 和旋转磁盘**。我很震惊旋转磁盘还在被使用——这么老的技术。而且它慢到需要一小时才能加载满容量。真的是很不吸引人的技术，但在某些地方有用。

## 密码学协议与神经网络的架构相似性 [02:04:03]

（坐下来聊不需要黑板的问题。）

你有一篇非常有趣的博客文章，讲的是不同密码学协议的架构在高层面上看起来很像神经网络。有一种趋同演化——它们都需要在所有输入之间混合信息。对密码学协议来说，是为了确保哈希函数的每个新输入都会完全打乱输出。对神经网络来说，是需要考虑这条信息如何改变你对另一条信息的理解。

高层面的区别是：某种意义上它们在做相反的事。密码学协议试图把有结构的信息变得跟随机不可区分。神经网络试图从看起来随机的东西（蛋白质序列、DNA、乱码文本）中提取更高层结构。所以它们有相似的高层机制，但实际上在做相反的事。

混合/搅拌在其他地方也出现——甚至有物理例子，比如搅拌蛋糕面糊。先这样搅再那样搅实际上不是一个坏方法。

回到数字世界。如果你随机初始化一个神经网络，它实际上可能也是一个合理的密码——因为随机初始化会以复杂方式打乱东西。让神经网络可解释的是**梯度下降**——你可以微分神经网络并得到有意义的导数。我们做了很多工作来不过度复杂化导数——残差连接让它保持简单，layer norm 也是。

对密码学密码最大的攻击之一也是微分密码。密码在不同的数域中运行——二元域（二进制），而神经网络理论上在实数域。但你绝对可以微分密码。这叫**差分密码分析**。基本上说的是：如果你取输入的小差异，很难让输出的差异也小。设计良好的密码的全部工作就是让输出差异很大。

区别在于优化目标是关于复杂化。它们没有相同的残差连接或 layer norm。
## 后门、对抗攻击与密码学的交汇 [02:07:27]

两者交汇的一个地方是后门。在神经网络中有后门时，你试图隐藏一个输入——不是前向传播的输入，而是反向传播的输入。这是对抗性的。

这实际上是你得到密码中那种雪崩性质的地方。对图像分类模型的对抗攻击——能否找到图像的一个非常小的扰动，完全改变分类、完全改变输出？这在密码中是常见情况，而在神经网络中是不期望的情况。

神经网络实际上被用于密码学了吗？

用神经网络做密码学——一般来说，创建新密码是非常危险的事。几乎所有的都被破解了，99% 都被破解了。所以可能不是一个好的起点。但反方向——至少在一个非常明确的案例中——相当有成效。

## Feistel 网络：从密码学到可逆神经网络 [02:08:51]

密码中有一个构造，然后被引入到神经网络中，叫 **Feistel cipher / Feistel network**。

想法是：你可能有某个函数 f，它不可逆，但你喜欢它因为它做有趣的事——比如做 MLP 或以有趣的方式混合。你想用它构建一个可逆的东西。

构造是：做一个双输入函数而不是单输入。应用 f(x)，但记住 x 是什么（把 x 放到旁边以便反向工作）。也不能丢掉 y——记住 y 并把它们加在一起。

怎么反转？如果我有输出想恢复 x 和 y：x 直接读出来。然后恢复 y：z - f(x)（因为我已经恢复了 x）。所以这个构造是可逆的。

这在密码中被大量使用。仍在使用。是构造密码的主要机制之一。你通常希望密码可逆，特别是密码的层要可逆，因为那有好的密码学性质。

这被移植到了神经网络中。有一篇 2017-18 年的论文叫 **RevNets（Reversible Networks）**。它让整个网络可逆——你做前向传播，但也可以反向运行整个传播。整个神经网络用这个构造变得可逆。

应用到 transformer 层：我们有函数 f（transformer 层）。正常情况下有一个输入和一个残差连接。但变体是：有两个输入 x 和 y。x 通过函数，加到 y 上。这变成新的输出 x。然后原来的 x 变成输出 y。

这实际上在做什么？如果你想两层前——它实际上在做从两层前的残差连接。这个 y 来自上一层，是那里的残差连接。因为这个构造，整个东西可逆。

## 可逆网络的训练优势 [02:12:09]

为什么我关心可逆？对训练有意义。前向传播训练时，假设有 4 层，按 0、1、2、3 顺序运行。我必须把所有 activations 写入 HBM。所以 HBM 占用跟层数线性相关。这实际上可能是训练中最大的内存占用。

然后反向传播以相反顺序读回来。RevNets 的想法是：因为它可逆，我根本不需要存储这些。我可以在运行反向传播时完全重新物化。前向传播运行完后，反向传播时我同步地撤销所有前向传播步骤，以获得我需要的 activations。

这最终是一个**内存节省**。有趣的是，你在花更多计算来节省内存。这跟 KV cache 正好相反——KV cache 是花更多内存来节省计算。

花更多内存来节省计算在当前硬件状态下通常是有利可图的。
