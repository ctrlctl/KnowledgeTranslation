## 核心观点

AI agent 在能够反映团队长期积累的知识和判断时表现最好。其中一部分是已经文档化的制度性知识（institutional knowledge），agent 可以直接使用。但大多数优秀组织还依赖于存在于员工脑中的**隐性知识**（tacit knowledge）。团队往往在尝试构建 AI agent 来自动化工作时，才意识到这些信息有多关键。**确保这些智慧进入 agent，需要一个融合领域专家输入的改进循环。**

---

## 示例场景：交易员Copilot

假设一家金融服务公司的交易员需要实时市场数据。目前他们把问题发给数据科学团队，数据科学家写 SQL 查询、取数据、返回结果。因为 LLM 擅长生成 SQL，这个工作流天然适合用 AI agent 自动化：交易员获得更快的响应，数据科学家可以去做更有趣的项目。

要让这个系统可靠运行，**agent 需要金融服务领域层面和技术数据库层面的双重上下文**。前者包括未成文的交易惯例——比如如何解读"今天的敞口"或"近期波动率"这类请求。后者包括数据库的实操知识——比如哪些表是权威的、哪些已过时，哪些查询模式容易出错或低效。**我们需要与相应的领域专家合作，把 agent 需要的所有未成文上下文纳入进来。**

## 人类输入如何改进Agent的各个组件

构建 agent 意味着决定何时调用 LLM，以及每次调用时提供什么上下文（文档、记忆、对话历史、工具）来达到预期结果。每一个设计选择都受益于来自合适利益相关者的输入。

### 工作流设计

今天的 LLM 很擅长自主编排动作序列——给它们一些工具和自然语言指令，它们就能自己决定调用顺序。但**用确定性代码定义部分工作流有明确好处：更低延迟、更少 token 消耗、以及关键步骤一定会执行的保证。**在某些监管或高风险场景中，你需要代码来严格控制动作序列。

在交易员 copilot 中，我们让 LLM 自主生成和执行 SQL 查询，但添加代码要求它在返回结果前验证最终答案是否符合公司的风险和合规要求。**我们需要风险和合规专家的输入来创建执行公司标准的自动化检查。**

### 工具设计

开发者必须实现 agent 可用的工具，并配置 LLM 用来决定何时调用它们的名称、参数和描述。在工作流的不同阶段提供不同的工具集通常很有用——限制单次 LLM 调用的工具集可以引导模型走向预期行为，减少它选择无关选项的概率。

Copilot 的工具可能包括数据库 schema 检查、查询执行和数据库文档检索。一个关键权衡是 LLM 生成查询的**灵活性 vs 控制力**：通用的 `execute_sql` 步骤允许灵活查询但增加风险；参数化查询工具更安全但能力更有限。**你需要运行评估来确定工具设计的性能和风险特征，只有所有利益相关者都满意时才上线。**

### Agent 上下文

早期 agent 只给模型一个 system prompt 和一组工具定义。随着时间推移，**行业已经转向在 agent 执行开始时提供更丰富的上下文。** Anthropic 的 Skills 就是这一趋势的典型例子——自 10 月推出以来迅速流行。

不再把所有东西塞进一个 system prompt，而是团队提前整理文档、示例和领域规则，让 agent 在运行时按需获取。这让 agent 能使用远超 system prompt 容量的知识。**有效的 agent 设计需要决定 agent 应该访问什么知识，并组织好让 agent 能在正确时刻检索到正确信息。**

选择和组织 agent 启动时可用的信息是 context engineering 的一部分。Context engineering 还涵盖了每次 LLM 调用中提供的信息如何随 agent 推进任务而演变。人类利益相关者在审查 agent 输出和评估分数时提供的反馈，可能影响你对 agent 端到端 context engineering 的方法。

## 将人类判断融入Agent改进循环

在 LangChain，我们与数百个部署 AI agent 的组织合作。**最成功的团队遵循一个紧凑的迭代循环：快速构建 agent，部署到生产或类生产环境，在每一步收集数据来指导改进。**我们称之为"agent 改进循环"，因为我们观察到大多数成功的 agent 都经历了多次这样的循环。

快速且频繁地迭代至关重要，因为决定 agent 行为的是 LLM 的实时推理，而不是代码。**在 agent 运行之前，你不可能知道它会做什么。** AI agent 的接口通常是自由形式的（比如用户可以输入任何内容的文本框），这使得预测用户与 agent 的交互更加困难。**把 agent 放到用户面前是收集你需要的数据来最终使其成功的唯一方式。**

![](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/69dce8f18d5f7e336d258f2c_agent-improvement-loop.png)

### 关键原则：自动化评估对齐人类判断

我们观察到，**当人类帮助设计和校准自动化评估器，而不是手动审查大量 agent 输出时，团队能获得更大的杠杆效应。** 无论团队多大或资源多充足，依赖大规模人工审查很少是经济的。可扩展的方法是将专家判断转化为自动化评估，让你能广泛且持续地测试。

这就是 LangSmith 的 **Align Evaluator** 功能的用途——它提供一个界面，让你用精选的示例和领域专家的反馈来校准 LLM-as-a-judge 评估器。

![](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/69dce8f18d5f7e336d258f3d_image6.png)

*使用 LangSmith 的 Align Evaluator 功能验证一个 LLM-as-a-judge 专业性评估器。评估器目前比人类评判更严格，所以我们需要调整 system prompt 使其更宽松。*

### 开发阶段：整理测试集和评估器

开发开始前，**工程师应该至少有一小组用例场景和预期行为作为项目需求的一部分。** 这些初始测试帮助确认 agent 能正确执行核心任务。随着 agent 接近生产就绪，工程师应与产品经理和领域专家合作，构建更全面的测试集来评估整体行为和关键子组件。

对于交易员 copilot，我们用 LangSmith 的 datasets 功能手动创建一些 ground truth 数据集，配对自然语言问题和正确答案。我们还创建包含"在我们数据库上下文中好的、高性能 SQL 长什么样"的示例数据集。

**我们可以在这个阶段创建一个小飞轮：用手动测试中遇到的有趣案例来扩充初始数据集。** 这有助于逐步自动化反馈循环，确保在 agent v1 准备上线时拥有全面的测试集。

![](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/69dce8f18d5f7e336d258f2f_image4.png)

*将 agent 输出与 ground truth 数据集对比——表现不错但仍有改进空间。*

### 部署后：用自动化评估和监控引导人类注意力

agent 上线后，你需要确保其可靠性并快速识别问题或改进机会。传统的用户体验验证方式是满意度调查和用户访谈，但这种方法的缺陷是它衡量的是用户告诉你的，而不是他们实际做的。LLM-as-a-judge 评估器给了我们一种更稳健的方法。**在生产数据上运行的自动化评估可以帮助监控 agent 并浮现需要人类关注的情况。**

例如，一个 LLM judge 可以自动检测用户何时表达了挫败感，并标记这些交互供审查。团队成员可以调查 trace 并决定问题是 bug、agent 知识缺口还是工作流弱点。

![](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/69dce8f18d5f7e336d258f32_image3.png)

*在 LangSmith 中创建 LLM-as-a-judge 在线评估器来检测用户表达挫败感的消息。*

我们的假设公司会设置：

- **在线评估**：配置 LangSmith 在可观测性数据进来时运行评估器。例如，对慢查询或危险 SQL 进行自动代码检查，以及用 LLM-as-a-judge 评估器审查对话中用户是否对 copilot 的回答满意。
- **告警**：当 LangSmith 看到错误、延迟或负面在线评估分数的峰值时，触发已有的告警系统。
- **标注队列**（Annotation queues）：将值得注意的 trace 标记为需要人工审查，发送到 LangSmith 的标注队列。在队列中，领域专家审查在线评估器返回非常负面分数的案例（表明 agent 有问题）。边界分数则表明我们需要调整评估器本身。

![](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/69dce8f18d5f7e336d258f38_image2.png)

*LangSmith 的仪表板展示 agent 的聚合指标，让团队验证其持续按预期表现。*

### Insights Agent：从 trace 数据中获取价值的另一种方式

**对实时行为的非结构化探索能激发 AI agent 最有价值的改进。** LangSmith 提供 Insights Agent——一个内置的 AI agent，能以最少的用户配置分析大量 trace 数据。它浮现 agent 行为中的模式和趋势，这些从单个 trace 或确定性评估中不容易看出来。

对于交易员 copilot，我们可能运行一个 insights 报告，自动识别相似对话并将其聚类为用例类别。了解交易员向 copilot 提问背后的主题，可以帮助我们识别应该重点支持的用例，甚至发现能更好服务交易员的未来产品功能。

![](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/69dce8f08d5f7e336d258f21_image1.png)

*LangSmith Insights Agent 生成报告，浮现数据中的隐藏模式。*

## 持续优化：将生产数据转化为测试集

构建 agent 第一版时，你的评估集充其量是对"需要什么测试来验证它能工作"的有根据的猜测。**上线后，你获得了一个好得多的测试用例来源：真实的生产数据。**

你需要将这些数据整理成全面但不过大的测试集。自动化系统可以帮助生成候选数据集——例如根据评估器结果过滤生产 trace。但**我们通常需要人类判断来整理平衡的、有代表性的评估集。** 评估只需几百个精心选择的示例就能发挥作用，所以值得让专家参与决定哪些示例应该定义测试集。

团队可以从审查过的 trace 中创建数据集来运行更稳健的评估套件。最有帮助的数据集之一是**"黄金数据集"**（golden dataset）——由 copilot 迄今最佳表现的示例组成，用作基线确保未来版本至少表现同样好。

![](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/69dce8f18d5f7e336d258f35_image7.png)

*使用 LangSmith 标注队列审查 LLM judge 标记为高质量的 chatbot trace，决定它们是否真正属于黄金数据集。*

## 结论

有效的 agent 开发将人类判断与自动化评估的可扩展性结合起来。人类专业知识帮助定义"好"是什么样子——塑造工作流、工具、上下文和评估标准。自动化评估器将这种判断大规模应用，帮助团队快速测试 agent、监控其生产行为、并将人类注意力引导到最重要的案例上。

随着时间推移，这创造了一个飞轮：人类反馈改进评估器、测试集和 agent 本身；改进后部署的 agent 给我们更多数据告诉我们如何改进它；这些洞察驱动下一次开发迭代。

**同样的原则适用于构建任何 agent：建立紧凑的迭代循环，将专家判断捕获到可扩展的评估中，并持续将生产数据转化为更好的测试。** 这是创建为业务带来真正价值的 AI agent 的关键。
