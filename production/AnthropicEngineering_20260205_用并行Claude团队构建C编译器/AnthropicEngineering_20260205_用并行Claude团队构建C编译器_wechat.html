Building a C Compiler with a Team of Parallel Claudes：用并行 Claude 团队构建 C 编译器

作者：Nicholas Carlini，Anthropic Safeguards 团队研究员。

我一直在实验一种监督语言模型的新方法，我们称之为"agent teams"（agent 团队）。在 agent teams 中，多个 Claude 实例在共享代码库上并行工作，无需人类主动干预。这种方法极大地扩展了 LLM agent 可实现的范围。

为了压力测试这种方法，我让 16 个 agent 从零开始编写一个基于 Rust 的 C 编译器，能够编译 Linux 内核。经过近 2000 个 Claude Code session 和 20000 美元的 API 成本，agent 团队产出了一个 10 万行的编译器，可以在 x86、ARM 和 RISC-V 上构建 Linux 6.9。

编译器本身是一个有趣的产物，但我在这里聚焦于我在设计长时间运行自主 agent 团队的 harness 方面学到的东西：如何编写让 agent 在没有人类监督的情况下保持正轨的测试，如何组织工作让多个 agent 能并行推进，以及这种方法在哪里触及天花板。

· · ·

让 Claude 长时间运行

现有的 agent scaffold（如 Claude Code）要求操作者在线并可以协同工作。如果你要求解决一个长而复杂的问题，模型可能解决一部分，但最终会停下来等待继续输入。为了引导持续的自主进展，我构建了一个 harness，把 Claude 放在一个简单的循环中（如果你见过 Ralph-loop，这应该很熟悉）。当它完成一个任务，立即拿起下一个。（在容器中运行，不要在你的实际机器上）。

#!/bin/bash
while true; do
  COMMIT=$(git rev-parse --short=6 HEAD)
  LOGFILE="agent_logs/agent_${COMMIT}.log"
  claude --dangerously-skip-permissions \
    -p "$(cat AGENT_PROMPT.md)" \
    --model claude-opus-X-Y &> "$LOGFILE"
done

在 agent prompt 中，我告诉 Claude 要解决什么问题，要求它把问题拆成小块、追踪正在做什么、弄清楚下一步做什么，并持续做到完美。（关于最后一点，Claude 别无选择。循环永远运行——虽然有一次，我确实看到 Claude 不小心执行了 pkill -9 bash，从而杀死了自己并结束了循环。哎呀！）

· · ·

并行运行 Claude

并行运行多个实例可以解决单 agent harness 的两个弱点：

1. 一个 Claude Code session 一次只能做一件事。特别是随着项目范围扩大，并行调试多个问题效率高得多。 2. 运行多个 Claude agent 允许专业化。当几个 agent 被分配去解决实际问题时，其他专门化的 agent 可以被调用来维护文档、关注代码质量或解决专门的子任务。

我的并行 Claude 实现非常简单。创建一个新的 bare git repo，为每个 agent 启动一个 Docker 容器，repo 挂载到 /upstream。每个 agent 克隆一个本地副本到 /workspace，完成后从自己的本地容器 push 到 upstream。

为了防止两个 agent 同时尝试解决同一个问题，harness 使用一个简单的同步算法：Claude 通过向 current_tasks/ 写入文本文件来"锁定"一个任务（例如，一个 agent 可能锁定 current_tasks/parse_if_statement.txt，另一个锁定 current_tasks/codegen_function_definition.txt）。如果两个 agent 试图认领同一个任务，git 的同步机制迫使第二个 agent 选择不同的任务。Claude 完成任务后，从 upstream pull，合并其他 agent 的变更，push 自己的变更，然后移除锁。合并冲突很频繁，但 Claude 足够聪明能搞定。

这是一个非常早期的研究原型。我还没有实现 agent 之间的其他通信方法，也没有强制执行管理高层目标的流程。我不使用编排 agent。相反，我让每个 Claude agent 自己决定如何行动。大多数情况下，Claude 会拿起"下一个最明显的"问题。

用 Agent 团队编程的经验教训

scaffold 让 Claude 在循环中运行，但这个循环只有在 Claude 能判断如何推进时才有用。我的大部分精力花在设计 Claude 周围的环境——测试、环境、反馈——让它能在没有我的情况下自我定位。以下是我在编排多个 Claude 实例时发现最有帮助的方法。

编写极高质量的测试

Claude 会自主地解决我给它的任何问题。所以任务验证器必须近乎完美很重要，否则 Claude 会解决错误的问题。改进测试 harness 需要找到高质量的编译器测试套件、为开源软件包编写验证器和构建脚本，以及观察 Claude 犯的错误，然后在识别出这些失败模式时设计新测试。

例如，在项目接近尾声时，Claude 开始频繁地在实现新功能时破坏现有功能。为了解决这个问题，我构建了一个持续集成流水线，实施了更严格的执行，让 Claude 能更好地测试其工作，使新 commit 不能破坏现有代码。

站在 Claude 的角度思考

我必须不断提醒自己，我是在为 Claude 而不是为自己编写这个测试 harness，这意味着要重新思考很多关于测试应该如何传达结果的假设。例如，每个 agent 被放入一个没有上下文的全新容器中，会花大量时间定位自己，特别是在大型项目中。在到达测试之前，为了帮助 Claude 帮助自己，我包含了维护详尽 README 和 progress 文件的指令，这些文件应该频繁更新当前状态。

我还牢记语言模型有固有的局限性，在这种情况下需要围绕它们来设计：

  • Context window 污染：测试 harness 不应打印数千字节的无用信息。最多打印几行输出，将所有重要信息记录到文件中让 Claude 在需要时找到。日志文件应该易于自动处理：如果有错误，Claude 应该写 ERROR 并把原因放在同一行，这样 grep 就能找到。预计算聚合摘要统计也有帮助，这样 Claude 不必重新计算。
  • 时间盲：Claude 无法感知时间，如果放任不管，会愉快地花几个小时运行测试而不是推进工作。Harness 不频繁地打印增量进展（避免污染 context），并包含一个默认的 --fast 选项，运行 1% 或 10% 的随机样本。这个子样本对每个 agent 是确定性的但跨 VM 是随机的，所以 Claude 仍然覆盖所有文件但每个 agent 能完美识别回退。

让并行化变容易

当有许多不同的失败测试时，并行化是平凡的：每个 agent 选择一个不同的失败测试来工作。在测试套件达到 99% 通过率后，每个 agent 工作于让不同的小型开源项目（如 SQLite、Redis、libjpeg、QuickJS、Lua）编译通过。

但当 agent 开始编译 Linux 内核时，它们卡住了。与有数百个独立测试的测试套件不同，编译 Linux 内核是一个巨大的单一任务。每个 agent 都会遇到同一个 bug、修复那个 bug，然后互相覆盖变更。16 个 agent 运行没有帮助，因为每个都卡在解决同一个任务上。

解决方案是使用 GCC 作为在线已知正确的编译器 oracle 来对比。我写了一个新的测试 harness，用 GCC 随机编译内核的大部分文件，只用 Claude 的 C 编译器编译剩余文件。如果内核工作了，问题就不在 Claude 的文件子集中。如果坏了，可以通过用 GCC 重新编译其中一些文件来进一步缩小范围。这让每个 agent 能并行工作，修复不同文件中的不同 bug，直到 Claude 的编译器最终能编译所有文件。

多种 Agent 角色

并行化也使专业化成为可能。LLM 编写的代码经常重新实现现有功能，所以我让一个 agent 负责合并它发现的任何重复代码。我让另一个负责提升编译器本身的性能，第三个负责输出高效的编译代码。我让另一个 agent 从 Rust 开发者的角度批评项目设计并做结构性改进，还有一个负责文档。

压力测试 Agent 团队的极限

这个项目被设计为一个能力基准测试。我有兴趣压力测试 LLM 今天勉强能实现什么，以帮助我们为模型未来能可靠实现什么做准备。我一直用 C 编译器项目作为整个 Claude 4 模型系列的基准。

我从起草我想要的东西开始：一个从零开始的优化编译器，无依赖、GCC 兼容、能编译 Linux 内核、设计支持多后端。虽然我指定了设计的某些方面（例如应该有 SSA IR 来支持多个优化 pass），但我没有详细说明如何实现。

之前的 Opus 4 模型勉强能产出一个功能性编译器。Opus 4.5 是第一个跨越阈值的，能产出通过大型测试套件的功能性编译器，但仍然无法编译任何真实的大型项目。我用 Opus 4.6 的目标是再次测试极限。

评估

经过近两周的近 2000 个 Claude Code session，Opus 4.6 消耗了 20 亿输入 token 和 1.4 亿输出 token，总成本略低于 20000 美元。与最贵的 Claude Max 计划相比，这是一个极其昂贵的项目。但这个总额只是我自己产出这个东西所需成本的一小部分——更不用说一个完整团队了。

这是一个净室实现（Claude 在整个开发过程中没有互联网访问）；它只依赖 Rust 标准库。这个 10 万行编译器可以在 x86、ARM 和 RISC-V 上构建可启动的 Linux 6.9。它还能编译 QEMU、FFmpeg、SQLite、postgres、redis，在大多数编译器测试套件（包括 GCC torture test suite）上有 99% 的通过率。它还通过了开发者的终极试金石：能编译并运行 Doom。

然而，编译器并非没有局限：

  • 它缺少从 real mode 启动 Linux 所需的 16 位 x86 编译器。为此它调用 GCC（x86_32 和 x86_64 编译器是它自己的）。
  • 它没有自己的汇编器和链接器；这些是 Claude 最后开始自动化的部分，仍然有些 bug。
  • 编译器成功构建了许多项目，但不是全部。它还不是真正编译器的直接替代品。
  • 生成的代码效率不高。即使启用所有优化，输出的代码也不如 GCC 禁用所有优化时高效。
  • Rust 代码质量合理，但远不及专家 Rust 程序员可能产出的质量。

编译器几乎达到了 Opus 能力的极限。我努力尝试修复上述几个局限但没有完全成功。新功能和 bug 修复经常破坏现有功能。

编译器的源代码已公开。下载它，阅读代码，在你喜欢的 C 项目上试试。

展望

每一代语言模型都开辟了与它们协作的新方式。早期模型在 IDE 中用于 tab 补全。不久后，模型能从 docstring 补全函数体。Claude Code 的发布将 agent 带入主流，让开发者能与 Claude 结对编程。但这些产品都在一个假设下运行：用户定义任务，LLM 运行几秒或几分钟返回答案，然后用户提供后续输入。

Agent teams 展示了自主实现整个复杂项目的可能性。 这让我们作为这些工具的用户，可以对目标更加雄心勃勃。

我们仍处于早期，完全自主开发伴随着真实风险。当人类在开发过程中与 Claude 同坐时，他们可以确保一致的质量并实时捕捉错误。对于自主系统，很容易看到测试通过就假设工作完成了，但这很少是事实。我曾在渗透测试领域工作，利用大公司产品中的漏洞，程序员部署他们从未亲自验证过的软件这个想法确实令人担忧。

所以，虽然这个实验让我兴奋，它也让我感到不安。构建这个编译器是我最近最有趣的经历之一，但我没想到这在 2026 年初就接近可能。语言模型和我们用来与它们交互的 scaffold 的快速进步，打开了编写大量新代码的大门。我预期正面应用会超过负面，但我们正在进入一个需要新策略来安全导航的新世界。
