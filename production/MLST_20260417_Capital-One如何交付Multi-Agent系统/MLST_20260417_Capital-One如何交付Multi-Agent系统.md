# Capital One 如何交付 Multi-Agent 系统

## Multi-Agent 的动机 [00:38]

我们从经典 ML 世界走到了 LLM 生成响应的世界。现在我们要进入一个需要采取行动的世界。当我们处理的问题是复杂的，这就是 multi-agent 发挥作用的地方。

---

## Rashmi 的背景 [01:00]

**Rashmi Shetty** 是 Capital One 企业生成式 AI 平台的高级总监。

她的个人经历与 agentic AI 的核心原则惊人地一致。她的硕士论文主题是**普适计算**（pervasive computing）——感知环境、获取信号、实时做出上下文感知的决策、让执行器触发动作来改变环境。虽然当时是在物理世界中实现的，但本质原则完全相同：**分布式智能**，智能嵌入你所处的系统中。

从学术界到工业界，她学会了如何在企业中扩展这些概念。经历了数据爆炸、构建 AI/ML pipeline、AutoML 平台的旅程。现在到了 agentic 世界——超越决策系统，实际采取行动——对她来说像是闭环的完成。

Capital One 在 AI/ML 旅程上已经走了十年，是最早上现代云平台的银行之一。Gen AI 旅程从 2023 年初开始，第一个 agent assist pilot 在 2023 年上线。

## Chat Concierge：落地案例 [06:12]

Chat Concierge 是 Capital One 部署 multi-agent 解决方案的**滩头阵地**（beachhead initiative）。它是一个汽车经销商应用，部署给经销商，桥接经销商和客户之间的体验。

核心洞察：**购车体验不是从经销商处开始的**——它从客户访问网站、查看库存时就开始了。Chat Concierge 在这个节点让体验无缝化：根据家庭需求、人口统计需求、个性化需求，找到匹配的车，然后生成后续动作（预约试驾等）。

**为什么选择 multi-agent？** 当有多种用户意图需要由单一应用服务时，需要判断：这能用单一确定性模型解决，还是需要随机推理系统（即 multi-agent）？

在这个场景中，有多种意图：
- 一个 agent 专门理解意图、通过澄清问题消歧
- 多个工具根据意图执行不同动作
- 一个 **planner agent** 做判断
- 其他 agent 确保交付内容经过治理、风险标准验证、响应准确性验证、延迟需求验证
- 最终将响应精炼为客户能理解的格式

## 监管环境中的 Agent [10:05]

Capital One 在 agentic 旅程上如此前沿的最大优势之一是：**这是 Capital One 的 DNA**。可以说他们是一个做银行业务的科技组织——拥有构建健壮、可扩展企业系统所需的所有现代技术栈，同时深度嵌入银行业的模型风险框架。

有非常健壮的 **Model Risk Office**，紧密合作。所有风险和合规框架嵌入平台中，表现为策略、guardrails、安全执行、网络安全执行——跨平台不同层实施，覆盖 agent 的不同威胁边界。

两个层面：
1. **Agent 运行时治理**：平台在运行时治理 agent——这是平台的巨大价值。给架构师灵活性专注于设计，平台带来所有治理和风险合规
2. **Agent 自身的治理**：agent 本身可以为特定领域引入治理，叠加在平台提供的基础风险治理之上

---

## 平台的角色：安全与速度 [13:22]

平台的目的是弥合差距，让客户能**快速、安全地大规模开发和部署 agentic 解决方案**。

优先级顺序：
1. 这些 agent 能否在环境中安全执行？
2. 能否扩展？能否满足所有客户指标？
3. 开发速度——SDK、框架、工具，让客户以闪电般的速度构建、安全部署

**策略绑定的 agentic 操作**（policy-bound agentic operations）：策略可以在多个边界以多种方式执行——guardrails、基于工具的权限、agent 的目标是什么、agent 的 manifest 是什么、agent 被允许执行什么。这些都是在平台的入口/出口边界做出的有界策略决策。

---

## 开发者需要什么 [16:15]

从经典 ML 到 agentic AI 系统的关键区别：

过去是部署模型、评估单个模型、确保精确、准确、安全。现在是**跨多个层级的系统**。需要整合的基础要素：

- **数据血缘和上下文血缘**：跨多个 agent 传递而不撑爆上下文窗口
- **Memory 服务集成、Tool 服务集成**
- **数据的便捷定位**，带着数据治理
- **扩展、延迟机制**

范式转变：过去被视为非功能性需求的东西（如延迟），今天是**产品特性**，烘焙进开发者体验中。

Capital One 的优势：一直认为**数据优势就是 AI 优势**。在进入 agentic 旅程之前，所有企业数据 pipeline、现代技术栈都已就位。提供可复用服务和企业钩子（治理钩子、网络安全钩子）变得非常容易。

开发者需要的核心：**在保持安全的同时追求速度**。周期时间在压缩——过去模型开发需要数月，现在实验以天计。从 pilot 到 production 的路径必须清晰。

## 可观测性的范式转变 [20:20]

Chat Concierge 被选为滩头项目的原因之一：**高表面积、低风险**的场景——是观察生产中失败模式的绝佳方式。

Agentic 系统的可观测性方法：

传统方式：golden dataset → 离线批量 eval → 设计系统 → 部署。

Agentic 系统的目标是形成**闭环系统**：计划、推理、思考、行动、然后观察和学习。开发者对这个闭环系统有更高的意识——在设计时做离线 eval，在生产中观察跨层级的特定指标。

可观测性有不同风味：
- 业务用户看到的指标
- 运维工程师看到的指标
- 研究科学家看到的指标（模型漂移等）

这些在生产系统中实时观察，反馈回来用于持续学习和迭代。

---

## Multi-Agent 的可观测性挑战 [22:58]

在 multi-agent 世界中，可观测性挑战被**复合放大**——你有这些根本上概率性的系统在互相交互。

在随机系统中，能够**重放 agentic 动作**并理解其运作方式至关重要。

Agent 行为需要多维度的可观测性：
- 调用了什么工具？
- 什么推理机制导致了那个工具调用？
- 跨系统传递了什么上下文？
- 跨层级的延迟优化监控

延迟今天是**跨职能的努力**——必须端到端观察，不能是孤立的方法。

Capital One 的优势：一直在为未来设计，有健壮的可观测性栈。新东西进来时，只需要额外的 SDK 来服务特定的细微层或组件——像插件一样。

---

## Eval 框架 [26:11]

Agentic eval 与经典 ML eval 的基本原则相同：golden dataset、特定指标、围绕它们的实验。

**关键区别**：eval 框架现在调优为做**端到端 eval**，而不是单个 agent eval——因为单个 agent eval 如果上下游不工作就毫无意义。

作为平台，提供不同的 eval 工具来构建 eval pipeline、部署它们、提供 golden dataset、提供沙箱环境执行。

---

## 模型演进与推理优化 [27:37]

Capital One 的 risk-first 平台策略在这里帮助很大。新模型出现时，有专门的层用于推理层配置、推理优化层和基准测试——让新模型的评估更快更容易。

核心哲学：**推理 + 专业化**。

- **推理能力**：通过 agentic 框架提供
- **专业化**：对于 Chat Concierge 这样的用例，提供个性化体验至关重要。通过**专业化模型和微调**实现。**Teacher-student distillation** 给你对个性化体验和延迟指标的控制

这回到了数据是价值的观点——数据是独特资产，围绕它构建需要定制模型。

---

## 关键架构决策 [30:18]

1. **Risk-first 平台方法**：即使是滩头客户（第一个 agentic 应用投产），从一开始就有平台思维
2. **全栈方法**：数据在哪里？模型优化策略？跨层监控？延迟优化？
3. **使用开源基础模型的专业化策略**
4. **多 agent 编排**：哪些 agent 被配置？agentic 层的治理？工具执行如何配置？
5. **基于生产学习改进栈的任何部分**——"管弦乐队问题"：如何编排从 pilot 到 production 再回到实验的整个生命周期
6. **Human handoff**：在什么节点需要人类交接？什么治理或策略决定了人类交接？

---

## MCP 与 Agent 标准 [33:01]

平台的目的是**抽象掉复杂的底层技术决策**。MCP vs 原生工具 vs 本地 tool calling——这些都在平台内抽象，客户只需利用暴露给他们的东西来加速旅程。

对 MCP、A2A 等标准有明确的立场和观点，决策烘焙进平台中。

---

## Human-in-the-Loop 设计 [34:11]

Human-in-the-loop 是 agent 编排的一部分。这些是需要决定 agent 有界动作的节点——在哪个节点需要引入人类进行验证。

这是经典的多轮、多遍 agentic 架构，其中一个决策者可以是人类。通过编排机制和框架烘焙进去——循环在哪里被特定人类中断，之后循环可以继续。

Human-in-the-loop 通常部署在**高风险用例**中。每个业务线已经有策略来决定如何向最终客户交付这种用户体验——可能是 24×7 支持系统，响应时间烘焙进端到端 SLA。

作为平台，需要对通知机制保持**不可知**——有简单的方式嵌入到业务线的运营环境中。

---

## 平台复杂性管理 [36:39]

平台隐藏复杂性。开发者通过多种方式与系统交互：CLI、SDK、UI。

对于 multi-agent 旅程上的新手客户——提供**预构建蓝图**，拿来就能用。对于老练的客户——提供开发者工具包。根据客户来源、用例、如何以最少约束最快到达生产来提供不同范围的服务。

底层基础设施（如 Kubernetes 环境）隐藏在 API 后面。推理优化层确保正确的模型托管在正确的环境中、为推理优化、通过特定 SDK 和 API 提供。对客户来说，这些都是不同的服务，在 agentic 开发旅程中需要经过。

---

## 闭环系统与持续改进 [42:13]

平台的角色是确保沿闭环旅程提供钩子和工具，让客户自己决定具体怎么做。

流程：可观测性观察特定失败模式 → 捕获信号 → 回到实验环境 → 客户调优想调的东西（prompt 调优、模型调优、上下文管理、检索、grounding）→ 重新对齐 agentic 系统以适应不断变化的运营环境。

从平台角度，关键是确保**数据 pipeline 稳固**，在暴露信号的各个位置都能访问数据。

---

## Model Risk Office 的合作 [44:20]

与 Model Risk Office 是**合作伙伴关系**，共同交付同一目标。世界现在才开始觉醒于 agentic 治理并尝试构建框架——Capital One 已经有健壮的框架。

这些合作伙伴帮助理解如何将当前监管合规策略烘焙进任何新系统、现代栈、技术组件中。

---

## 经验教训与最佳实践 [45:41]

核心教训：

1. **把 agentic AI 当作系统对待**——它真的是一个系统
2. **从治理数据开始**，在应用的多个层级烘焙风险控制
3. **延迟需要端到端优化**——包括交接在内的端到端客户体验
4. **最大收益来自生产后遥测**
5. **不要丢弃遗产**——Capital One 利用已有的技术栈快速跳上 agentic 列车
6. 推理变得显式，专业化变得模块化

对于平台角色的人：
- 理解你缺少什么服务来构建 agentic 能力
- 理解你缺少什么策略
- 从全新视角看可观测性，更早地 instrument，定义升级阈值
- **构建 agent 的问题已经解决了**——我们正快速进入 agent 执行和执行环境中的治理变得更关键的世界

## 下一步：规模化 [48:56]

现在有了必要的组件，问题是**规模化**。如何触达数百万客户，保持同样的速度和治理水平？如何从开发者和消费者两个角度扩展？

这有技术组件（在生产中运行大量 agent 服务大量客户），也有战略组件（如何管理跨公司、跨业务线的 agent 舰队）。

需要与行业中不断演进的治理标准保持一致，同时保持扩展标准。

关于平台与开发者的关系：世界移动太快，没有摩擦的时间。有快速反馈循环机制，从内部和外部用户获取反馈回到平台。

关键原则：**不剥夺开发者的能动性**。他们需要能动性来根据自己的视野配置和探索系统。提供所有工具包、开发者工具包、框架、服务、可观测性——让他们在观察系统时知道该做什么。
