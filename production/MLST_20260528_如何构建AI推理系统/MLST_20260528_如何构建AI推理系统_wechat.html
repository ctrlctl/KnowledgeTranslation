推理是 AI 中最重要的工作负载 [00:46]

Sam：Philip，你是怎么进入推理工程领域的？

Philip：2022 年——ChatGPT 发布前 10 个月——我有一个非常强烈的行业论断：我需要一份工作。我在 Base10 和一个洗衣配送创业公司之间选择，最终选了 Base10。四年多来，我亲历了 AI 行业的崛起：从预测建模到生成建模，从内部工作流到成为 AI 原生公司的营收路径。

Sam：Base10 早于 ChatGPT，当时有很多 MLOps 公司在竞争。随着生成式 AI 崛起，很多被收购或消失了。但存活下来做得好的，很多都在做推理。为什么？

Philip：推理是 AI 中最重要的工作负载，也是最有粘性的。 这是我们进入 AI 基础设施市场的楔子。推理非常复杂，做好它对任何依赖生成模型驱动产品的公司都至关重要。

我们一开始就是推理公司，只是推理的模型不同——用 CPU 和 T4 GPU 跑 XGBoost、Wave2Vec、GPT-J。然后 Whisper 出来了——天哪，一个模型十亿参数！现在需要 GPU，需要很多，很难跑起来，很难跑得够快。自然而然地，随着模型变大，ML serving 栈中最复杂的部分变成了推理。

推理为什么难：混合格斗的类比 [07:18]

Philip：我是格斗运动员。在 MMA 中，你不能只精通一件事就成为冠军——不能只是好的摔跤手或好的拳击手。你需要在很多不同的复杂技能上都出色。推理也一样。

你需要理解 GPU 上发生的事——CUDA 级编程、PyTorch、推理引擎。你需要能应用研究——不同的量化技术、投机解码算法、KV cache 复用机制、跨 GPU 并行、跨不同硬件的解聚。然后还有运行大规模分布式系统的所有传统问题——过去 20 年的云架构知识，加上处理全球大流量工作负载。

所有后端 web 基础设施、所有 GPU 编程，在推理中汇聚在一起，而且时间窗口非常苛刻——通常只有几百毫秒的延迟 SLA。正是大量复杂系统的编排让它成为如此困难的问题。

研究到生产：可能是世界上最快的时间线 [10:06]

Sam：推理中研究到生产的时间线是不是特别快？

Philip：可能是世界上最快的时间线。 医学中研究到药房可能需要几十年。物理或工程中应用新概念可能需要几年。即使在 AI 内部，训练一个模型用新技术可能还需要几周到几个月来调超参数。

但推理的时间线通常是几小时。新模型架构出来，你必须第零天就搞清楚怎么支持它。PoloQuant 论文出来后，我们模型性能团队的一个工程师 31 小时后就实现了 CUDA kernel。

唯一可能比推理更快的行业是交易（trading，不是 training）。

关于 PoloQuant——论文一年前就有了，但最近才火。它被重新发布为博客文章引起了关注。我在爱荷华长大，受芝加哥经济学派影响——有效市场假说是你能给年轻人灌输的最危险的谬误。不是所有东西都已经被搞清楚了。推理领域的低垂果实已经被摘了很多，所以现在我们在找下一步时，一年前看起来不可行或不值得的技术突然变成了"哦等等，现在我们准备好了"。

谁应该关心推理工程 [13:46]

Philip：首先，这是一个你可能想从事的有趣领域。三年前世界上可能只有几百个推理工程师——他们当时可能都不这么称呼自己。现在有几千、几万个。

即使有 AI 辅助代码生成带来的生产力提升，我相信几年后对推理工程师的需求还会是今天的 10 到 100 倍。在 Base10，我们招不够懂推理的人。

即使你不想在推理平台工作——每个垂直 AI 应用公司最终都要搞清楚自己的推理策略。需要懂技术和权衡的人来制定和执行策略。好的推理可以是"感觉像魔法的快速产品"和"导致持续流失的慢速 buggy 体验"之间的区别。

理解推理改变你构建产品的方式 [16:03]

Philip：在一个大多数 AI 工程师在 GPT 和 Claude 模型上训练出来的世界里，你以特定方式理解世界：我有 N 个模型，每个有固定的智能水平、固定的速度、固定的成本、固定的可靠性。

推理工程的第一课是：从把这些当作不可变的离散点，转变为理解它们是一个频谱。你可以通过调整 batch size 或添加/移除投机算法来在延迟和吞吐量之间权衡。当你创建了一个结果频谱——高性能推理的有效前沿——你开始理解"等等，我可以选择改变消费这些系统的方式"。

比如你可以在产品中建优先队列——付费用户流量优先于免费用户。或者你理解了量化——因为你有自己的产品特定 eval，你可以有信心地量化模型而不降低用户体验质量。然后你自己量化的模型跑得更快更便宜，而且你不会受到第三方提供商随机智能降级的影响。

甚至像理解 KV cache 复用的工作方式——序列早期哪怕一个 token 的差异都会打乱后面所有的缓存——这会影响你怎么构建 chat template 或模型输入。

推理成熟度周期：从按 token 付费到自主部署 [22:08]

Philip：这个旅程通常和产品成熟度周期对齐——注意是产品成熟度，不是公司成熟度。有时小公司比大公司走得更远，因为 AI 组件对他们的产品更关键。

阶段一：完全依赖按 token 的闭源模型提供商。几乎所有人都应该从这里开始——用一个 API key 获得前沿智能，起步时很难打败这个。

阶段二：遇到成本问题或容量问题。人们转向超大规模云（AWS、GCP），做预留吞吐量购买，在 Bedrock、Vertex、Azure AI Foundry 上启动模型。

阶段三：转向专门的推理提供商（如 Base10），用自己拥有权重的模型做专用部署。或者建内部平台、组建团队。

也有公司走边缘推理路线——用 IoT 问题替换分布式系统问题。我看到较少的是公司大量购买 GPU 放在办公室地下室——但医疗和金融领域确实有这样做的。

所有这些方法在正确的情况下都是有效的。但这些技术确实非常难做好和跟上，所以"买而不是建"在推理侧越来越成为趋势。

GPU 生命周期：Hopper 的持久力 [27:44]

Philip：我经历了三个完整的 GPU 周期：Ampere、Hopper、Blackwell。GPU 代际从制造到分发需要几个月到一年，然后又需要几个月到一年把行业代码移植上去。

Hopper GPU 在推理中仍然非常流行。 一个重要原因是大量开源工作来自中国实验室——受出口管制影响，他们通常在 Hopper 而非 Blackwell 上工作。所以你得到的是 FP8 kernel、为 Hopper 异步编程范式构建的东西、为 8×H200 节点大小设计的模型。

Ampere 终于在推理中失宠了——主要因为不支持 FP8 量化，必须全精度运行或遭受灾难性质量损失。但 Hopper 因为 Blackwell 短缺和大量 Hopper 优化工作负载，有巨大的持久力。H100 的租赁价格现在比一年前还贵。

Hopper 对小模型也很好——用 MIG（多实例 GPU）切分来适配嵌入模型、语音模型这些 1-8B 参数的模型。不需要全新的 72 块 Blackwell GPU 机架。

我对 GPU 代际的有价值生命周期非常看好——从 Hopper 开始，2018-2020 年的 GPU 我们五六年后还在用。

推理工程能被 AI 自动化吗 [32:14]

Philip：某些部分正在被 AI 加速——比如 CUDA kernel 编写。过去几个月有一堆开源项目和创业公司在做按需定制 CUDA kernel。

但推理系统相对于模型仍然非常通用——你用相当通用的 kernel、框架和引擎在非常通用的硬件上运行特定架构。有大量解锁空间来让推理系统更特定于确切的工作负载，并且动态调整。我能想象未来的推理系统比今天复杂 10 倍。

但我们喜欢说：你不能 vibe code uptime。 对于这些有数亿甚至数十亿美元经济价值依赖的关键任务系统，仍然需要能对结果负责的人类所有者。

Agent 驱动推理专业化的需求 [36:36]

Philip：对 agent 和多步推理的需求，正是驱动高度专业化推理优化需求的原因。

在聊天世界里，用户每次操作你对一个模型发一个请求。在 agent 世界里，用户一次操作你可能对不同模型发几十、几百甚至几千个请求。如果你想让 agent 快速可靠，每个模型以及它们之间的每个连接都需要快速可靠。

这让推理成为更关键的挑战。也意味着能快速优化单个模型和工作负载的系统——也许用 AI 加速的编程范式——能让你更可靠地构建和扩展 agent。

多模态推理的特殊挑战 [38:39]

Philip：理解推理帮你构建更好产品的另一个例子：分类任务。我可以把数据扔给 Opus 4.6 Max Thinking High，得到非常好的分类——然后付一大笔钱。或者我可以用传统 ML 分类器，如果选对了，也能得到非常好的分类——而且几乎免费。

命名实体识别——没人真的用前沿 LLM 做这个（我希望没有）。但即使用 Flash 模型做可能需要 500 毫秒，我们刚发布的专用运行时做到了 1 毫秒。如果你的 agent 每个用户请求做 100 次这个操作，这就从"看转圈"变成了"瞬间完成"。

模态方面：大多数模型聚合在两种范式——自回归 token 循环（包括语音模型、嵌入模型）和扩散（视频/图像生成，还有扩散 LLM）。但每种内部都有特殊考量。

比如 VLM（视觉语言模型）——前面有个小小的 10 亿参数视觉编码器，后面是万亿参数 LLM。那个小视觉编码器经常比 LLM 本身造成更多运行时问题——因为行业中视觉编码器太异构了，软件支持少得多。

TTS 模型是个有趣的例子——很多现代 TTS 本质上是极度微调的 LLM，扩展了词汇表来包含音频波形的编码表示。所以我们能直接用 TensorRT-LLM 的定制版本跑它，获得出色性能。但对 Whisper（有编码器+解码器）就不行。

即使架构相似，跨模态也可能有不同的性能目标。LLM 你想要尽可能多的 tokens/s。TTS 你只需要实时语音所需的 ~80-100 tokens/s——达到后你想增加 batch size 跑更多并发流，或者在更便宜的硬件上达到同样速度。不同的性能目标完全改变你架构系统的方式。

推理引擎的开源格局 [47:31]

Philip：推理的开源市场集中度惊人。JavaScript 框架鼎盛时期有几十个可行选择，编程语言有八种合理选择。但推理主要集中在三个开源运行时：vLLM、SGLang 和 TensorRT-LLM。

部分原因是从零搭建新运行时的复杂度极高，所以大多数人觉得贡献给现有项目更有用。推理优化方面有很多好的开源工作——kernel 库、量化工具、KV cache 复用工具、投机解码等。但完整推理引擎从零构建太复杂了。

即使推理提供商也通常是拿开源引擎加定制，而不是从头重新发明——除非他们在自己设计的专用硬件上或创建了自己的编程语言。

· · ·

硬件专业化与 2026 展望 [49:56]

Philip：我是绿队（NVIDIA）的——书封面是绿色的有原因。但硬件层的专业化也有道理。最酷的 demo 之一是 Talus——那个 ASIC 把 Llama 3.1 8B 烧到芯片上，达到了疯狂的 16000 tokens/s。

2026 可能是解聚（disaggregation）之年——NVIDIA 收购 Groq 有了更专业的 prefill vs decode 计算。AWS 也在组合 Trainium 和 Cerebras 做 decode。对于超大规模工作负载——一个模型接收百万并发请求——硬件专业化会提供很多解锁。

2026 是推理之年。 2025 也是，2024 也是，2027 也会是。

我最兴奋的趋势是公司开始拥有自己的智能。Shopify 转向 Qwen 模型省了几千万。如果你想构建真正差异化的产品，你需要在每个层面都差异化——包括模型层面。
