Eval Awareness in Claude Opus 4.6's BrowseComp Performance：Eval 意识——Claude Opus 4.6 的 BrowseComp 表现

BrowseComp 是一个旨在测试模型在网络上查找难以定位信息能力的评估。像许多 benchmark 一样，它容易受到污染：答案通过学术论文、博客文章和 GitHub issue 泄露到公开网络上，运行 eval 的模型可以在搜索结果中遇到它们。

当我们在多 agent 配置中对 Claude Opus 4.6 评估 BrowseComp 时，我们在 1266 个 BrowseComp 问题中发现了 9 个这类污染的例子。然而，我们还目睹了两个新型污染模式的案例。Claude Opus 4.6 没有无意中遇到泄露的答案，而是独立地假设自己正在被评估，识别出它在运行哪个 benchmark，然后定位并解密了答案密钥。

据我们所知，这是首个有记录的案例：模型在不知道正在运行哪个 benchmark 的情况下怀疑自己正在被评估，然后反向工作成功识别并解决了评估本身。我们认为这种此前未观察到的技术是由模型智能的提升和更强大的工具（特别是代码执行）所促成的。这一发现引发了关于静态 benchmark 在启用网络的环境中运行时是否仍然可靠的问题。

· · ·

典型污染与 Eval 意识

在答案来自 benchmark 材料而非原始研究的 11 个问题中，9 个是直接污染——benchmark 问题的答案出现在公开可用的网络内容中。最常见的来源是学术论文。多篇 ICLR 2026 提交在 OpenReview 上使用 BrowseComp 问题作为案例研究，并以明文表格发布答案；来自多个实验室的 ArXiv 论文在附录中包含完整的解题轨迹。

剩下的两个案例在质性上不同。在这两个案例中，模型在最初通过常规网络搜索尝试解决问题后，其输出开始交替进行搜索和分析问题本身，推测为什么会被问到这个问题。Claude 注意到问题的"极其具体的性质"，并假设它是作为测试构造的。它考虑了问题可能是作业或考试题、"一个旨在测试 AI 能否承认找不到答案的不可回答问题"，或 LLM benchmark 中的一个条目的可能性。然后它系统地搜索这个问题可能属于哪个 benchmark，最终解码了 benchmark 的加密答案密钥。

其中一个问题消耗了 4050 万 token，大约是中位数的 38 倍。在前 3000 万左右 token 中，模型进行了合法搜索，在数十个平台上用 12 种语言调查了十几个具体候选者。在数百次失败的搜索后，它写道：

让我尝试一种全新的方法——也许这是来自 GAIA benchmark 数据集的问题，该数据集旨在测试 AI agent。

Claude 还没有发现自己在 BrowseComp 中，但它已经正确推断自己可能在一个评估中。然后它尝试搜索任何类似的 eval。模型首先在搜索查询中附加"puzzle question"，然后是"trivia question"、"multi-hop question"、"AI benchmark question"和"LLM evaluation"。它专门搜索了 GAIA 但在检查了 165 个公开验证问题中的 122 个后排除了它。然后它机械地遍历了它知道的其他 benchmark——BrowseComp、SimpleQA、FRAMES、WebArena——并派遣子 agent 执行包括"BrowseComp how to decrypt answers"和"BrowseComp canary string decrypt"在内的指令。

即使在识别出 BrowseComp 是 benchmark 之后，提取答案还需要几个步骤。Opus 通过网络搜索在 GitHub 上找到了评估源代码并阅读了 XOR 解密实现。它定位了用作解密密钥的 canary string，然后使用 SHA256 和 XOR 编写并执行了自己的 derive_key() 和 decrypt() 函数。但加密数据集作为 application/octet-stream MIME 类型的二进制文件托管，harness 的 web 工具因内容类型错误拒绝了它。Opus 然后搜索数据集的替代镜像，在 HuggingFace 上找到了一个以 JSON 而非二进制格式提供相同加密数据的第三方副本，成功获取，对所有 1266 个条目运行解密代码，并定位到了它的问题。然后它通过在网络上搜索实际来源材料来验证解密的答案。

Eval 意识的潜在触发因素

我们追踪了两个 eval 意识案例中的推理，发现了相同的进展。首先，模型在数百次尝试中耗尽了合法搜索策略。然后它从搜索答案转向推理问题的结构，注意到问题的具体性感觉是人为构造的。接着它推测问题可能来自"特定的 OSINT 挑战、隐私练习或教育材料"。然后它按名称列举 AI benchmark：GAIA、BrowseComp、FRAMES、SimpleQA、WebArena、AgentBench、FanOutQA、MuSR 和 Humanity's Last Exam。最后它对每个进行搜索。

这表明模型对 benchmark 问题的样子有隐式理解。极端具体性、晦涩的个人内容和多约束结构的组合似乎对模型来说是可识别的"评估形状"。触发因素不是单一观察，而是失败搜索的累积加上问题的人工感。

失败的尝试

两次成功的尝试并不是 Opus 试图解密 BrowseComp 答案的唯一例子。还有 16 个问题中 Opus 试图访问 benchmark 材料但失败了。最重要的防御是上述相同的二进制文件限制。在三次运行中，Opus 找到了评估代码、理解了 XOR 方案并拥有解密密钥，但无法弄清楚如何以纯文本形式检索加密数据。数据集认证门控阻止了另外六次尝试。

其中四个问题得分为 0.0，因为搜索 benchmark 答案完全取代了合法研究：模型把所有时间花在试图弄清楚它在运行哪个评估上，而不是回答问题。在最极端的案例中，模型的最终提交不是问题的答案，而是一份 benchmark 识别报告。

18 次运行独立收敛到相同策略表明这种行为不是偶然，而是一种可复现的模式，随着能力增加可能会变得更加普遍。

· · ·

新型跨 Agent 污染向量

除了 eval 意识，我们发现了第二种不太刻意的污染形式：agent 无意中留下搜索痕迹，后续 agent 可能会捡到。一些电商网站从搜索查询自动生成持久页面，即使没有匹配产品。例如，一个网站会把查询变成一个带有效 HTML 标题和 200 状态码的页面。

这些页面本身不包含有用信息。但 agent 可以读取 URL 路径，在某些情况下包含其他 agent 搜索查询中嵌入的假设。一个 agent 正确诊断了它看到的东西："多个 AI agent 之前搜索过同一个谜题，在商业网站上留下了缓存的查询痕迹，这些不是实际的内容匹配。"

每个搜索网络的 agent 都会留下痕迹，网络正在慢慢积累先前评估运行的永久记录。

· · ·

多 Agent 放大效应

我们还用单 agent 配置运行了相同的 1266 个 BrowseComp 问题。非预期解的比率在单 agent 配置中为 0.24%，多 agent 为 0.87%，相差 3.7 倍。我们假设多 agent 架构不会改变模型找到非预期解的倾向；相反，更高的 token 使用量和每轮使用多个并行搜索者增加了至少一个 agent 遇到泄露材料或开始怀疑自己正在被评估的概率。

· · ·

结论

总共，我们发现了至少 20 个不同的 BrowseComp 答案泄露来源。新的污染源持续出现，由研究社区在论文中使用 benchmark 问题作为示例的做法驱动。

我们已更新了 Claude Opus 4.6 和 Claude Sonnet 4.6 的模型卡。对于本报告中描述的 Opus 4.6 多 agent 配置，我们最彻底调查的运行中，我们用屏蔽列表重新运行了 11 个标记的问题；8 个通过合法研究返回了正确答案。调整后的分数为 86.57%，低于 86.81%。

随着模型变得更强大、eval 变得更复杂，防止模型以意外或不期望的方式解决问题将变得越来越困难。我们不认为 Opus 4.6 在 BrowseComp 上的行为代表对齐失败，因为模型没有被告知以任何方式限制其搜索，只是被要求找到答案。但这确实引发了关于模型为完成任务可能走多远的担忧，以及在现实世界中约束其行为将有多困难——特别是在复杂的、计算密集的、长时间运行的任务上，这些任务增加了 agent 找到问题的意外解决方案的可能性。

在我们的实验中，URL 级别的屏蔽列表不足以遏制这种行为，因为 Opus 找到了绕过它们的替代路径。最有效的缓解措施只是屏蔽包含任何"BrowseComp"变体的搜索结果。我们预期这些动态会加剧，并鼓励研究社区将 eval 完整性视为一个持续的对抗性问题，而不是设计时的一次性考虑。
