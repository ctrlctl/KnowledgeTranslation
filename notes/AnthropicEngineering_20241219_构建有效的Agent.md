# 构建有效的Agent

> 来源：output/markdown/AnthropicEngineering_20241219_构建有效的Agent.md

## 要点摘录

### Agent设计三原则

**原文：**
> 实现 agent 时，我们遵循三个核心原则：
>
> 1. 保持 agent 设计的**简单性**
> 2. 通过显式展示 agent 的规划步骤来优先保证**透明度**
> 3. 通过充分的工具文档和测试，精心打造 agent-计算机接口（ACI）
>
> 框架可以帮你快速起步，但走向生产时不要犹豫减少抽象层、用基础组件构建。

**理解/讨论：**
三个原则对应三个维度：架构复杂度（简单）、可调试性（透明）、工具质量（ACI）。最后一句点明了对框架的态度——框架是脚手架，不是地基。生产系统需要你理解每一层在做什么。

---

### Agent适用场景的四个共性

**原文：**
> 我们与客户的合作揭示了两个特别有前景的 AI agent 应用方向。它们的共性：需要对话和行动结合、有明确的成功标准、能形成反馈循环、人工监督能有效介入。

**理解/讨论：**
这四条是判断"这个场景适不适合用 agent"的检查清单：
1. 对话+行动：纯聊天不需要 agent，纯自动化不需要 LLM，两者结合才是 agent 的甜区
2. 明确成功标准：没有可衡量的目标就无法评估 agent 是否在正确工作
3. 反馈循环：agent 需要从环境获取 ground truth 来自我纠正（如测试结果、API 返回）
4. 人工可介入：agent 会犯错，必须有人能在关键节点审查和纠偏

---

### Workflow vs Agent 的权衡

**原文：**
> Agentic 系统通常用**延迟和成本换取更好的任务表现**，你需要考虑这个权衡何时合理：
> - 对于定义明确的任务，**工作流**提供可预测性和一致性
> - 当需要灵活性和模型驱动的决策时，**Agent** 是更好的选择
> - 对于很多应用，**优化单次 LLM 调用**（配合检索和上下文示例）通常就够了

**理解/讨论：**
三级递进：单次调用 → 工作流 → Agent。选择标准是任务的开放程度和对灵活性的需求。面试中用这个框架回答"什么时候该用 agent"比泛泛而谈更精准。

---

### 最简方案优先

**原文：**
> 构建 LLM 应用时，我们建议**找到最简单的可行方案**，只在必要时增加复杂度。
>
> 只在复杂度能明显改善结果时才添加复杂度。LLM 领域的成功不在于构建最复杂的系统，而在于构建**适合你需求的正确系统**。

**理解/讨论：**
这是工程判断力的体现。面试中展示"我知道什么时候不该用 agent"比"我会搭 agent"更加分。

---

### Agent的本质架构

**原文：**
> Agent 能处理复杂任务，但**实现往往很直接**——通常只是 LLM 在循环中基于环境反馈使用工具。因此，清晰、周到地设计工具集及其文档至关重要。

**理解/讨论：**
Agent = while loop + tool call + environment feedback。复杂度不在架构本身，而在工具设计和错误处理。这句话点破了 agent 没有什么神秘的——难的是让它可靠地工作。

---

### ACI设计方法论

**原文：**
> 一个经验法则：想想人机接口（HCI）投入了多少精力，计划对 **agent-计算机接口（ACI）** 投入同等精力。
>
> - **站在模型的角度想**。仅凭描述和参数，使用这个工具是否显而易见？
> - **参数名和描述能不能改得更直白？**
> - **测试模型如何使用你的工具**：在 workbench 中运行大量示例输入，看模型犯什么错误，然后迭代。
> - **对工具做防呆设计（Poka-yoke）**：修改参数使犯错更难。

**理解/讨论：**
ACI 是这篇文章最有实操价值的部分。核心思路：把工具当产品来设计，用户是 LLM。工具文档 = prompt engineering 的一部分。Anthropic 自己在 SWE-bench agent 上"花在优化工具上的时间比优化整体 prompt 更多"。

---

### 框架的陷阱

**原文：**
> 这些框架帮你封装了底层琐事，上手很快。但它们往往**多加了一层抽象，把底层的 prompt 和 response 藏起来了**，出了问题很难调试。它们还容易诱导你在简单方案就够用时添加不必要的复杂度。
>
> 我们建议开发者**从直接使用 LLM API 开始**：很多模式几行代码就能实现。

**理解/讨论：**
对 LangChain 等框架的含蓄批评。框架的问题不是功能不够，而是抽象层让你失去对底层行为的可见性。生产环境出 bug 时，你需要看到每一轮的 prompt 和 response 才能定位问题。

### 面试万能框架：Agent系统设计三步决策

**第一步：选复杂度级别**

从简单到复杂逐级评估：
- 单次 LLM 调用（配合 RAG/few-shot）→ 固定输入输出、一次搞定
- 工作流（代码控制流程）→ 能拆成固定步骤（Prompt链/路由/并行化/编排者-工人/评估者-优化者）
- Agent（LLM 自己决定流程）→ 路径不可预测、步骤数不确定

关键判断句：用延迟和成本换更好的任务表现，这个 trade-off 值不值？

**第二步：设计工具（ACI）**

| 原则 | 做法 |
|------|------|
| 站在模型角度想 | 仅凭描述能否无歧义使用？告诉模型什么时候用、什么时候不用 |
| 防呆 | 改接口让犯错不可能（绝对路径、确认token、枚举代替自由文本） |
| 减少格式开销 | 不要求预知未来（diff的行数）、不要求转义（JSON里写代码） |
| 接近自然格式 | 模型训练数据中常见的格式更容易输出正确 |
| 测试迭代 | 跑大量示例看模型怎么犯错，改工具而不是改prompt |

**第三步：加安全边界**

- 停止条件：最大迭代次数、无进展检测、超时、检查点暂停
- Guardrails：输入侧（injection检测）、输出侧（独立LLM审查）、执行侧（确认token/阈值/沙箱）
- 人工介入：置信度低、不可逆操作、超出预设范围时升级

### 什么情况下使用Agent（详细判断标准）

**核心判断：你能不能提前画出流程图？能→工作流，不能→Agent。**

**四个适用信号：**
1. 步骤数不确定（修bug可能改1个文件也可能改10个）
2. 需要从环境反馈决定下一步（跑测试→读报错→改另一个文件）
3. 同一任务的不同实例走完全不同路径（两个客服对话路径完全不同）
4. 需要错误恢复能力（工具失败后自己换方式重试）

**反面信号（不该用agent）：**
- 每次走一样的步骤 → 工作流
- 不需要工具调用 → 单次LLM调用
- 对延迟敏感 → agent多轮循环太慢
- 错误代价极高且不可逆 → 人工审批流更安全

### ACI设计详解（带例子）

**核心理念：工具设计 = 给LLM做UX设计。**

**例子1：好的工具描述 vs 差的**

❌ `db_query(query: str)` — 描述："Execute a database query"
✅ `search_orders(user_id, status?, date_from?)` — 描述包含：什么时候用、什么时候不用、和其他工具的边界

**例子2：防呆——绝对路径**

模型cd到子目录后用相对路径出错。解决：参数名改为 `absolute_path`，接口层面让错误不可能发生。

**例子3：防呆——确认token**

`delete_user(user_id, confirmation_phrase)` — phrase必须是用户对话中说出的原文，工具层面验证。

**例子4：格式开销——文件编辑**

- Diff：需要预算行数（预知未来）→ 高出错率
- 重写整个文件：无格式要求但token多 → 低出错率
- Search-and-replace：折中方案，只需旧文本+新文本

**关键洞察：** Anthropic"花在优化工具上的时间比优化整体prompt更多"。改工具接口的效果比改prompt更持久可靠。
